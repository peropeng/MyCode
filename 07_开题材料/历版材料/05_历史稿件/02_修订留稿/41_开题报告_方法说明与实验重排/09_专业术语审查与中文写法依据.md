# 专业术语审查与中文写法依据

本次按三个标准核对专业表达：是否有稳定的学科含义，本文新定义是否明确对象、操作与判定，以及工程措辞是否准确传达研究内容。

以下分为“通用术语”“本课题操作定义”“工程表达”。操作定义可以在学术论文中使用，但须明确它指什么；中文论文出现过某个词，也不能自动证明本文对它的使用准确。

## 中文依据及使用范围

- **CN1：黄震华等《基于排序学习的推荐算法研究综述》**，《软件学报》2016，27(3)：691–713。[官网全文](https://www.jos.org.cn/html/2016/3/4948.htm)。本地读取引言、第2.1—2.2节及评价部分；支持“排序学习”“评分函数”“点级、对级、列表级”等通用表达。推荐对象与本文历史步骤不同，本文须重新定义候选组。
- **CN2：曹帅等《深度学习在基于信息检索的缺陷定位中的应用综述》**，《软件学报》2025，36(4)：1530–1556。[官网全文](https://www.jos.org.cn/html/2025/4/7288.htm)。本地读取引言、评估方法与讨论；支持“缺陷报告—候选源代码构件—定位结果”“文本表示、特征提取、评价指标”等表达。本文排序对象是历史步骤，不能把这类源码定位结果当作相同任务成绩。
- **CN3：香佳宏等《大模型在软件缺陷检测与修复的应用发展综述》**，《软件学报》2025，36(4)：1489–1529。[官网全文](https://www.jos.org.cn/html/2025/4/7268.htm)。本地读取引言、第5.1节修复机制、第5.3节及第6.4节挑战；支持“自动程序修复、补丁生成、补丁验证、测试用例、上下文、迭代修复”等表达。有限测试通过与更强的补丁正确性判断应分开。
- **CN4：李卿源等《神经程序修复领域数据泄露问题的实证研究》**，《软件学报》2024，35(7)：3071–3092。[官网全文](https://www.jos.org.cn/html/2024/7/7110.htm)。既有本地阅读记录支持按具体数据流说明训练/验证/评价隔离，不以“无泄露”一句替代核对过程。

CN1—CN4用于术语和研究写法参照。具体外部方法的结构、标注及成绩，仍以开题全文中对应原始论文为依据。下表“专业依据”标记CN文献时，表示它支持所用概念与写法，未表示它已经提出本课题的具体机制。

| 表达 | 分类及准确含义 | 本文使用建议 | 依据 |

| 大语言模型（LLM） | 通用模型类别 | 首次出现给中英文，后文用“大模型”或LLM并保持对应 | CN3；全文[1] |
| 智能体 | 通用概念，但不同研究定义有差别 | 本文明确为模型、工具、环境和持续执行机制组成的任务系统 | 全文[3,16,17] |
| 软件智能体 | 通用研究对象 | 说明能读取仓库、修改源码、运行工具，避免只给抽象名词 | 全文[2] |
| 工具调用 | 通用操作术语 | 指模型经接口发出读取、编辑、命令等操作；不等同于一次API生成请求 | 全文[2,3] |
| 环境观察／执行反馈 | 通用交互表述 | 写出是命令输出、测试结果还是文件内容；“反馈”须有具体来源 | 全文[3,22,23] |

| 缺陷定位 | 软件工程通用术语 | 通常定位当前文件、方法或语句；与本文的历史步骤定位区分对象 | CN2 |

| 排序学习（Learning to Rank） | 通用学科术语 | 写出训练数据、评分函数及排序对象，避免把一次数值排序等同于学习 | CN1 |
| 评分函数 | 通用学习术语 | 指共享的可学习映射；新轨迹可调用，不是每条轨迹手工定义分数 | CN1 |
| 点级／对级／列表级 | 排序学习通用分类 | 可用于解释监督视角；本文单正例softmax应说明组内训练对象 | CN1；全文[12,13] |
| 交叉熵／softmax | 通用模型与损失术语 | 保留英文函数名，给定它在哪个集合上归一化、标签如何定义 | 全文[11,13] |
| 独热标签／one-hot标签向量 | 通用编码术语 | 建议替代未解释的“独热目标分布”；如第2步为标签，四步向量是`(0,1,0,0)`，0不等于步骤完全正确 | 全文[13]及本文监督定义 |
| 单正例 | 排序学习中的通用标签情形 | 指一组仅有一个被标注的相关位置，不代表现实中只有一个有影响的错误 | 全文[13] |
| 图神经网络／消息传递 | 通用模型机制 | 说明谁是节点、依据什么连边、传递什么表示，不能只列算子名称 | 全文[35] |
| 关系通道 | 多关系表示中的通用建模表达 | 本文四通道为时间、角色、记录结构、动作结构，各自有明确构造规则 | 全文[35]及本文定义 |

| 残差／旁路 | 通用网络结构术语 | 说明原表示通过加法或拼接继续进入后续计算，其作用仍需消融验证 | 本文式（1）及评分结构 |
| 自注意力／查询、键、值 | 通用模型机制 | 解释查询对应当前候选，键用于匹配，值承载信息；注意力不是责任概率 | 全文[38] |
| 上下文 | 通用术语但范围易含糊 | 每次具体写模型读到的步骤记录、当前代码或测试反馈，区分诊断上下文和修复上下文 | CN3 |
| 多层感知机（MLP） | 通用模型术语 | 首次给全称，说明输出步骤分数，没必要逐层罗列函数 | 本文式（3） |
| 自动程序修复 | 软件工程通用研究术语 | 以给定缺陷及环境生成、验证补丁为基本任务背景 | CN3 |
| 候选补丁／补丁生成 | 通用修复术语 | 补丁是待应用或已应用的代码修改，候选尚待检查 | CN3 |
| 补丁验证 | 通用修复阶段 | 说明用何种测试、静态检查或其他条件筛选；测试通过不自动等于完整正确 | CN3 |
| 回归测试 | 通用测试术语 | 检查原本需要保留的行为；不能无条件保护与新需求冲突的过时行为 | CN3；全文[29] |
| 复现测试 | 通用程序修复表达 | 用于重现所报告的问题；可由方法内部生成，须与共享反馈测试区分 | CN3；全文[29] |
| 数据划分／训练、验证、评价 | 通用实验术语 | 写出任务分组隔离和实际使用环节，不能仅说“互相独立” | CN4 |
| 消融实验 | 通用实证方法 | 只改变指定模块，保持对应方法的其他条件，用来检验模块作用 | CN2及本文实验设计 |
| 控制实验 | 通用实验术语 | 写清变化因素和固定条件，避免所有变体都笼统称消融 | 本文5.5 |
| 参数匹配 | 通用公平比较表达 | 说明匹配模型容量以检查“参数更多”这一替代解释，不等于自动实现全面公平 | 本文4.3、5.5 |
| 配对比较 | 通用统计设计 | 在同一原始任务上比较方法差异，重复运行先按任务汇总 | 本文5.6 |
| 自助重采样／置信区间 | 通用统计术语 | 重采样单位是原始任务；重复轨迹不扩充独立问题数量 | 本文5.6 |
| 自然终止 | 常规算法运行概念 | 指方法自己的停止条件触发；与外部时间、费用、进程保护中断分开 | 本文5.3 |

## 需要明确写成“本文定义”的表达

| 表达 | 判断 | 建议定义或改写 | 理由 |
| --- | --- | --- | --- |
| 失败诊断 | 通用词在本文有特定操作定义 | “分析已失败执行轨迹，输出历史步骤责任检查次序” | 避免与异常检测、源码缺陷定位或一般自然语言归因混淆 |
| 责任步骤排序 | 本课题任务定义 | “对同一失败轨迹中的历史步骤评分，并按分数给出检查顺序” | 排序对象及责任标签都须说明，不能借名称推定存在完整责任全序真值 |
| 责任位置／责任标签 | 依来源规范确定的标签 | 分别说明哪个来源关注错误引入、职责遗漏或错过纠正机会 | 不能将来源标签直接称为无条件客观真因 |
| 检查优先级 | 对模型输出的解释 | “在当前观察与监督下，优先检查该位置” | 比“绝对责任概率”更对应实际监督与输出 |
| 匿名角色 | 编码操作的名称 | “同一轨迹内按首次出现顺序编号；同编号仅保持该轨迹内身份对应” | 不同轨迹的role1不必具有同一种职责；原角色名是否仍见于文本须据实际输入检查 |
| 可观察日志关系 | 本课题构图规则的总称 | 列明四类联系和邻居上限，并说明它们提供信息读取范围 | 同角色或同结构不自动等于语义因果依赖 |
| 关系增强表示 | 本课题网络输出名称 | “经过关系消息传播后的步骤向量” | 是计算阶段名，不是无需定义的独立学科概念 |
| 步骤上下文 | 本文候选相关聚合产物 | “针对当前被评分步骤，从同轨迹聚合得到的上下文向量” | 与所有步骤共享的平均向量、修复模型文本上下文区分 |
| 失败任务恢复 | 本课题恢复任务定义 | “从失败执行留下的代码及环境出发，利用诊断继续修正，以完成原始任务” | 避免被误解为撤销全部历史、系统重启或仅生成补丁 |
| 失败初态 | 实验输入状态名称 | “失败执行结束后固定保存的代码、环境和相关输入” | 它与原始仓库提交不同，必须有实际快照 |
| 可见测试 | 信息权限定义，与“修复反馈测试”同义 | “允许将代码、标识和执行结果提供给修复过程的测试” | “可见”描述求解过程的信息许可，不是测试能力强弱 |
| 目标测试 | 任务行为定义 | “检查本次问题要求实现或修复的行为的测试” | 是否在初态失败要据实际运行，不能把目标测试全部等同于失败项 |
| 可见目标 | 范围模糊，不宜直接使用 | 优先写“修复反馈测试中的目标测试”或“已通过目标测试标识”，按具体对象选择 | 原词容易混淆任务要求、测试集合与当前通过集合 |
| 修复反馈测试 | 本文明确采用的操作定义，不能假称固定标准术语 | 允许向修复过程开放测试代码、标识及执行结果的测试，亦称可见测试 | 有助于把信息边界讲清，但改名不改变原集合B、H、T的含义 |
| 独立验收测试 | 实验评价操作定义 | “与生成过程隔离，仅用于评价最终交付的规定测试” | 隔离的是信息使用，不能把“独立”当作对整个程序正确性的证明 |
| 恢复成功 | 项目成功标准 | “最终选定交付通过规定独立验收” | 与某轮反馈测试改善、候选被接纳区分 |
| 失败任务恢复成功率RSR | 本课题评价指标 | 给出任务、重复、预算、共同可判定集合和公式 | 不能只用缩写代替分母与成功标准 |
| 历史编辑 | 本课题筛选后的输入类型 | “成功执行且实际改变许可项目源码的历史操作及其差异” | 推理、读文件与未应用编辑仍是诊断步骤，但不是这类恢复输入 |
| 编辑选择／调用去重 | 具体输入处理操作 | 按排序筛选，用编辑调用标识去重，保留来源步骤 | 说明实际操作即可，不宜包装成未经定义的新理论 |
| 当前代码核对 | 具体修复操作 | 每轮重读与历史变更有关的当前文件与符号 | 历史差异不等于当前待改内容 |
| 候选接纳 | 本课题状态更新决定 | “候选满足保持条件后，更新为下一轮使用的代码状态” | “接纳”不等于恢复成功，也不保证修复目标增加 |
| 测试保持 | 本课题约束名称 | 明确保持B及累计已通过目标H的测试标识，不仅保持通过数量 | 其约束范围限于实际运行的稳定测试 |
| 动态测试保持 | 本课题具体设计 | 新接纳状态中新通过的目标加入后续保护集合 | “动态”来自集合随接纳更新，不代表测试代码本身可以变化 |
| 累计目标集合保持 | 可解释的操作名称 | 直接给B∪H_t⊆Pass(S′)，再用测试标识例子说明 | 应先解释对象，再给抽象名词 |
| 数量保持 | 对照策略名称 | 明确比较目标失败数或通过数，并规定不恶化规则 | 只保数量可能允许测试身份替换 |
| 仅回归保持 | 对照策略名称 | 只保护初始指定回归集合，不累计新通过目标 | 与完整策略区分，不能误写成不运行目标测试 |
| 输入机会／有效编辑数量分层 | 分析变量 | 用固定规则说明多少历史编辑真正可能进入有限输入 | 术语本身不能证明排序干预有效，需查实际请求 |
| 排序替换 | 控制实验操作 | 固定恢复流程、筛选与容量，只换步骤次序来源 | 与外部完整系统比较是不同实验 |

## 宜改为面向论文读者的具体表达

| 原表达 | 判断 | 建议 | 解释 |
| --- | --- | --- | --- |
| 样本资格 | 内部管理式概括，单独出现含义不明 | “实验对象纳入标准”“样本筛选条件” | 学术写法要说清筛选对象、条件及数量；没有必要把“资格”当新的技术概念 |
| 失败资格 | 不够明确的内部检查语 | “依据来源任务完成标准确认该次执行未完成任务” | 需要确认失败，但开题的实验流程应重点呈现如何准备、运行和评价；详细筛选规则可放备注或附录 |
| 合格问题／合格方法 | 可用普通形容词，必须跟条件 | “环境可重建、历史编辑可回查、反馈测试可执行的问题”；或“完成适配的基线” | 不能读作已取得有效结果或已完成全部评价 |
| 完整运行资格／门检／gate | 工程审核表达 | 用“运行前检查”“环境与实现核验”并写具体条件 | 工程记录可以保留，正文不宜用这些词替代实验步骤 |
| 来源池 | 数据管理简称 | “候选来源集合”或“已收集问题集合” | 候选数量、最终纳入数量、已完成评价数量应分开 |
| 冻结 | 实验工程中可用，但面向专家需具体 | “在正式运行前固定任务、参数、测试和判定规则” | 说明固定什么及何时固定，比反复使用“冻结”更清楚 |
| 共同分母／任务槽 | 内部汇报表达 | “固定计划任务数”“逐题结果矩阵”“共同可判定任务集合” | 槽位不是独立样本，重复运行也不增加问题数 |
| 曝光／未曝光 | 可表达开发使用历史，需具体 | “已用于方法开发或选择”“未用于本课题开发和选择” | 不能从“未曝光”推断基础模型训练绝对无污染 |
| 可执行／可恢复 | 普通技术形容词，范围常被省略 | 写明环境能否重建、测试能否运行、是否观测到成功 | 能运行不等于能修复；能继续执行不等于独立验收成功 |
| 自然终态 | 可作为运行状态说明，但偏抽象 | 优先“运行至方法自身停止条件触发” | 外部限时、费用未知或进程保护导致中断应单列 |
| 未知／未运行／删失 | 统计及运行状态可用 | 分别写验收结果尚不可判定、尚未启动、因外部条件中断而未观察到自然结束 | 这些状态不能直接填成正常算法失败 |
| 模型调用 | 范围不明确 | “大模型API请求次数”，明确请求、重试、子智能体及工具执行的计数规则 | 不能把模型生成、工具调用和内部前向计算混成一个数 |
| 词元 | 合法中文翻译，但本轮用户指定英文 | 统一写token，定义输入与输出的汇总范围 | 不应将用户习惯使用的通用英文强行替换为中文 |
| 完整流程墙钟时间 | 有技术含义，本轮已要求删除该资源指标 | 资源表保留token与大模型API请求次数；时间预算仍按实验节点说明 | 删除指标不等于取消30分钟等预算节点或停止规则 |
| 显存／内存开销 | 有技术含义，本轮已要求删除 | 从资源指标及相关创新验证句一并删除 | 不是术语错误，是本轮交付范围调整 |

## 易被误读的专业说明

1. **“同角色、同结构”是可观察联系，不是已经证明的语义依赖。** 它们规定从哪里读邻居信息，模型及控制实验再检验这种读取是否有用。
2. **“责任标签”由来源规范确定，不等于最终报错行。** 有的来源标错误编辑，有的来源可标漏检的验证步骤；标签含义应随来源报告。
3. **“单责任位置监督”不等于其他步骤都没有问题。** 标签仅给一个优先位置，剩余候选的完整次序由模型估计。
4. **“注意力权重”不等于责任概率。** 注意力分配信息汇集权重，责任次序由后续评分器产生。
5. **“诊断正确”不自动等于“恢复输入更好”。** 排名要经过可编辑操作筛选、去重和容量限制，实际请求可能保持不变。
6. **“候选被接纳”不等于“目标更多通过”。** 原规则允许在保持已有通过项的条件下接纳未增加通过目标的候选，给不同实现路径保留空间。
7. **“测试保持”不保证所有需求正确。** 保证范围限于已经执行、标识稳定且结果确定的测试。独立验收用于检查未作为修复反馈的规定行为。
8. **“完整系统比较”与“模块控制”回答不同问题。** 前者比较整套方法的任务效果，后者固定流程只改变一个因素，以解释作用环节。
9. **“三次独立重复”是对生成随机性的观察，不是三倍问题数。** 统计单位仍是原始问题；内部候选、投票或响应复制不能算独立完整重复。
10. **“20个问题”应指固定任务清单或明确的计划样本量。** 若不是20个都经过同一条件检查并完整评价，不能把它写成已完成的20题独立实验。

## 专业说明的逐项判断

第三章的方法说明已在[按段分析](08_开题分析_按段解释.md)解释其对象、操作、作用和依据。以下结论用于审查措辞，不把文风判断替代技术验证。

四类日志关系、两层门控传播、候选相关自注意力和MLP评分均具有明确计算操作，可以作为学术方法说明。四类具体日志关系是本文设计，不能写成领域公认的因果关系。事件配对融合只在来源给出对应时使用，不能概括为任意相邻记录都会配对。

历史编辑选择、调用去重、当前代码读取和输入截断属于可复现的方法操作；它们是否带来收益，需要排序替换、输入记录和任务结果支持。不能仅因加上“上下文”“增强”“引导”等词，就把工程处理自动写成已经证明的创新。

补丁生成、测试执行及补丁验证沿用自动程序修复通用阶段。本文的具体设计在于输入材料怎样由诊断形成，以及新通过目标怎样进入后续保持条件。B、H、T和Pass的定义明确后，集合保持是可检验的状态更新规则；它只约束有限已执行测试，不能称为对所有程序行为的正确性保证。

“样本资格”“失败资格”可以出现在内部检查记录中，但未定义时不能帮助读者理解研究。当前正文改为确认执行未完成、环境可重建、历史编辑可回查及测试可执行等具体纳入条件。实验流程页的主体因此是怎么运行、何时选定交付、怎样独立验收。

## 中文论文写法怎样落实到本稿

研究意义参考CN2与CN3引言的论证顺序：先说软件维护中的缺陷分析、定位和验证负担，以及质量维护价值；再说明智能体连续执行留下的新过程问题。2.2不以“将使用某网络、某注意力”代替意义，也不引用综述中的历史成本比例充当本文预期提升。

方法说明参考CN2对输入、定位对象及输出的界定，以及CN3第5节“定位—补丁生成—补丁验证”的展开。RQ2因而明确大模型接收原问题、历史编辑、当前代码与执行反馈，提出补丁，再由应用和测试结果决定状态更新；专业表达与实际操作保持对应。

实验说明把任务、共同初态、完整运行、交付和验收连成可执行顺序，指标先于基线。Top-1用于所有诊断方法，完整排序方法再比较MRR与Hit@3/5；恢复基线共同使用RSR及token/API请求次数。写法参照不代表把其他任务的成绩直接搬到本文。
