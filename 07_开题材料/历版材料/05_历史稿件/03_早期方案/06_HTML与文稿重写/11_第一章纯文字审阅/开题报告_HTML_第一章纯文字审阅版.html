第一章 绪论：研究背景与国内外研究现状

1.1 研究背景

近年来，大语言模型驱动的智能体逐渐从单轮文本生成系统发展为能够持续调用外部工具、读取中间结果并修改执行环境的软件系统。智能体可以通过检索、文件编辑、代码运行、测试、进程管理和版本库操作完成较长的任务。工具调用使智能体获得了改变环境的能力，也使任务结果不再只由最终回答决定。文件内容、进程状态、依赖关系和版本库差异都会成为后续步骤可以继续读取的执行状态。

这种执行方式改变了传统失败分析的对象。单轮问答中，错误通常可以在最终答案中直接观察；在有状态工具调用中，早期步骤造成的局部偏差可能被后续步骤继续使用、扩大或暂时掩盖，直到测试、验收或提交阶段才表现为明显失败。因此，最后出现错误的位置不一定是最早造成状态偏离的位置。若只依据最后一条报错信息定位责任，容易把症状位置误认为责任位置。

工具调用还使恢复过程具有状态依赖。删除一条可疑指令并不必然能够恢复任务，因为后续步骤可能已经基于该指令产生的状态继续修改同一文件、进程或仓库。恢复范围过小，错误状态会继续残留；恢复范围过大，又会连带撤销与故障无关的正确工作。可靠恢复需要同时考虑责任步骤、后续依赖和可验证的状态变化，并在隔离环境中重新执行恢复候选。

由此，智能体失败处理逐渐形成两个相互联系的研究方向。一方面，需要从完整执行轨迹中识别更可能导致失败的步骤，并使所有步骤具有可比较的责任次序。另一方面，需要把诊断结果转化为具体的回退、重放和验收操作，检验目标状态是否恢复以及非目标状态是否受到影响。前者提供恢复的优先依据，后者检验诊断是否具有实际效用。两者之间的连接，构成本文研究问题的现实背景。

1.2 研究现状与问题来源

现有研究已经从不同角度说明执行轨迹、跨步交互和恢复上下文的重要性。部分工作关注智能体在真实软件环境中的工具使用过程，部分工作关注多智能体系统中的失败归因，另一些工作则关注错误发现后的回退、修复和状态保持。这些研究为理解智能体为什么失败、错误如何传播以及恢复为什么需要上下文提供了基础，但不同方向之间的输出形式和验证对象并不一致。

本文将相关论文分为国外研究和中国研究两部分介绍。这里的“国内研究”按论文作者及研究团队所属的中国高校或科研机构界定；国外研究则指中国以外的研究团队。论文名称在正文中采用便于阅读的简称，同时保留年份、作者和发表 venue，使研究脉络能够被准确识别。

1.3 国外研究

Who&When

2025年，Zhang等人在ICML发表Who&When，讨论多智能体任务失败中“由谁负责”和“何时发生关键行为”的区分。该工作把失败归因从主体层面推进到时间位置层面，说明责任主体识别和责任步骤识别并不是同一个问题。它对本文的直接启发是，失败轨迹需要保留步骤顺序和上下文，不能只根据最终输出或单个智能体标签进行判断。与此同时，Who&When主要关注责任归因本身，尚未把全部步骤组织成可直接供恢复系统使用的完整排序。

ReAgent

2025年，Zhao等人在EMNLP发表ReAgent，研究多智能体多跳推理中的可逆执行。当系统发现当前推理与已有证据发生冲突时，ReAgent可以回到较早的有效状态，并根据错误范围选择局部回退或全局回退。该工作说明，恢复不能简单理解为继续向前尝试，系统需要保留可以返回的有效状态，并根据失败影响范围决定回退粒度。ReAgent的实验对象主要是知识增强问答中的推理状态，而软件工具调用还会产生文件、进程和版本库等外部副作用，因此其回退思想需要进一步转化为面向环境状态的依赖范围选择。

SWE-agent

2024年，Yang等人在NeurIPS发表SWE-agent，将智能体置于真实软件仓库中，通过定位、编辑、运行测试和修正等工具操作完成软件工程任务。该工作证明，工具接口和执行过程会显著影响智能体的任务表现，也为记录完整工具轨迹提供了成熟范式。它为本文提供了有状态执行环境和可观测轨迹的研究背景，但论文的主要评价对象是任务完成效果，并未进一步回答一条失败轨迹中哪一个步骤应当优先被归因或恢复。

TraceElephant

2026年，Chen等人在ACL发表TraceElephant，强调对输入、工具调用、上下文和执行环境进行完整轨迹观测。该工作针对只查看最终答案或少量消息所造成的信息缺失，建立了面向失败归因的全轨迹数据基础。它说明，步骤级责任判断必须同时利用动作内容、上下文和环境反馈。不过，完整观测仍然只是诊断的输入，不能自动形成跨任务稳定的责任排序，也不能直接说明后续恢复应当覆盖哪些状态。

StepFinder与CAM

2026年，Zhu等人提出StepFinder，以时序语义和跨步交互进行多智能体失败归因；同年，Lyu等人提出CAM，分析中间特征及其交互对代码生成结果的贡献。两项工作共同说明，早期动作的影响可能在后续步骤中显现，局部异常与跨步结构需要同时建模。它们推动了步骤级和交互级分析，但仍主要停留在责任解释或贡献分析层面。本文进一步关注如何把这种诊断结果组织为覆盖完整轨迹的排序，并在独立执行中检验排序对恢复选择的影响。

1.4 中国研究

Process-Centric Analysis

2026年，Liu等人在PACMPL发表Process-Centric Analysis of Agentic Software Systems，从过程中心视角分析智能体软件系统，将工具接口、任务阶段和执行轨迹视为系统行为的一部分。该工作与本文关注的状态化执行环境具有较强关联，说明智能体研究不能只围绕模型输出展开，还需要分析过程中的工具交互和状态变化。其不足在于，过程理解并未直接给出面向失败恢复的步骤优先次序，诊断结果与恢复执行之间仍然存在接口缺口。

APR Traceability

2026年，Ceka等人发表Understanding Automated Program Repair Agents Through the Lens of Traceability，从可追踪性角度分析自动程序修复智能体的定位、编辑和验证过程。该工作把中间决策和执行记录纳入修复评价，使研究者能够回看智能体如何从故障信息走向补丁结果。它对本文的启发在于，恢复过程必须可审计，不能只报告最终是否成功。但自动程序修复的核心对象是代码补丁，而本文面对的是工具调用造成的外部状态，需要额外处理回滚、重放和非目标状态保持。

Multi-granularity APR

2024年，Lin等人在ISSTA发表One Size Does Not Fit All，比较不同修复粒度对自动程序修复结果的影响。该工作表明，修复范围并不存在适用于所有故障的固定尺度，过细或过粗的候选都可能降低修复效果。这个结论可以迁移到状态恢复范围的讨论中：恢复候选需要在单点、等规模范围和依赖闭合范围之间进行有控制的比较。不过，代码补丁粒度与工具状态恢复范围并不完全等价，仍需通过统一任务、统一候选池和统一执行预算建立直接证据。

中国研究的总体特点

中国研究更强调过程分析、工程化追踪和修复行为的可解释性，为有状态智能体的失败研究提供了系统工程视角。与国外研究侧重责任归因、可逆推理和完整轨迹观测相结合，可以看到当前研究已经覆盖了问题的多个环节，但各环节的输出尚未统一。尤其是，责任排序通常停留在诊断评价，恢复研究通常从候选回退或修复策略开始，两者之间缺少一个能够把步骤优先次序传递给状态恢复执行的中间层。

1.5 研究切入点

综合国内外研究可以看到，现有工作已经分别解释了轨迹观测、跨步交互、可逆推理、修复粒度和过程追踪的重要性。它们共同支持这样一个判断：智能体失败不能只依据最终症状处理，系统需要回看完整执行过程，并根据错误影响范围选择恢复动作。与此同时，现有研究的验证对象分散在推理状态、代码补丁、GUI操作和软件工程轨迹等不同场景中，责任归因的输出也常常是单个位置、有限候选或解释性分数，难以直接用于统一的恢复执行比较。

本文据此把研究对象限定为包含工具调用和可观测状态变化的失败轨迹。研究首先关注如何在不依赖原始词汇身份的条件下，对完整步骤进行可比较的责任排序；随后关注如何依据排序组织候选恢复范围，并在隔离环境中实际重放。恢复结果同时考察目标状态是否恢复、非目标状态是否保持以及执行资源是否可接受，从而把诊断证据与恢复行为放在同一条可审计链条中考察。
