## 0. 先用一句话理解整篇论文

给定一条已经失败的智能体执行轨迹，先为全部可评价步骤生成一个**责任候选优先级排序**；再按照这个顺序，在固定预算内依次尝试若干个可撤销的恢复计划。一个计划只有在“目标任务恢复”且“非目标状态没有受到不可接受的破坏”时才提交，否则撤销并尝试下一个候选。

可以把整条研究主线压缩为：

```text
失败轨迹
  ↓
哪些步骤更值得优先检查？                 —— RQ1：责任候选排序
  ↓
πq = [步骤4, 步骤2, 步骤6, ……]
  ↓
先围绕哪个步骤、处理多大范围？           —— RQ2：恢复计划生成与排序
  ↓
从一致检查点隔离执行；目标与非目标双边验收 —— 可靠执行
  ↓
通过：提交；不通过：撤销并尝试下一计划
```

这里最重要的不是某个网络结构，而是三个接口被严格分开：

1. **诊断接口**：RQ1 只输出排序，不直接决定最终恢复结果；
2. **执行接口**：RQ2 只读取已经冻结的排序，不用恢复结果反向改分；
3. **验收接口**：是否提交由真实执行后的验证器决定，不由模型自我评价决定。

## 1. 用一个贯穿全文的例子理解问题

假设一个软件工程智能体要修复“配置读取错误”，它产生了如下轨迹：

| 步骤 | 动作 | 表面结果 | 真实作用 |
|---|---|---|---|
| 1 | 阅读 issue | 成功 | 理解任务 |
| 2 | 搜索配置文件 | 成功 | 误把 `legacy/config.py` 当成目标文件 |
| 3 | 打开文件 | 成功 | 基于错误路径继续执行 |
| 4 | 编辑 `legacy/config.py` | 成功 | 写入了错误状态 |
| 5 | 运行局部测试 | 通过 | 测试覆盖不充分，未暴露问题 |
| 6 | 再次编辑 `legacy/config.py` | 成功 | 继续固化错误状态 |
| 7 | 修改 `tests/test_config.py` | 成功 | 改动了另一目标对象 |
| 8 | 运行完整测试 | 失败 | 失败第一次被明确暴露 |

只看最后一步，会误以为步骤 8 是“错误步骤”；但步骤 8 只是把已有问题暴露出来。真正值得优先干预的候选可能是步骤 4、步骤 2 或步骤 6。

RQ1 可能输出：

```text
πq = [4, 2, 6, 7, 3, 5, 1, 8]
```

这表示：在当前可观察证据下，步骤 4 最值得优先检查，步骤 2 次之，步骤 6 再次之。它不是“步骤 4 已经被证明具有真实因果效应”，而是一个用于后续排查和恢复的**优先级判断**。

围绕步骤 4，RQ2 可以生成三类计划：

```text
单点范围：              只撤销/屏蔽步骤4的状态增量
等规模前向范围：        处理两个后续状态动作，但不要求它们与步骤4同目标
同目标前向关联范围：    处理步骤4和步骤6，因为它们都修改 legacy/config.py
```

每个计划都从全新的隔离副本开始。系统撤销或屏蔽计划指定的状态增量，再按既定规则重放其余过程，最后运行：

- 目标探针：原始配置问题是否解决；
- 非目标检查：其他文件、测试和状态是否仍满足约束；
- 冲突检查：是否新增执行冲突。

双边验收通过才提交，否则丢弃该副本并尝试下一计划。

这个例子已经包含全文的核心：**失败暴露位置不等于应优先干预位置；责任判断需要排序；恢复需要范围；范围执行需要可撤销；可撤销还不等于可提交，必须经过真实验收。**

## 2. 四个必须先区分的概念

### 2.1 失败检测、失败诊断、责任定位和任务恢复

| 概念 | 回答的问题 | 典型输出 |
|---|---|---|
| 失败检测 | 任务是否已经异常？ | 成功/失败、异常分数、触发时间 |
| 失败诊断 | 失败可能由什么形成？影响了哪些部分？ | 原因类别、候选范围、证据 |
| 责任定位 | 哪个主体或步骤更值得优先检查？ | 责任 Agent、责任步骤、步骤排序 |
| 任务恢复 | 怎样干预才能让本次任务重新达到验收条件？ | 回退、重放、替代计划、提交/撤销结果 |

本文不是重新做一个失败检测器。输入已经是失败轨迹，核心是：

- RQ1：把失败轨迹转化为步骤级责任候选排序；
- RQ2：把排序转化为实际可执行、可撤销、可验收的恢复尝试。

### 2.2 “责任”不等于“真实因果”

当前方法使用的位置、角色、动作结构、返回结构和步骤间关系都属于**可观察证据**。这些证据可以支持“优先检查谁”，但不能自动证明：

> 对该步骤实施干预，一定会以可识别的因果方式改变最终任务结果。

因此，论文中更稳妥的说法是：

- 责任候选优先级；
- 决定性错误步骤的预测；
- 可观察的跨步骤关联或依赖代理；
- 真实恢复实验为排序提供下游效用证据。

不宜直接写：

- 找到真实根因；
- 学习到了因果图；
- 证明某条边是错误传播路径。

真正的因果责任通常要求受控干预、反事实替换或更严格的因果识别条件。本文的 RQ2 可以提供一定的**干预一致性证据**，但仍不应把相关代理直接写成真实因果边。

### 2.3 “最早出错”也不一定等于责任步骤

直觉上，我们容易把责任定义成“最早出现错误的步骤”。但完整执行环境中还存在**可恢复机会**：

- 上游步骤产生了错误；
- 后续验证器已经看到异常，却没有纠正；
- 最终失败可能更应该归因于漏检或错误放行的验证步骤。

TraceElephant 使用了带恢复含义的决定性步骤标准：责任判断不仅看最早偏差，还看哪个步骤使系统错过了恢复机会。因此，论文中最好使用：

> 决定性偏差引入或未能纠正的位置

而不是机械地写成：

> 最早发生错误的位置。

### 2.4 普通日志不等于可用于诊断的轨迹

普通日志可能只记录模型输出或工具返回。本文所需的轨迹至少要恢复：

- 步骤次序；
- 当前角色；
- 动作与参数结构；
- 工具反馈；
- 可观察的状态变化；
- 最终任务结果；
- 训练或评价阶段可用的责任标注。

证据不完整时，模型能力再强也可能无法定位；证据过多但没有结构化时，又会产生长上下文噪声。这正是 TraceElephant 与 StepFinder 分别提供的启示。

# 第一部分：RQ1——怎样形成完整责任候选排序

## 3. RQ1 的形式化对象

对任务组中的一条失败轨迹，记为：

```text
T_q = (x_1, x_2, ..., x_(n_q))
```

其中每个候选步骤 `x_i` 包含测试阶段可观察的行为、角色、位置、反馈和结构信息。排序函数输出：

```text
s_i = f_theta(x_i, T_q)
```

其中 `s_i` 是步骤 `i` 的责任候选优先级分数。按分数从高到低排列全部候选，得到：

```text
pi_q = 将 C_q 中全部候选按 s_i 从高到低排列
```

为了避免概念混乱，建议把 `s_i` 解释为：

> 在当前轨迹和可观察证据下，步骤 `i` 应被优先检查或作为恢复锚点的程度。

不要直接解释为“真实责任概率”或“因果贡献”。

### 为什么要输出完整排序，而不是只输出 Top-1

Top-1 只告诉系统第一次试哪里，但真实恢复存在四种情况：

1. 最高分步骤不是可逆状态动作；
2. 最高分步骤恢复成本太高；
3. 第一次恢复计划执行失败；
4. 多个候选分数接近，需要在预算内继续尝试。

完整排序保留了后续候选的相对次序，使诊断结果可以直接成为有限预算下的恢复队列。

---

## 4. 局部证据：先判断“一步本身看起来是否可疑”

### 4.1 局部表示应该包含什么

当前方案把测试阶段可见的单步信息组织为局部表示，主要包含：

| 特征组 | 示例 | 它能回答什么 |
|---|---|---|
| 动作结构 | 工具类别、参数键集合、动作是否为空 | 这一步在做什么类型的操作？ |
| 结果结构 | 成功/失败、返回长度、返回结构 | 工具是否异常返回？反馈形态是否特殊？ |
| 角色信息 | 匿名角色索引 | 哪个职责在执行这一步？ |
| 过程位置 | 连续相对位置、前/中/后三阶段 | 它出现在任务的哪个阶段？ |
| 局部异常先验 | 由测试可见规则产生的异常提示 | 单看当前步骤，是否存在可复核异常？ |

这里有一个必须修正的表述：v13 中把某一维写成“局部责任分数”，同时又说整个向量是局部排序器的输入，这容易形成循环定义。若该量来自模型输出，就不能再作为同一个模型的输入；若它来自固定规则，应明确改名为：

> **局部异常先验分数**或**可观察启发式异常分数**。

精确的 17 维、23 维只是当前原型的实现配置，不是理论核心。答辩时首先解释“证据类别”，精确维数放在附录。

### 4.2 为什么位置只能作为证据，不能直接当标签

许多失败确实在早期形成，但也存在：

- 后期错误提交；
- 验证器漏检；
- 最终一步执行了真正有害的动作；
- 多角色系统中责任由协作关系决定。

因此，连续相对位置和阶段编码可以帮助模型理解过程，但不能预设“越早越有责任”或“越晚越有责任”。正确做法是把位置作为普通可观察特征，由训练数据学习其作用。

## 5. 为什么使用任务内成对排序，而不是逐步二分类

### 5.1 RankNet 真正规定的学习对象

对任务 `q`，记候选步骤集合为 `C_q`，人工标注的 Gold 责任步骤为 `g_q`，步骤 `i` 的特征向量为 `z_(q,i) in R^d`。对任一非责任候选 `j in C_q 且 j != g_q`，训练监督表达的是：

> 在同一条失败轨迹内，`g_q` 应排在 `j` 前面。

若单候选效用为 `u_(q,i) = f_theta(z_(q,i))`，RankNet 使用两个候选输出之差定义偏好概率：

```text
o_(q,g_q,j) = u_(q,g_q) - u_(q,j)
P(g_q 排在 j 前) = sigmoid(o_(q,g_q,j))
```

其中，`g_q ranks before j` 表示 Gold 步骤的排序优先级高于候选 `j`，`sigmoid(t)=1/(1+e^(-t))` 是 Logistic 函数。在线性效用模型下，

```text
u_(q,i) = w^T z_(q,i)
o_(q,g_q,j) = w^T [z_(q,g_q) - z_(q,j)]
```

令

```text
d_(q,j) = z_(q,g_q) - z_(q,j)
```

则理论上的单个有序偏好样本可以写为 `(d_{qj},1)`。RankNet 的关键是“同一任务内比较”和“用效用差训练相对次序”，并不强制把交换顺序后的样本再复制一次。

### 5.2 当前代码为什么显式构造正反样本

当前原型没有单独实现一个固定反对称结构的 RankNet 输出层，而是复用了带可学习截距的通用二元逻辑回归：

```text
p_n = P(y_n = 1 | d_n) = sigmoid(w^T d_n + b)
```

因此，每个原始 Gold—非 Gold 候选对被展开为：

```text
正向训练行：( d_(q,j), 1)
反向训练行：(-d_(q,j), 0)
```

代码实际优化的加权二元交叉熵与 `L_2` 正则目标可写为：

```text
L(w,b) = mean_n[-omega_pos*y_n*log(p_n)
                 -(1-y_n)*log(1-p_n)]
         + (lambda/2)*||w||_2^2
```

各符号和当前实现参数如下：

| 符号或参数 | 含义 | 当前冻结值 |
|---|---|---:|
| `d_n` | 一条候选对的特征差向量 | 由任务内 Gold 与非 Gold 步骤构造 |
| `y_n` | 差分方向标签 | 正向为 1，反向为 0 |
| `w` | 决定各证据维度排序方向和强度的权重 | 由训练折估计 |
| `b` | 通用逻辑回归的截距 | 训练时估计，推理排序时不使用 |
| `N` | 展开后的训练行数 | 原始候选对数的 2 倍 |
| `omega_pos` | 正类损失权重 | 1.0 |
| `lambda` | `L_2` 正则强度 | 0.001 |
| epochs | 全批量梯度下降轮数 | 200 |
| learning rate | 梯度下降步长 | 0.05 |

只保留 `(d_{qj},1)` 而继续使用这段通用逻辑回归代码时，训练标签将全部为 1。由于截距 `b` 不受 `L_2` 正则约束，模型可以主要通过不断增大 `b` 来降低损失，而不必从 `d_{qj}` 中学习“哪一个差分方向表示更应负责”。这会把排序学习退化为近似恒定的正类判断。

加入交换方向的样本有三个具体作用：

1. **补齐两个类别**：避免训练集只有正类标签；
2. **施加交换一致性**：若 `g_q ranks before j`，交换输入后就应得到 `j does not rank before g_q`；
3. **消除截距捷径**：当正负样本严格对称且 `omega_pos=1` 时，对称损失的最优截距趋于 `b=0`，模型必须主要依靠 `w^T d_(q,j)` 学习偏好方向。

需要特别注意：反向样本没有增加新的人工标注或新的独立统计证据，只是把同一偏好约束按两个方向编码。实验记录中的独立样本数仍应按任务、轨迹或原始候选对统计，不能把展开后的 `2N` 行当成两倍独立数据。

正反展开只平衡了“偏好方向”的 0/1 标签，并没有自动使不同长度的任务等权。若任务 `q` 有一个 Gold 和 `|C_q|-1` 个非 Gold 候选，它会贡献 `2(|C_q|-1)` 条展开训练行；当前代码保留全部候选对且未按任务重新加权，因此候选较多的轨迹对参数估计贡献更大。正式协议应明确采用“候选对等权”还是“任务等权”，后者可通过每任务归一化权重或任务内采样实现。

### 5.3 正反样本不是成对排序的普遍硬性要求

如果模型直接写成无成对截距的 RankNet 形式

```text
P(x_a 排在 x_b 前) = sigmoid(u_a - u_b)
```

或者模型结构本身保证 `r(x_a,x_b)=-r(x_b,x_a)`，那么只按一个固定方向输入“高相关候选—低相关候选”即可训练。DirectRanker 对反射性、反对称性和传递性作了形式化分析，并明确指出：在结构已经保证反对称时，训练时固定高相关样本位于一侧就足够。

因此，本研究应把“正反样本”表述为**适配当前通用逻辑回归实现的对称化编码**，而不是写成“RankNet 必须复制正反两类样本”。

### 5.4 成对偏好怎样转成完整排序

训练完成后，对任务 `q` 中每个候选独立计算共享效用：

```text
u_(q,i) = w^T z_(q,i)
```

任意两步的偏好对数几率由效用差给出：

```text
logit[P(x_i 排在 x_j 前)] = u_(q,i) - u_(q,j)
```

截距 `b` 不进入单候选效用，也不会改变任务内候选次序。按 `u_{q,i}` 降序排列即可得到完整排序：

```text
pi_q = 将 C_q 中全部候选按 u_(q,i) 从高到低排列
```

若需要在同一任务内显示归一化权重，可以进一步计算：

```text
p_tilde_(q,i) = exp(u_(q,i)) / sum_{k in C_q} exp(u_(q,k))
```

Softmax 不改变排序，但这些权重只在同一候选集合内可比较，不能直接解释为跨任务校准后的“真实责任概率”。所以，第24页“通过正反成对样本获得任务内可比较分数”应准确理解为：**共享效用差产生任务内可比较次序；正反样本负责让当前带截距的训练器稳定地学习该方向。**

### 5.5 这样设计解决了什么

1. **直接优化相对次序**：最终目标本来就是“谁排在谁前面”；
2. **允许不同长度的候选集合**：每条轨迹只在自身集合内比较；训练时是否让各任务等权仍须单独规定；
3. **缓解逐步二分类的不平衡问题**：训练目标围绕 Gold—非 Gold 偏好对构造，而不是让大量独立负步骤主导损失；
4. **自然输出完整排序**：共享效用可以直接排序，不需要把彼此独立、未必可比的分类概率拼成队列。

### 5.6 必须说明的标签前提

若数据中每条轨迹只有一个 Gold 决定性步骤，以上构造比较直接。若存在多个等价责任步骤，则需要提前规定：

- 多正例之间是否并列；
- 是否只与负例构造训练对；
- MRR 按第一个命中还是多相关项计算。

这个口径必须写进协议，否则“完整排序”会因标签语义不同而不可复核。

## 6. 跨步骤关系：为什么单看每一步还不够

### 6.1 一个步骤可能“局部正常、全局错误”

工具调用返回成功，只说明调用被执行，不说明它符合任务目标。以下情况都需要跨步信息：

- 某一步重复执行了先前已经失败的调用结构；
- 同一角色连续采用错误策略；
- 某个状态动作修改了文件，后续动作继续修改同一文件；
- 一步的返回内容被相邻步骤立即读取并放大。

因此，当前方法把一条轨迹构成多通道步骤图。

### 6.2 四类关系分别表达什么

“四个通道”不是四个顺序执行的模块，也不是四个不同模型。所有通道共享同一批步骤节点，但分别保存四套邻接表；它们相当于从四种结构语义观察同一条轨迹。

| 关系通道 | 当前代码的实际建边规则 | 希望补充的上下文 | 不能声称的内容 |
|---|---|---|---|
| 时间邻接 | 连接当前步骤的前一个和后一个执行步骤 | 紧邻步骤间可能发生局部状态或信息传播 | 时间相邻不等于因果关系 |
| 同角色 | 连接最近的前一个和后一个同匿名角色步骤 | 同一职责在不同时刻的连续尝试、策略延续或纠错 | 同角色不等于共同负责 |
| 同完整结构签名 | 连接最近的前一个和后一个同完整匿名结构签名步骤 | 整体调用与返回结构的重复，可能对应重试或模式复现 | 结构相同不等于语义和目标对象相同 |
| 同非空动作结构 | 只对存在有效动作的步骤，连接最近的前一个和后一个同动作结构步骤 | 忽略自然语言和结果差异后，识别相同类型有效操作的重复 | 动作结构相同不等于修改了同一状态 |

这里“最近的前一个和后一个”很重要：当前实现不是把所有同类步骤连成完全图，而是只连接时间上相邻的同类出现位置，从而限制边数和传播范围。

可以把一条轨迹想成下面的例子：

| 步骤 | 匿名角色 | 主要行为 | 可能进入的关系通道 |
|---|---|---|---|
| 1 | role_A | 形成计划 | 与步骤2形成时间邻接；与后续最近的 role_A 步骤形成同角色边 |
| 2 | role_B | 调用编辑工具 | 与步骤1、3形成时间邻接；与后续最近的 role_B 步骤形成同角色边 |
| 3 | role_B | 运行检查工具 | 与步骤2、4形成时间邻接；与步骤2形成同角色边，但通常不形成同动作结构边 |
| 5 | role_B | 再次调用相同结构的编辑动作 | 可能与步骤2形成同完整结构边或同非空动作结构边 |

四个通道的目的不是预先判定“哪条边代表错误”，而是给排序器提供四种可复核的跨步上下文。若把所有边直接混成一种邻接，模型将无法区分“只是时间相邻”“同一个角色再次尝试”和“相同动作结构再次出现”。

这里建议统一使用“跨步骤关联”或“依赖代理”，而不是直接把四类边称为“因果依赖”。

### 6.3 两轮无参数消息聚合怎样工作

对关系通道 `c`，节点 `i` 在第 `r` 轮接收邻居均值：

```text
若通道 c 中节点 i 存在邻居：
    m_(i,c)^(r) = 通道 c 内所有邻居上一轮表示 h_j^(r-1) 的均值
若不存在邻居：
    m_(i,c)^(r) = 全零向量
```

随后进行残差更新，例如：

```text
h_i^(r) = h_i^(r-1) + sum_c m_(i,c)^(r)
```

第一轮看到直接邻居，第二轮看到经邻居传递的二跳上下文。当前传播本身没有可学习参数，因此它不是一个复杂的端到端 GNN；真正学习排序的是后面的成对排序器。

对每个节点，四个通道分别计算邻居均值并保留为不同特征块。例如，某一步在“时间邻接”通道收到的是前后步骤信息，在“同角色”通道收到的可能是相距较远但由同一角色执行的步骤信息。后续排序器可以学习这两类信息应取不同权重。

这样设计有两个优点：

- 每类关系的含义可以单独解释、删除或置乱；
- 增益不容易被归因于“多了一大堆图网络参数”。

### 6.4 当前代码中的 215 维表示

实验112与112C的实际协议是：

```text
23 + 92 + 92 + 8 = 215
```

其中：

- 23：初始局部表示；
- 92：4 个通道的一轮消息，4×23；
- 92：4 个通道的二轮消息，4×23；
- 8：每个通道一个平均相对距离和一个邻居存在位，4×2。

实际拼接方式是：

```text
g_i = [初始局部表示，四通道第一轮消息，四通道第二轮消息，
       四通道平均相对距离，四通道邻居存在位]
```

当前代码没有额外拼接“第二轮减第一轮”的轮间差值。若PPT把215维解释为同时包含两轮原始消息、轮间差值和存在位，维数会不成立；正式表达应以上述实际协议为准。

## 7. 交互排序器和结构负对照

将图表示 `g_i` 代入同样的成对学习目标，可以得到跨步骤交互分数：

```text
s_i^(graph) = w_g^T g_i
```

真正重要的不是“用了图”，而是证明图分支提供的有效信息来自步骤之间的正确关系，而不是来自额外维数、额外计算或任意平滑。所谓“保持节点特征、训练目标和排序器容量一致”，就是在对照实验中固定以下内容：

- 每个步骤原有的23维局部特征不变；
- Gold—非 Gold 成对训练目标不变；
- 排序器、优化器和参数规模不变；
- 只改变关系边与步骤之间的对应方式，或者屏蔽图分支输出。

这样，如果真实关系条件优于对照，差异才可以归因于关系信息，而不是“完整模型用了更多特征或更大模型”。

### 7.1 当前协议实际实现的三个图关系对照

| 当前条件 | 实际操作 | 保持了什么 | 真正回答的问题 |
|---|---|---|---|
| `B2_deletion` | 将图效用全部置零，使B2退化为原有成对局部排序 | 相同任务、局部分数、排序规则和评测口径 | 图分支整体是否提供额外排序信息？ |
| `B2_shuffle` | 在同一条留出轨迹内置乱最终图效用分数，保留分数多重集合 | 图分数的数值分布和数量 | 图分数是否分配给了正确步骤？ |
| `random_dependency` | 对邻接关系进行确定性节点重映射，再用原节点特征聚合 | 节点数、各通道边数及图拓扑规模 | 真实边与节点特征的对应是否优于任意对应？ |

这里必须纠正PPT第26—27页的一个术语：当前 `B2_shuffle` 置乱的是**最终图效用在步骤之间的对应**，不是分别在四个通道内部置乱邻接边；`random_dependency` 才是在保持各通道结构规模的情况下破坏边与原步骤的语义对应。因此，现阶段不应笼统写成“通道内置乱”。

### 7.2 当前对照还不能回答什么

当前协议能够检验“组合后的四通道图分支是否有用”，但不能分别证明时间邻接、同角色、同完整结构和同非空动作结构各自都有贡献。若要回答每个通道的独立作用，需要另设四个留一删除条件：

- 删除时间邻接通道，其余三类关系保持不变；
- 删除同角色通道，其余三类关系保持不变；
- 删除同完整结构通道，其余三类关系保持不变；
- 删除同非空动作结构通道，其余三类关系保持不变。

这些才是真正的“通道级消融”。在完成此类实验前，专业口径应是“采用四类可观察关系形成联合跨步表示”，而不是“实验已经证明四个通道分别有效”。

如果完整关系与删除、分数置乱、随机依赖对照表现接近，就不能说方法利用了真实跨步关系；它可能只是从额外特征变换或平滑中获益。

## 8. 为什么需要局部分数与交互分数融合

局部模型和交互模型关注的证据不同：

- 局部分数：当前步骤本身是否异常；
- 交互分数：当前步骤放进整条过程后是否与邻居、角色和调用模式形成可疑关系。

二者可能一致，也可能冲突。例如：

- 某步返回失败，局部上很可疑，但它只是正确发现了前序错误；
- 某步调用成功，局部上正常，但它位于一个连续错误调用链的起点。

因此可构造融合特征，例如：

```text
局部分数
交互分数
二者差值
二者绝对差
二者乘积
交互模型带来的名次提升
是否进入头部候选
```

这些特征送入一个轻量融合器，输出最终分数。

### 融合层为什么必须使用 OOF 预测

若先在全部训练任务上拟合局部模型和交互模型，再用它们对同一批任务产生的训练内分数训练融合器，融合器会看到过于乐观的基模型表现，相当于间接记住训练任务。

折外预测（Out-of-Fold，OOF）的原则是：

> 每个用于训练融合器的基模型分数，都必须由没有见过该任务组的模型产生。

流程如下：

```text
外层训练任务组
  ├─ 划分内层折1……折K
  ├─ 用其余K-1折训练局部/交互排序器
  ├─ 预测当前留出折
  └─ 汇总所有留出折的样本外分数
          ↓
       训练融合器
          ↓
外层测试任务只做一次前向评价
```

OOF 是保证融合结果可信的**信息隔离协议**，不是论文创新点本身。更专业的名称是：

> 基于折外预测的堆叠融合（OOF stacking）。

## 9. RQ1 最终输出和评价指标

### 9.1 输出记录

每个任务至少保存：

- 任务组标识；
- 候选步骤标识；
- 局部分数、交互分数和最终分数；
- 完整排序 `pi_q`；
- 外层折号、模型版本和配置；
- 并列项处理规则。

并列时最好使用与标签和内容无关的确定性键，例如原始 `step_id`。不建议用“匿名摘要”作为并列键，因为摘要内容仍可能携带语义并影响排序结果。

### 9.2 MRR

若 Gold 责任步骤排在第 `r_q` 位，则任务的倒数排名为：

```text
RR_q = 1 / r_q
```

任务组等权 MRR 为：

```text
MRR = 所有任务 RR_q 的平均值
```

例如，Gold 分别排在第 1、2、5 位，则：

```text
MRR = (1 + 1/2 + 1/5) / 3 = 0.567（约值）
```

MRR 越高，表示责任步骤越靠近队列前部，也就越适合有限预算恢复。

### 9.3 Recall@K / Hit@K

若每条轨迹只有一个 Gold，则：

- Recall@1 等价于 Top-1 准确率；
- Recall@3 表示 Gold 是否进入前三名。

论文中第一次出现时应说明“单 Gold 条件下等价于 Hit@K/Top-K accuracy”，避免读者误解召回率的分母。

### 9.4 为什么以任务组为统计单位

同一任务可能有多条近重复轨迹。若把每条轨迹当独立样本：

- 相似样本可能跨越训练与测试；
- 某些任务因轨迹多而主导总体结果；
- 配对统计会错误低估不确定性。

因此同一任务及其近重复轨迹必须只属于一个分区，主指标也应先在任务组内确定，再进行任务组等权汇总。

# 第二部分：RQ2——怎样把排序转化为可靠恢复

## 10. RQ2 的输入不是一个标签，而是一条冻结队列

RQ1 输出 `pi_q` 后立即冻结。RQ2 可以读取：

- 候选标识；
- 候选分数；
- 确定性名次。

但不能根据恢复结果反向修改：

- RQ1 的责任分数；
- 候选池；
- 已规定的排序条件；
- 测试任务上的超参数。

这条“只读接口”非常关键。否则系统可能在看过恢复结果后重新挑选候选，形成后验选择和信息泄漏。

---

## 11. 一个恢复计划到底包含什么

建议把恢复计划写成四元组：

```text
p = (a, S, o, V)
```

其中：

| 符号 | 含义 | 例子 |
|---|---|---|
| `a` | 责任锚点 | 步骤 4 的文件编辑 |
| `S` | 干预范围 | 步骤 4 与步骤 6 的同目标前向关联集合 |
| `o` | 执行操作 | 撤销、补偿、屏蔽状态增量并重放 |
| `V` | 验收函数 | 目标探针 + 非目标约束 + 冲突检查 |

恢复计划不是一句“请重新做一次”，而是一个具有明确执行语义和提交条件的候选事务。

### 哪些步骤可以成为锚点

不是所有轨迹步骤都能直接恢复。当前代码仓库场景中，锚点通常应满足：

- 是成功执行过的状态动作；
- 能观察到或重建其状态差分；
- 目标对象可以稳定标识；
- 该增量能够被撤销、补偿或确定性省略。

纯文本思考、不可复现的外部调用、无法确定状态差分的动作，需要返回弃权或采用其他恢复机制。

---

## 12. 为什么需要三种恢复范围

### 12.1 单点范围

只处理锚点动作本身。

优点：干预最小、成本低。  
问题：若后续动作已经读取或继续修改其错误状态，单点处理可能不够。

### 12.2 等规模前向范围

选择与依赖范围相同数量的后续状态动作，但不保留“同目标对象”这一身份关系。

它不是部署策略，而是一个实验控制，用于回答：

> 方法变好，究竟只是因为处理了更多动作，还是因为处理了真正相关的动作？

### 12.3 同目标、锚点包含的前向关联范围

当前原型以目标键为代理：

```text
S_target(a) = {x_j | key(x_j) = key(a)，并且 j 不早于锚点 a}
```

例如，步骤 4 与步骤 6 都修改 `legacy/config.py`，它们进入同一个范围；步骤 7 修改另一个文件，不进入。

这里不宜称为严格的“依赖闭包”，原因是：

- 它只表示相同目标对象；
- 没有追踪跨文件数据流；
- 没有追踪调用参数由谁生成；
- 没有证明传递因果依赖。

更准确的名称是：

> **目标键驱动的前向关联范围**，或**同目标前向后缀（依赖代理）**。

### 12.4 三种范围怎样分解贡献

| 比较 | 主要改变 | 可以解释的效应 |
|---|---|---|
| 单点 → 等规模范围 | 处理动作数量增多 | 范围扩展效应 |
| 等规模范围 → 同目标范围 | 动作数量近似一致，身份关系改变 | 目标关联身份的增量效应 |
| 固定/置乱顺序 → 预测顺序 | 候选池和范围不变，尝试顺序改变 | 诊断排序的下游效用 |

这比直接比较“单点”与“依赖范围”更严谨，因为后者同时改变了动作数量和动作身份，无法判断收益来自哪一个因素。

---

## 13. 当前恢复操作本质上是什么

当前方案更接近：

> **基于一致检查点的状态增量撤销/屏蔽与轨迹重放**。

它不是通用自动程序修复，也不是让大模型重新生成任意补丁。典型过程是：

1. 创建全新的仓库克隆或一致检查点；
2. 保留原始调用位置和预定重放次序；
3. 对计划范围内的状态增量执行撤销、补偿或屏蔽；
4. 重放其余允许动作；
5. 记录最终状态差分、冲突和执行日志；
6. 运行统一验收器；
7. 通过则提交，不通过则销毁副本。

因此，论文中建议使用：

- 回滚—重放式恢复；
- 状态增量抑制式恢复；
- 可撤销的候选恢复执行。

不宜直接使用：

- 自动生成正确修复；
- 通用自愈；
- 已证明适用于所有 Agent 环境。

### 重放语义需要满足什么假设

“保持调用位置和控制流不变”只有在以下条件之一成立时才可靠：

- 工具执行具有足够确定性；
- 关键工具返回被记录并按协议重放；
- 控制流由固定轨迹驱动，而不是重新让 Agent 自由规划；
- 对不可确定动作有显式中止或弃权规则。

若修改环境状态后重新实时调用工具，后续返回可能变化，控制流也可能分叉。正式论文必须写清楚：当前是**轨迹级确定性重放**、**记录回放**，还是**重新执行 Agent**。

---

## 14. 双边验收：恢复“看起来成功”为什么还不够

### 14.1 目标探针

目标探针检查原始任务是否恢复，例如：

- 指定测试通过；
- 原始断言成立；
- 目标文件状态满足预期；
- 任务成功判定器通过。

### 14.2 非目标无回归约束

当前代码仓库任务可定义一个适配后的安全谓词：

```text
TNR_adapted = NonTargetEqual AND AllowedDiff AND NoNewConflict
```

其中：

- `NonTargetEqual`：非目标状态与规定的参考边界一致；
- `AllowedDiff`：版本差异只包含计划允许的目标变化；
- `NoNewConflict`：没有引入参考执行中不存在的新冲突。

候选成功可以写成：

```text
Success(p) = Accepted(p) AND TargetProbe(p) AND TNR_adapted(p)
```

必须明确：这是一种**受 STRATUS 事务式无回归思想启发、针对代码仓库任务定义的适配条件**，不是 STRATUS 原论文 TNR 公式的直接复现。STRATUS 的原始约束以故障严重度不恶化和可撤销执行为核心，并依赖检查点、忠实撤销和风险窗口等假设。

### 14.3 参考状态必须定义清楚

建议区分三种状态：

| 状态 | 含义 | 测试时是否可用 |
|---|---|---|
| `S_{fault}` | 当前失败任务的一致起始状态 | 可用 |
| `S_p` | 执行候选计划后的状态 | 可用 |
| `S_{ref}` | 评价用参考状态或正确边界 | 可能只在基准评价中可用 |

如果 `NonTargetEqual` 需要一个真实正确参考状态，而部署时拿不到，就必须说明它是**基准评价验证器**而非线上可直接获得的信息。不能一边声称完全部署可用，一边使用隐藏参考状态决定提交。

### 14.4 “不安全尝试”不等于“最终造成损害”

若某个候选触发非目标约束失败，但已经被隔离执行并撤销，那么它是：

- 一个被验证器拒绝的不安全尝试；
- 不是已经提交到最终环境的持续损害。

因此建议区分：

- `UnsafeAttemptRate`：候选执行触发非目标失败或新增冲突的比例；
- `CommittedHarmRate`：最终提交状态仍含非目标损害的比例；
- `TNR Pass Rate`：非目标约束通过率。

当前 PPT 将 `Harm` 同时解释成“TNR 失败”“已验收候选未恢复”和“错误干预风险”，口径不一致，必须在正式稿中只保留一个精确定义。

## 15. 候选顺序、预算和四种排序对照

### 15.1 为什么预算很重要

恢复计划可能需要重新克隆仓库、执行工具和运行测试，不可能无限尝试。设每个任务最多尝试 `B` 个候选：

```text
任务 q 的实际尝试数 |A_q| 不超过预算 B
```

当前先导设置为 `B=2`。因此，把真正可恢复的计划排到前两位，会直接提高任务恢复率并降低平均尝试成本。

### 15.2 四种候选顺序

| 条件 | 次序来源 | 作用 |
|---|---|---|
| Fixed Order | 与诊断无关、预先规定的确定性顺序 | 可复现下界 |
| Shuffled Ranking | 在同一候选池内随机置乱 | 检验有信息排序是否优于随机顺序 |
| Predicted Ranking | RQ1 冻结输出 `pi_q` | 检验诊断排序的下游执行价值 |
| Oracle Ranking | 根据候选池中事后真实成功结果形成最优顺序 | 评价候选池上限，不可部署 |

比较时必须保持：

- 相同任务；
- 相同候选计划池；
- 相同恢复范围规则；
- 相同尝试预算；
- 相同执行器和验收器。

只改变顺序，恢复差异才能归因于诊断先验。

### 15.3 当前计划效用公式应怎样处理

v13 中提出了类似：

```text
U(p) = alpha*R(p) + beta*P_success_estimated(p)
       - gamma*Cost(p) - delta*Risk(p)
```

这个形式在理论上合理，但只有在下列部分已经有真实实现和训练协议时，才能作为“当前方法”：

- 成功概率估计器如何训练；
- 成本与风险如何在测试前计算；
- 权重如何在开发任务上确定；
- 是否使用了测试执行结果。

若当前实验实际上只按照 `pi_q` 和固定范围规则枚举候选，就应把该公式降为“未来扩展的预算效用模型”，主方法写成：

> 在固定候选池与预算下，按照责任锚点名次形成候选顺序。

这比写一个尚未落地的多因素效用函数更专业。

## 16. RQ2 的任务级指标

### 16.1 Recovery Success Rate（RSR）

设任务 `q` 在预算内实际尝试的计划集合为 `A_q`，则：

```text
Recovered(q) = 1，当且仅当 A_q 中至少存在一个成功计划 p；否则为 0
```

任务级恢复率为：

```text
RSR = 所有任务 Recovered(q) 的平均值
```

每个任务只贡献一次统计量，不能把候选尝试当成相互独立的任务样本。

### 16.2 安全与成本指标

建议同时报告：

- TNR 通过率；
- 不安全尝试率；
- 最终提交损害率；
- 平均候选尝试次数；
- 重放时长；
- 工具调用次数和 Token；
- 状态差分规模；
- 回滚次数。

恢复率高但大量候选产生非目标破坏，不能称为“可靠恢复”。反之，所有计划都被拒绝也很安全，却没有恢复价值。因此有效性和安全性必须并列报告。

## 17. 端到端算法的白话版与伪代码

### 白话版

1. 对失败轨迹中的全部候选步骤评分；
2. 得到冻结的完整责任候选排序；
3. 过滤不可执行锚点；
4. 为每个锚点生成单点、等规模和同目标前向范围计划；
5. 在固定预算内按照规定顺序尝试；
6. 每个候选都从新的隔离副本开始；
7. 执行撤销/屏蔽与重放；
8. 运行目标探针和非目标检查；
9. 双边通过就提交并停止；否则销毁副本并继续；
10. 预算耗尽仍无成功计划，则返回恢复失败或弃权。

### 伪代码

```python
def diagnose_and_recover(trace, checkpoint, budget=2):
    # RQ1：只执行一次，输出冻结排序
    ranking = responsibility_ranker.predict(trace)

    # RQ2：候选池由预先规定的规则生成
    plans = build_fixed_plan_pool(
        trace=trace,
        anchors=filter_reversible_anchors(ranking),
        scopes=("singleton", "extent_matched", "same_target_forward")
    )
    ordered_plans = order_plans(plans, ranking)

    attempts = []
    for plan in ordered_plans[:budget]:
        sandbox = clone_from_checkpoint(checkpoint)
        result = execute_rollback_replay(sandbox, trace, plan)
        verdict = validate_bilaterally(result)
        attempts.append((plan, result, verdict))

        if verdict.target_ok and verdict.non_target_ok:
            commit(sandbox)
            return {"recovered": True, "attempts": attempts}

        discard(sandbox)  # 失败候选不污染下一次尝试

    return {"recovered": False, "attempts": attempts}
```

# 第三部分：核心论文到底支持了什么

## 18. 论文地图：不要把“借鉴”写成“论文已经证明了我的方法”

每篇论文可以提供三种不同层级的依据：

1. **问题依据**：说明这一类问题真实存在且值得研究；
2. **方法依据**：某个技术思想可以合理借鉴；
3. **结果依据**：只证明原论文在其数据和条件下有效，不能直接继承到本文。

下面按“论文做了什么—本文借什么—不能继承什么”解释。

---

## 19. SWE-agent：为什么 Agent 失败必须连同环境一起看

**论文**：[SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering（NeurIPS 2024）](https://proceedings.neurips.cc/paper_files/paper/2024/hash/5a7c947568c1b1328ccc5230172e1e7c-Abstract-Conference.html)

### 它研究什么

论文研究智能体—计算机接口怎样影响软件工程 Agent 的行为，使模型能够浏览仓库、编辑文件和运行命令。核心启示是：Agent 的表现不只由语言模型决定，也受工具接口和环境反馈约束。

### 本文借鉴什么

- 把执行轨迹视为“模型决策 + 工具行为 + 环境状态”的联合过程；
- 失败诊断不能只看最后一段自然语言输出；
- 恢复必须真正作用于可执行环境。

### 不能继承什么

SWE-agent 不研究责任排序或事务恢复，不能作为 RQ1/RQ2 方法有效性的直接证据。

## 20. Who&When：责任 Agent 和责任步骤是两个不同任务

**论文**：[Which Agent Causes Task Failures and When?（ICML 2025）](https://proceedings.mlr.press/v267/zhang25cq.html)

### 它研究什么

论文正式定义多智能体失败归因任务：给定失败日志，识别：

- 哪个 Agent 应承担责任；
- 哪一个步骤构成决定性错误。

Who&When 数据集包含 127 个失败系统。论文报告最佳责任 Agent 识别准确率约为 53.5%，决定性错误步骤准确率只有约 14.2%，说明“知道是谁”远不等于“知道何时出错”。

### 本文借鉴什么

- RQ1 的问题定义和 Gold 步骤评价口径；
- 责任主体与责任步骤必须分开；
- 步骤级定位是一个尚未充分解决的难题。

### 本文相对它推进什么

- 不只输出一个 Top-1 步骤，而是输出全部候选的连续排序；
- 进一步用真实恢复实验检验排序是否有下游价值。

### 不能过度声称什么

Who&When 的标签和评价主要服务归因，不能直接证明本文的恢复范围或事务协议正确。

## 21. Scope Delineation：先缩小搜索范围，再定位

## 22. FLKR：开放式代码生成中，行为作用比表面路径更重要

### 它研究什么

## 23. TraceElephant：完整可观测性和动态重放决定归因上限

**论文**：[Seeing the Whole Elephant（ACL 2026）](https://aclanthology.org/2026.acl-long.912/)

### 它研究什么

论文构建带完整执行轨迹和可复现环境的失败归因基准，保留输入上下文、输出、工具和环境证据，并通过动态重放验证决定性步骤。完整轨迹相对部分观测显著提高归因表现。

### 本文借鉴什么

- 定位前必须先定义证据边界；
- 步骤记录应包含实际输入上下文、输出和工具交互；
- 动态重放可以帮助判断某一步是否错过恢复机会；

### 对“责任步骤”的重要修正

TraceElephant 的决定性步骤带有可恢复性含义。若前序步骤出错，而后续验证器本可发现并纠正却没有做到，责任可能落在后续漏检步骤。它不支持“永远找最早错误”这一简单规则。

### 本文与它的区别

本文用结构化排序与恢复接口处理轨迹；若没有实施与 TraceElephant 等价的动态反事实重放，就不能声称采用了相同的责任标签生成机制。

## 24. StepFinder：时序语义可以用轻量模型形成步骤分数

**论文**：[StepFinder: A Temporal Semantic Framework for Failure Attribution in Multi-Agent Systems（KDD 2026）](https://doi.org/10.1145/3770855.3817991)

### 它研究什么

StepFinder 先把日志编码成时序语义序列，再通过时序模型、Agent-aware 注意力、多尺度差异和位置偏置计算步骤错误分数。它避免每次都让大模型对整段日志进行长文本推理，并显著降低推理时间。

### 本文借鉴什么

- 失败步骤必须放进序列演化中判断；
- 角色和时间关系可以形成结构偏置；
- 可以把大模型限制在表示阶段，把排序交给较轻量模型；
- 位置偏置只能是温和先验，不能替代证据。

### 必须纠正的研究缺口表述

StepFinder 已经产生每步分数，并使用 Acc@K 和 MRR@3 评价排序质量。因此不能笼统写：

> 现有研究只有 Top-1，尚未形成步骤排序。

更准确的缺口是：

> 现有工作虽已产生步骤分数或小规模候选排序，但其主要证据仍止于归因指标；尚缺少把冻结的任务级排序作为真实恢复候选次序，并在同候选池、同预算下检验下游效用的系统研究。

### 本文与它的区别

本文使用多通道可观察关系和任务内成对排序，并把完整排序连接到可撤销恢复。是否优于 StepFinder 必须通过统一数据和评价协议复现，不能只凭方法描述推断。

## 25. RankNet：成对排序目标的经典依据

**论文**：[Learning to Rank using Gradient Descent（ICML 2005）](https://www.microsoft.com/en-us/research/publication/learning-to-rank-using-gradient-descent/)

### 它研究什么

RankNet 将排序转化为候选对之间的偏好概率学习。原文先为每个候选计算实值输出 `f(x_i)`，再以输出差 `f(x_i)-f(x_j)` 定义 Logistic 偏好概率，并用交叉熵优化“谁应排在谁前面”。论文还明确要求只比较同一 query 返回集合中的对象；映射到本文，就是只比较同一失败轨迹内的候选步骤。

### 本文借鉴什么

- 任务内候选对，而不是跨任务步骤对；
- 用共享效用之差表示相对偏好；
- 用相对偏好训练完整排序；
- 排序损失与最终候选次序一致。

### 当前实现额外做了什么

RankNet 本身没有规定每个候选对必须同时保存正向行和反向行。本文当前代码复用带截距的通用逻辑回归，因此显式加入 `(d,1)` 与 `(-d,0)`，用数据对称性避免截距吸收全部正类信号。这是实现适配，不应写成原论文的固定步骤。

### DirectRanker 提供的边界说明

**论文**：[Pairwise Learning to Rank by Neural Networks Revisited: Reconstruction, Theoretical Analysis and Practical Performance（2019）](https://arxiv.org/abs/1909.02768)

DirectRanker 使用共享子网络之差、零输出偏置和反对称激活构造排序器，并证明其反射性、反对称性和传递性。论文明确指出，当结构已经保证反对称时，训练时始终把高相关样本放在同一输入侧即可，无需再用交换顺序的样本教模型一次。这说明“是否需要正反样本”取决于模型是否已从结构上保证交换一致性。

### 不能写成什么

成对学习是成熟基础方法，不是本文创新。本文的潜在贡献在于：怎样定义 Agent 轨迹证据、怎样组织跨步关系，以及怎样把排序连接到恢复。

## 28. BacktrackAgent：检测—判断—反思—回退闭环

**论文**：[BacktrackAgent: Enhancing GUI Agent with Error Detection and Backtracking Mechanism（EMNLP 2025）](https://aclanthology.org/2025.emnlp-main.212/)

### 它研究什么

BacktrackAgent 在 GUI 执行中设置：

- Verifier：检查动作是否可执行、是否有效；
- Judger：判断动作是否有助于当前目标；
- Reflector：在异常后产生修正信息并回退。

它把错误检测和后续动作修订组织为闭环。

### 本文借鉴什么

- 诊断证据应进入恢复决策；
- 恢复不是机械重试，而是需要判断回退位置并修订后续动作；
- 目标有效性与执行有效性可以分层检查。

### 本文与它的区别

BacktrackAgent 主要围绕 GUI 当前动作和页面状态回退，不使用本文的任务级完整责任排序，也没有“同目标前向关联范围”的实验分解。

---

## 29. SagaLLM：长流程中的检查点、补偿和独立验证

**论文**：[SagaLLM: Context Management, Validation, and Transaction Guarantees for Multi-Agent LLM Planning（PVLDB 2025）](https://doi.org/10.14778/3750601.3750611)

### 它研究什么

SagaLLM 把长流程多智能体规划组织为具有上下文管理、独立验证和事务保证的执行过程。它借鉴 Saga 事务思想，为已执行步骤定义检查点和补偿操作；失败时按照逆序执行补偿，避免部分完成状态长期残留。

### 本文借鉴什么

- 每个恢复候选应从一致状态开始；
- 状态动作需要明确的补偿或撤销语义；
- 验证应尽量独立于生成计划的主体；
- 失败候选不能污染后续候选。

### 不能过度声称什么

SagaLLM 的事务保证依赖它自身的流程模型、补偿定义和验证假设。本文若只在 fresh clone 中屏蔽 Git 增量，应写“借鉴检查点—补偿—验证思想”，不能直接继承其全部事务保证。

---

## 30. STRATUS：恢复必须满足事务式无回归边界

**论文**：[STRATUS: A Multi-agent System for Autonomous Reliability Engineering of Modern Clouds（NeurIPS 2025）](https://proceedings.neurips.cc/paper_files/paper/2025/hash/47a6e9e2c3019f13ad94a0f259fe4970-Abstract-Conference.html)

### 它研究什么

STRATUS 面向云可靠性工程，把检测、诊断和缓解组织为状态机。缓解动作从检查点执行，若执行后故障严重度不高于执行前并满足事务条件则提交，否则撤销。论文还讨论了写入排他性、忠实 undo 和有限风险窗口等假设。

### 本文借鉴什么

- 生成了恢复动作，不代表恢复成功；
- 目标故障消除和非目标不退化应共同决定提交；
- 每个候选都要有检查点和撤销路径；
- 可靠性需要状态机式的提交/中止边界。

### 必须保持的边界

本文的 `NonTargetEqual ∧ AllowedDiff ∧ NoNewConflict` 是代码仓库任务的自定义适配，不是 STRATUS 原始 TNR 的同一数学定义。专业表述应为：

> 借鉴 STRATUS 的 Transactional No-Regression 思想，针对仓库级状态定义可执行的非目标无回归约束。

---

## 31. SyncMind：强模型并不会自动拥有恢复能力

**论文**：[SyncMind: Measuring Agent Out-of-Sync Recovery in Collaborative Software Engineering（ICML 2025）](https://proceedings.mlr.press/v267/guo25l.html)

### 它研究什么

SyncMind 构造真实代码仓库的环境失同步场景：共享仓库已经变化，Agent 仍按旧状态行动。其大规模实验表明现有 Agent 的恢复率普遍不高，协作和资源感知能力也不足。

### 本文借鉴什么

- 恢复是独立于生成能力的研究问题；
- 环境状态变化会让后续正确推理建立在错误前提上；
- 需要以真实可执行任务，而不是静态文本自评，验证恢复。

### 本文与它的区别

SyncMind 研究 out-of-sync 适应性；本文研究责任排序怎样决定恢复候选次序和范围。二者共享动机，但任务与机制不同。

## 32. Faulty-Agent Resilience：系统结构和复核机制影响韧性

**论文**：[On the Resilience of LLM-Based Multi-Agent Collaboration with Faulty Agents（ICML 2025）](https://proceedings.mlr.press/v267/huang25ay.html)

### 它研究什么

论文向多智能体系统注入笨拙或恶意成员，比较不同协作拓扑，并引入 Challenger 和 Inspector 检查、质疑和纠正消息。结果说明层次结构和显式复核能够显著提高故障韧性。

### 本文借鉴什么

- 错误传播受到协作结构影响；
- 独立检查和纠正机制能够阻断错误；
- 系统级可靠性不能只看单个 Agent 能力。

### 本文边界

它主要修正 Agent 消息，不等于步骤级状态回滚，也不直接证明本文的恢复范围设计。

## 33. AgentDebug / AFTraj：错误分类、轨迹资产和纠正性反馈

**论文**：[Where LLM Agents Fail and How They Can Learn From Failures（arXiv 2025）](https://arxiv.org/abs/2509.25370)

### 它研究什么

该预印本提出 Agent 错误分类、失败轨迹/基准资产和 AgentDebug，通过结构化错误反馈帮助后续执行改进。

### 本文借鉴什么

- 失败轨迹可以组织为步骤级诊断数据；
- 结构化诊断反馈可以进入后续执行；
- AFTraj 类资产可以作为 RQ1 的先导数据来源。

### 必须说明的证据等级

它目前是 arXiv 预印本，不应与 ICML、ACL、KDD 等正式主会论文并列声称为同等级的同行评审证据。数据集命名、版本、许可证和样本筛选必须以实际下载资产为准。

# 第四部分：论文设计的真正增量在哪里

## 34. 哪些是成熟组件，不应单独包装成创新

以下内容是保证实验正确或工程可运行的必要条件，但不是独立学术创新：

- RankNet/成对排序本身；
- 图均值聚合本身；
- OOF、分组交叉验证和 Bootstrap；
- 固定随机种子、JSON、Python 环境；
- fresh clone、Git diff、日志记录；
- checkpoint、commit、rollback 这些通用事务词汇。

## 35. 当前方案可以主张的贡献层级

### 35.1 方法贡献一：局部证据与跨步骤关联联合的任务级责任候选排序

重点不是“首次输出排序”，因为 StepFinder 已经输出步骤分数；更稳妥的增量是：

- 在同一任务内用成对目标学习候选次序；
- 显式分离局部行为和多通道跨步关系；
- 用删除、置乱和随机关系检验关系内容；
- 使用严格 OOF 融合形成可复核完整排序。

### 35.2 方法/实证贡献二：把冻结排序变成恢复候选次序

在相同任务、候选池、范围、预算、执行器和验收器下，只替换 Fixed、Shuffled、Predicted 和 Oracle 顺序，直接检验：

> 排序质量能否转化为实际恢复率和成本收益。

这是连接 RQ1 与 RQ2 的核心桥梁。

### 35.3 实验设计贡献：拆分范围数量效应与关联身份效应

通过：

```text
单点范围 → 等规模前向范围 → 同目标前向范围
```

分别测量：

- 多处理动作本身带来的收益；
- 选择关联动作身份的额外收益。

这可以避免把完整方案的全部提升都归给“依赖语义”。

### 35.4 可靠执行贡献：任务级真实执行与双边验收

恢复候选必须：

- 从一致状态开始；
- 能记录和撤销状态变化；
- 通过目标探针；
- 通过适配的非目标无回归约束；
- 失败时不污染下一候选。

该贡献更适合表述为“受控可执行恢复协议和实证链条”，而不是已经提出通用事务理论。

## 36. 当前先导结果应该怎样理解

### RQ1

当前材料报告完整诊断方法在 716 个任务组上的 MRR 由约 0.3437 提高到约 0.4961，绝对增量约 0.1524，配对置信区间下界大于零。

它支持：

- 关系和融合值得继续研究。

它不自动支持：

- 比 StepFinder、Scope 等已发表强方法更强；
- 已经具备跨任务、跨框架普适性；
- 关系边是真实因果传播边。

### RQ2

当前材料报告预测排序与同目标范围组合恢复 14/34，Oracle 为 16/34；范围消融显示单点约 7/34、等规模范围约 12/34、同目标范围约 14/34。

它最重要的解释是：

- 从 7 到 12 的主要增益首先来自处理更多动作；
- 从 12 到 14 才是当前目标关联身份的点估计增益；

# 第五部分：答辩时最常见的追问

## 37. 为什么不用大模型直接阅读整条轨迹并解释？

大模型直接归因可以作为强基线，但存在长轨迹噪声、推理成本、输出不稳定和难以严格控制信息边界的问题。本文把轨迹转化为可复现的局部字段和跨步关系，再用轻量排序器输出确定性分数，便于做删除、置乱、随机图和 OOF 对照。是否优于大模型归因仍需统一协议实证比较。

## 38. 你的责任排序是不是在找因果根因？

不是严格因果识别。它根据测试阶段可观察证据输出应优先检查/干预的候选次序。跨步骤边是关联代理；RQ2 的真实干预可以验证排序是否具有恢复效用，但不足以把所有责任分数解释为因果效应。

## 39. 为什么不用 Top-1？

恢复存在预算和失败候选。Top-1 不可逆、不可执行或验收失败时，系统还需要知道下一步试谁。完整排序提供连续候选队列，并可用 MRR 与恢复尝试成本共同评价。

## 40. 为什么使用成对排序？

研究目标是同一任务中候选之间的相对优先级；责任步骤稀少、轨迹长度变化大。成对学习直接优化“责任步骤应排在非责任步骤之前”，比独立二分类更贴合输出形式。

## 41. 四类边是怎么选的？

它们来自测试阶段稳定可观察的次序、角色和调用结构，分别表达局部传播、职责连续性和模式复现。选择是否合理不靠直觉宣称，而靠删除、通道置乱和随机图对照验证。正式论文还应报告每类边的单独消融。

## 42. 为什么只传播两轮？

两轮是当前先导配置，用于在不引入深层过平滑和高成本的情况下覆盖一跳与二跳上下文。它不是理论最优值，应由训练/开发任务的内层验证确定，并在外层测试前冻结。

## 43. OOF 为什么这么复杂？

因为融合器不能用同一任务上的训练内基模型分数，否则会学习到过于乐观的训练表现。OOF 保证每个融合训练样本的局部/交互分数来自没有见过该任务组的模型，外层测试才是一次性评价。

## 44. 你的恢复到底“修了”什么？

当前不是生成新补丁，而是围绕可疑状态动作撤销、屏蔽或补偿增量，并从一致检查点重放其余过程。它回答的是“移除哪些可疑状态后，任务能否恢复”，属于回滚—重放式任务恢复。

## 45. 为什么同一个文件的后续编辑就算依赖？

当前只把它视为一个低成本、可执行的依赖代理：后续编辑作用于同一状态对象，可能继承此前内容。它不等于完整数据流依赖。正式稿应使用“同目标前向关联范围”，并通过等规模控制验证目标身份是否真的提供增量。

## 46. TNR 是你提出的吗？

不是。本文借鉴 STRATUS 的事务式无回归思想，再为代码仓库任务定义 `NonTargetEqual`、允许差分和无新增冲突等可执行约束。需要清楚区分原论文定义和本文适配实现。

## 47. Oracle 有什么用？

Oracle 使用候选池内事后真实结果，把成功计划优先排列，代表当前候选池和预算可达到的评价上界。它不能部署，只用于判断问题在“排序不够好”还是“候选池根本没有可恢复计划”。

## 48. 14/34 是否已经证明方法可靠？

只能证明当前小规模受控资产上流程可运行并存在正向信号。正式结论还需要：强基线复现、扩大任务规模、自然失败外测、分层结果、严格安全指标和任务级配对区间。

## 49. 为什么诊断结果不能根据恢复结果更新？

因为当前研究要识别“冻结诊断排序本身是否具有下游价值”。若恢复结果再回写排名，就变成在线自适应策略，RQ1 与 RQ2 的效应无法分离，也可能利用测试结果后验选优。

## 50. 这项工作适用于 GUI、数据库和云系统吗？

研究问题具有跨环境意义，但当前执行证据主要来自代码仓库。不同环境需要重新定义状态键、补偿操作、检查点和非目标约束。正式结论应写“提供可扩展接口”，而不是直接声称已验证跨环境通用性。

# 第六部分：推荐的自学顺序

## 51. 第一阶段：先看懂问题，不看公式

1. Who&When：为什么“谁出错”和“哪一步出错”不同；
2. TraceElephant：为什么证据边界和动态重放重要；
3. ReAgent / BacktrackAgent：为什么失败后需要回退而不是继续向前；
4. STRATUS：为什么修复动作必须经过事务式验收。

完成后应能口头回答：

> 失败暴露点与责任候选位置为什么可能错位？为什么只做定位不够？

## 52. 第二阶段：看懂 RQ1

1. RankNet：成对排序；
2. StepFinder：时序语义和步骤分数；
3. Scope Delineation：候选范围；
4. FLKR：行为语义和上下文一致性；
5. 回到自己的局部字段、四通道关系和 OOF 融合。

完成后应能在纸上写出：

```text
轨迹 → 局部向量 → 图关系消息 → 两个排序分数 → OOF融合 → πq
```

并解释每一步解决什么问题。

## 53. 第三阶段：看懂 RQ2

1. ReAgent：局部/全局回滚；
2. BacktrackAgent：检测—判断—反思—回退；
3. SagaLLM：检查点、补偿、独立验证；
4. STRATUS：提交/撤销和无回归；
5. 回到自己的计划四元组、三类范围和双边验收。

完成后应能在纸上写出：

```text
πq → 锚点 → 三类范围 → 隔离重放 → Target/TNR → Commit/Abort
```

## 54. 第四阶段：只看实验归因

依次问四个问题：

1. 完整排序比公平局部基线好吗？
2. 正确关系比置乱/随机关系好吗？
3. Predicted 顺序在相同候选池中比 Fixed/Shuffled 好吗？
4. 同目标范围比等规模范围好多少？

只有这四个问题分别回答清楚，才能避免把完整系统总增益错误归给某一个模块。

# 第七部分：一页速记

## 55. 核心符号

| 符号 | 含义 |
|---|---|
| `T_q` | 任务 `q` 的失败轨迹 |
| `x_i` | 第 `i` 个候选步骤 |
| `s_i` | 责任候选优先级分数 |
| `pi_q` | 覆盖全部候选的确定性排序 |
| `a` | 恢复锚点 |
| `S` | 恢复干预范围 |
| `p=(a,S,o,V)` | 恢复计划 |
| `B` | 每任务最大候选尝试数 |
| TargetProbe | 原始任务是否恢复 |
| TNR | 非目标无回归约束/其适配版本 |
| RSR | 任务级恢复成功率 |

## 56. 两个研究问题的最简答法

**RQ1：** 给定失败轨迹，联合单步可观察行为与跨步骤关联，学习全部步骤的责任候选优先级排序；用任务组等权 MRR、Recall@K 和结构负对照评价。

**RQ2：** 将冻结排序作为恢复候选次序，在固定候选池与预算内比较单点、等规模和同目标前向范围；每个候选从一致检查点隔离执行，并以目标恢复和非目标无回归共同决定提交或撤销。

## 57. 最应该避免的五句话

1. “我们找到了真实因果根因。”
2. “现有方法都只输出 Top-1。”
3. “同文件后续动作就是严格依赖闭包。”
4. “本文直接采用了 STRATUS 的 TNR 公式。”
5. “14/34 已经证明方法在各种 Agent 场景下可靠。”

## 58. 推荐的五句话

1. “本文输出基于可观察证据的责任候选优先级，而非未经识别的真实因果效应。”
2. “已有工作已产生步骤分数或 Top-k 排序，本文进一步检验完整排序作为恢复接口的下游效用。”
3. “当前同目标前向范围是可执行的依赖代理，并通过等规模控制分离数量效应与身份效应。”
4. “本文借鉴事务式无回归思想，并针对代码仓库定义可执行的双边验收条件。”
5. “当前结果属于先导可行性证据，正式结论仍依赖强基线、自然失败外测和统一安全口径。”

# 附录 A：其余引用论文在当前设计中的位置

下面这些论文不是当前 RQ1/RQ2 的最直接方法锚点，但它们分别支持研究版图、执行环境、可追踪性、依赖切片、多粒度干预和未来在线化。若在 PPT 中引用，必须把“辅助依据”和“核心方法依据”区分开。

## A.1 轨迹分析综述：用于搭建研究版图

**论文**：[A Survey for LLM Agent Trajectory Analysis: From Failure Attribution to Enhancement（IEEE TSE 2026）](https://www.computer.org/csdl/journal/ts/5555/01/11626967/2iuF5rxPMqs)

### 它研究什么

该综述系统整理 LLM Agent 轨迹分析，覆盖失败分类、失败归因、系统增强、监控工具和数据基准等方向。它的作用是说明“轨迹已经成为理解、诊断和改进 Agent 的统一研究对象”。

### 本文怎样使用

- 用于第一章研究版图和术语分类；
- 说明失败分析已经从最终结果评价扩展到过程级轨迹分析；
- 帮助区分 attribution、monitoring、repair、enhancement。

### 不能怎样使用

综述不直接证明本文四类关系、排序器或恢复协议有效，也不能替代对原始方法论文的引用。

## A.2 APR Agent Traceability：用于说明“完整决策过程值得被追踪”

**论文**：[Understanding Automated Program Repair Agents Through the Lens of Traceability（ISSTA 2026 Research Paper，已接收/待会议召开）](https://conf.researchr.org/details/issta-2026/issta-2026-research-papers/194/Understanding-Automated-Program-Repair-Agents-Through-the-Lens-of-Traceability-An-Em)

### 它研究什么

该工作系统追踪 5 个自动程序修复 Agent 在 500 个真实修复任务中的完整决策流水线，从问题描述、仓库探索一直到补丁验证，分析它们怎样行动、在哪里失败以及与人类开发过程有何差异。

### 本文怎样使用

- 支持“不能只看最终补丁，必须观察完整工具与决策轨迹”；
- 支持在软件工程 Agent 中记录动作、状态和验证过程；
- 可作为错误案例分类和外部效度讨论的材料。

### 不能怎样使用

它是经验性可追踪研究，不是本文责任排序或可撤销恢复的直接算法来源。会议时间晚于当前开题日期，引用时应标为“已接收/即将发表”。

## A.3 CausalRepair：用于说明当前同目标代理未来应升级为真实切片

**论文**：[CausalRepair: Bridging the Causality Gap in LLM-based Automated Program Repair via Dual-Slicing（ISSTA 2026 Research Paper，已接收/待会议召开）](https://conf.researchr.org/details/issta-2026/issta-2026-research-papers/134/CausalRepair-Bridging-the-Causality-Gap-in-Large-Language-Model-based-Automated-Prog)

### 它研究什么

CausalRepair 在测试侧使用上下文感知静态切片净化测试语义，在源码侧使用基于执行轨迹的动态切片捕获运行时依赖，构造与缺陷更相关的上下文，并用于迭代补丁生成。

### 本文怎样使用

- 说明真正的依赖范围可以由静态/动态切片构造；
- 作为当前“同目标前向关联范围”的未来升级方向；
- 支持在局限性中明确：文件键相同远弱于运行时数据流依赖。

### 不能怎样使用

本文当前没有实现双切片，不能以 CausalRepair 为依据把“同文件后缀”直接称为因果依赖闭包；CausalRepair 研究的是补丁上下文和生成，不是本文候选级回滚—重放。

## A.4 Multi-granularity Patch Generation：用于说明干预粒度不能一刀切

**论文**：[One Size Does Not Fit All: Multi-granularity Patch Generation for Better Automated Program Repair（ISSTA 2024 Distinguished Paper）](https://2024.issta.org/details/issta-2024-papers/124/One-Size-Does-Not-Fit-All-Multi-granularity-Patch-Generation-for-Better-Automated-Pr)

### 它研究什么

该工作针对真实缺陷所需修改粒度不同的问题，从多种粒度生成候选补丁，再通过启发式重排序优先选择补丁。核心结论是：单一修复粒度无法覆盖不同缺陷。

### 本文怎样使用

- 支持“恢复范围应当具有多粒度候选”这一一般动机；
- 帮助解释为什么不能只做单点回退或全局重启；
- 可作为单点、局部范围和更大范围的邻近 APR 依据。

### 不能怎样使用

原论文的粒度是补丁生成粒度，本文的粒度是状态动作干预范围。二者只是问题结构相似，不能写成相同方法。

## A.5 AgentForesight：用于区分事后归因和在线审计

**论文**：[AgentForesight: Online Auditing for Early Failure Prediction in Multi-Agent Systems（arXiv 2026）](https://arxiv.org/abs/2605.08715)

### 它研究什么

AgentForesight 把轨迹结束后的事后归因改写成在线审计：审计器在每一步只能观察当前前缀，决定继续运行还是尽早报警，不允许读取未来步骤。论文还构建 AFTraj-2K，并训练面向 what/where/who 的在线审计模型。

### 本文怎样使用

- 说明当前 RQ1 属于事后诊断，而不是在线预测；
- 作为未来研究方向：在错误传播尚未完成时触发恢复；
- 帮助界定离线全轨迹方法不能直接声称部署期提前干预。

### 不能怎样使用

它是预印本，且输入只有轨迹前缀、目标是在线报警，与本文读取完整失败轨迹的排序任务不同。不能把其在线性能当作本文方法基线结果。

## A.6 SWE-bench：用于说明可执行仓库任务为什么合适

**论文**：[SWE-bench: Can Language Models Resolve Real-World GitHub Issues?（ICLR 2024）](https://openreview.net/forum?id=VTF8yNQM66)

### 它研究什么

SWE-bench 从真实 GitHub issue 与对应 pull request 构造 2,294 个软件工程任务，覆盖 12 个 Python 仓库。模型需要读取代码库并修改代码，使测试验证通过；任务通常需要跨函数、类和文件的长上下文推理。

### 本文怎样使用

- 支持仓库级 Agent 任务具有真实环境状态和可执行验收；
- 支持使用测试作为目标探针；
- 说明跨文件和长上下文依赖是恢复中的真实挑战。

### 不能怎样使用

SWE-bench 本身不提供责任步骤标签、恢复计划或无回归事务定义。若本文恢复任务不是直接来自 SWE-bench，也不能把其规模写成自己的数据规模。

## A.7 AgentRx：用于说明“约束—证据—定位日志”的另一条路线

**论文**：[AgentRx: Diagnosing AI Agent Failures from Execution Trajectories（arXiv 2026）](https://arxiv.org/abs/2602.02475)

### 它研究什么

AgentRx 发布 115 条跨结构化 API 工作流、事故管理和开放式 Web/文件任务的失败轨迹，并标注关键失败步骤和跨领域错误类别。其诊断器从领域策略与工具模式中合成约束，逐步检查轨迹，形成带证据的约束违规日志，再由 LLM judge 定位关键步骤与类别。

### 本文怎样使用

- 支持可审计诊断不应只输出一个无证据标签；
- 说明工具 schema、领域策略和逐步约束可以成为局部责任证据；
- 可作为未来强基线或外部数据源，尤其适合检验结构特征是否能跨领域迁移。

### 不能怎样使用

AgentRx 当前是预印本；它使用约束合成和 LLM judge，与本文匿名结构字段、图聚合和成对排序不同。不能只凭任务名称声称本文已经实现同等跨领域诊断。

# 附录 B：旧稿中的路由论文为什么不再属于当前 RQ2 主证据

旧稿引用 Confidence Tokens、Smoothie、Unified Routing and Cascading、AutoMix、RouteLLM、BEST-Route 等工作，用于支持“估计样本级相对质量后选择模型/策略”。这些论文对旧方案中的归因器路由是合理的方法依据，但当前 RQ2 已转为真实恢复，因此它们的地位应调整为：

| 旧稿论文族 | 可以保留的启示 | 当前不能支持的结论 |
|---|---|---|
| 置信度路由/选择性预测 | 预测可靠性后选择、升级或拒识 | 不能证明 Agent 状态能够回滚或恢复 |
| 样本级模型质量估计 | 不同样本适合不同候选方法 | 不能证明责任排序能改善真实 RSR |
| Routing/Cascading | 固定资源预算下的候选选择形式 | 不能替代检查点、补偿和双边验收 |

因此，当前主线不需要把这些论文放进核心方法页。它们可以保留在：

1. 方案演进附录；
2. 未来“预算感知计划选择器”的相关工作；
3. 若重新引入成功概率/风险估计时的方法论依据。
