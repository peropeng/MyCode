# 责任排序与恢复选择：本轮可行性结论

日期：2026-09-22。本轮按交接13完成 Exp123、Exp124 的可执行分支、配套来源审计和六例原任务测试接入。**当前两项新增贡献主张均未通过预定门：原责任排序明显弱于新增 StepFinder 强基线；责任第一名保护与恢复重排的组合没有同时优于两个组件。** 原有 Exp112C 相对旧基线的提升仍成立，但不能继续用它代替新增强比较。没有为了取得 GO 改模型、筛选成功任务或解封历史 confirmation。

## 1. 给导师的直接回答

| 本轮问题 | 观测与裁决 |
|---|---|
| 原责任排序是否仍优于强基线？ | 否。任务组等权 full MRR：A+B **0.496057**，StepFinder 同数据适配 **0.845827**；差值95% CI完全低于0。 |
| 恢复组合是否同时优于直接责任顺序与纯恢复顺序？ | 未成立。三次预算下组合22/34，纯恢复23/34；训练侧风险约束下组合8/34，直接责任顺序11/34。 |
| 组合是否在风险不增时保持双重增量？ | 否。相对责任顺序的风险门通过，但恢复没有提高；相对全弃权的纯恢复虽有恢复增量，held不安全尝试也显著更多。 |
| 第三次尝试是否值得？ | 组合从18/34增至22/34，新增不安全任务为0，属于固定顺序的局部正信号；不能据此绕过训练风险门，或声称组合优于纯恢复。 |
| 是否拿到了新的外部迁移证据？ | 没有。TraceElephant发布的220条轨迹全部有历史用途，未见合格任务为0；Who&When生成式基线缺可用模型，未完成。 |
| 原任务测试能否接入？ | 固定六例全部成功接入，7个目标测试复现失败后由官方参考补丁转为通过，460个保留测试前后通过；这不是恢复算法修复了六个Issue。 |

因此，现阶段适合保留责任排序的历史结果、恢复排序的内部机制证据与可复用执行资产，**收缩“组合具有独立贡献”的表述**。不能把本轮写成两项创新都已验证，也不能把外部资产不足混称算法失败。

## 2. 恢复选择：增量来自哪里，风险限制后还剩多少

Exp123沿用34个历史任务、8个仓库、每任务8个同目标键前向切片。单点候选成功标签训练固定恢复后验，切片结果用于恢复评价和训练侧深度校准；没有换成切片标签训练新方法。M1只执行责任第一名，M2沿责任顺序，M3按纯恢复后验，M4保护责任第一名后按同一后验排列剩余候选。

原后验本来不含责任分数或责任名次。因此，**M3与M4实际只差责任第一名保护**，不是两个分数模型的新融合。验收是目标Python文件能否编译及非目标状态约束，不能等同于原Issue修复。

同预算指上限相同，不是实际消耗相同。M1始终只有一次。三次预算下，组合相对M2提高23.53个百分点，但不安全尝试也提高14.71个百分点；相对M3恢复少2.94个百分点且平均尝试更多，没有显示第一名保护的独立收益。

风险深度通过outer-train内部按仓库OOF校准，以训练任务M2@2风险为参照，从0至3选深度，冻结后才评价held仓库。实际M3所有折选0，M4所有折选1，后者退化为M1。**M3的0成功来自校准后全弃权，不是它没有恢复能力。** 训练侧约束也不保证held风险相同。

| 训练侧风险约束下比较 | 恢复率差与95% CI（百分点） | 不安全任务率差与95% CI（百分点） |
|---|---:|---:|
| M4−M2 | −8.82［−17.65，0.00］ | −8.82［−20.59，0.00］ |
| M4−M3 | +23.53［+11.76，+38.24］ | +17.65［+5.88，+29.49］ |

M4相对较强恢复基线M2为−27.27%，未达到≥10%；对两个组件的恢复差CI下界同时大于0、三种子均优于两者等门均未通过。M3基线为0时，相对提升不定义，只报告绝对差。相对M2的不增险统计门通过，不能弥补恢复增量缺失；相对M3的更多恢复伴随更多风险，不能称同等风险下优于M3。

CI以34个任务为独立单位，先在每任务内平均三个种子，再做5,000次配对bootstrap。逐一去掉八个仓库时，M4−M2的恢复差仍均为负（−6.25至−10.34个百分点）；这是方向敏感性检查，不是八仓库足以支持广泛迁移的证明。全部故障均是受控语法故障，不补造自然失败类别。

第三次尝试的边际结果：M2增加3个恢复、2个不安全任务；M3增加2个恢复、0个不安全任务；M4增加4个恢复、0个不安全任务。相应恢复增量CI分别为［0，20.59］、［0，14.71］、［2.94，23.53］个百分点。M4第三次有局部正收益，但其前三次累计风险仍是14/34，训练校准没有允许这条前缀部署；不能只看第三次的边际风险为0就跳过整条前缀的风险。

安全候选池上界为23/34，11个任务没有任何验收通过的切片。M3@3已达到这一恢复上界，在当前池内组合无法以恢复数超过它。风险面板较强基线为11个，要达≥10%需至少13个；23个的数量上界允许达到该门，故不能用“上界不够”解释本轮风险约束组合失败。该数量预检本身不保证风险约束可满足。

### 完整性与明确缺项

本轮新执行579个物理单元：272个单点训练、272个切片评价、34个故障参照和1个重复哨兵；对应816个切片逻辑槽、24个冻结决策及4,080条策略记录。正式192次模型拟合，独立再拟合192次，held顺序、inner-OOF顺序及选定深度全部重现。接受状态的实际文件已保存为内容寻址快照并重新验证；检查覆盖18,159个blob，ZIP约87.23MB，不能仅靠执行器“承诺撤销”填零损害。主driver约2,031.95秒，分项回放时间不含全部模型和复核开销。

**日志合同仍有缺项：逐候选原始stdout/stderr未保存。** 结构化执行、验收、状态字节、摘要和全局日志齐备，状态/提交/泄漏独立审计通过；缺失的原始流不能重建。最终状态为`COMPLETE_WITH_OBSERVABILITY_GAP`，综合严格GO不通过。科学联合门本身也未通过；本轮不是仅因日志格式问题错失GO。详见[Exp123报告](../实验/实验123_责任排序与恢复选择风险补充/README.md)和[独立终态审计](../实验/实验123_责任排序与恢复选择风险补充/results/independent_final_audit.json)。

## 3. 责任排序：新增强比较改变了贡献判断

Exp124在相同731条记录、716个任务组、7,366个候选步骤上实际运行StepFinder同数据适配，复用Exp112C合法冻结预测比较。开发记录包括math278、coding165、agentic288；496条为注入式故障，235条为诊断式标签，不能统称自然发生失败的真实因果Gold。

StepFinder直接采用冻结官方结构及真实Qwen3-Embedding-0.6B。输入是相同可见轨迹内容、动作、thought与匿名角色；Gold、任务ID、题目和标注解释不进入表示。按原三种子五折任务组划分，在outer-train内选epoch，再完整outer-train重拟合，15个checkpoint均在held评价前保存。不使用作者额外生成训练集，因此名称是“同数据适配”，不是原论文复现。

| 方法 | 任务组等权full MRR |
|---|---:|
| StepFinder同数据适配 | **0.845827** |
| A+B（原责任排序） | 0.496057 |
| pairwise_B | 0.343700 |
| recency | 0.330520 |
| local | 0.314238 |

A+B−StepFinder为−0.349770，95%任务组配对CI［−0.377511，−0.321637］；A+B三个种子均较低。716个任务组中，A+B更好89组、更差505组、相同122组。StepFinder R@1=0.760591、R@3=0.924232；full MRR不与MRR@3混称。

A+B相对pairwise_B仍有44.33%的历史内部提升，但新增最强合法比较器已是StepFinder。因此当前原方法的强基线增量未成立，而且差距有明确方向。事后描述性分层中，诊断式标签子集也是A+B 0.434581、StepFinder 0.671129；该检查没有追加训练或改变主门，不把整体差距简单归因为注入子集，也不据此作新的因果解释。

15折选epoch、重拟合与held评价合计878.63秒，批量嵌入122.77秒；正式与独立审计通过。主线程从全部折外分数/顺序独立重算MRR，结果一致。15个实际模型、731条嵌入及所有逐候选预测已归档，合入后通过逐文件摘要核验。[Exp124报告与复核入口](../实验/实验124_责任排序强基线与外部迁移/README.md)

## 4. 两项研究之间是否已经真正接通

现有链路为Exp113部署流程（已修正的Exp112 helper）→Exp113J封存八锚点顺序→Exp122→Exp123，**不是直接使用Exp112C最终outer-held全turn排序输出**。八锚点输入为匿名动作形状，也不是完整自然语言轨迹。历史整文件Git对象及fitted权重缺失，当前可核对封存顺序SHA、tie函数与实际源码链；不能宣称缺失对象已核验。

272个锚点全部映射到原SFT消息、函数调用和可执行切片，覆盖八候选池100%，但只覆盖所选轨迹789次调用的34.47%。这是身份映射和状态关系代理，不是真实跨文件因果闭包。开发任务与34个恢复任务的ID及规范化题文规则检查未命中，仍不能据此把已反复使用的34任务变成新外测。

配套原任务测试门按公开元数据顺序固定六例，全部来自moto；Windows原生pytest验证7个FAIL_TO_PASS节点从失败到通过、460个PASS_TO_PASS节点前后通过。数量按任务计，跨任务可能复用节点，不是467个独立样本。成功修复来自公开官方参考补丁。依赖错误与5个截断参数化节点的唯一匹配适配均保留原始失败记录；没有换任务或删测试。本机官方Linux/container环境不可用，故结论是六例原测试可接入，不是官方容器评测通过，更不是Exp123已修复原Issue。[完整来源与六例报告](20260922_可行性配套审计/README.md)

## 5. 下一步最小缺口与保留资产

本轮不再追加模型追求正结果。下一轮若继续原方向，应先解决能改变结论的缺口：

1. **RQ1先明确新增贡献。** 当前结构排序不能以“优于StepFinder”为已证成果；任何结合语义表示的新方法需另立协议和对照，不能补写成本轮已有结果。
2. **RQ2先判断是否需要组合。** 当前纯恢复在三次预算达到候选池恢复上界，第一名保护未带来独立收益。可保留更简单基线；若研究风险选择，应针对首候选风险与全弃权现象提出新问题，不能临时加模型覆盖本轮失败。
3. **确认外部资产与原任务验收。** 需要真正未参与开发、步骤标签适配的独立排序任务；真实恢复还需独立任务、可执行修复候选及原测试验收。六例接入门提供技术入口，不替代新外部协议。

权威代码、协议、结果已进入`main/实验/`。公开模型、Python环境、原始快照及大数据仍保留在对应执行工作区，避免在复现资产迁移完成前删除。旧实验、PPT和用户原有未提交资料保持不变。新实验均无新增付费资源。
