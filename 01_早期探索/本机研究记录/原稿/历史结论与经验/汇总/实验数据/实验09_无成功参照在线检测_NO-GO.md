### 动作状态在线检测实验结果

#### 1. 结论先行

本实验是一次真实的 **NO-GO**。在 1,200 条 OpenHands 运行上，完整方法“动作后果 + 变化点/持续性 + 独立成功任务组阈值校准”没有超过最强的当前-only Fail-Fast 风格基线，反而使失败报警召回从 28.04% 降到 16.82%。失败运行配对 Bootstrap 95% 置信区间和失败任务组配对 Bootstrap 95% 置信区间的下界都小于 0，因此不能把这两个在线模块作为第一章的有效改进结论。

这不是第二章责任动作定位的证据，也不能支持把当前题目直接写成已经完成“责任动作定位”。成功参照方法仍然只作为历史强基线：它的召回为 42.06%，但不属于本方法，也不能掩盖本方法相对当前-only 基线的失败。

#### 2. 数据、输入边界和真实运行核验

| 项目 | 数量 |
|---|---:|
| 成功运行 | 1,093 |
| 失败运行 | 107 |
| 任务组 | 281 |
| 含失败任务组 | 82 |
| 去重前匹配运行 | 1,216 |
| 去重后运行 | 1,200 |

五折按规范化任务描述分组，同一任务的运行不会跨测试折。每个训练折再按独立哈希抽出成功任务组校准阈值；测试折没有参与阈值选择。成功误停预算固定为 10%，报警只在 20%、40%、60%、80% 前缀检查。

原始日志把第 `i` 个动作的工具回传文本放在第 `i+1` 个动作所带的用户消息中。脚本因此在长度为 `k` 的前缀只使用 `actions[1:k]` 的回传文本；最后一个动作的未来回传没有被补入。这避免了使用当前动作之后尚未到达的结果。`resolved`、最终评审、接受补丁和同任务成功轨迹没有进入新方法特征。

正式运行退出码为 0，标准错误为空；输出文件为本目录的 `results.json`。旧基线结果从已提交的早期预警结果读取，并核验了四项数据基数（1,200 条运行、107 条失败、1,093 条成功、281 个任务组）一致；新方法的特征和五折拟合由本目录脚本重新计算。

#### 3. 主指标

| 方法 | 失败报警召回 | 成功误停率 | 失败平均节省步骤 |
|---|---:|---:|---:|
| 步数 | 18.69% | 11.71% | 8.04% |
| 当前结构 | 16.82% | 11.25% | 7.85% |
| Fail-Fast 风格当前-only 基线 | **28.04%** | **6.86%** | **18.50%** |
| 同任务成功参照（历史强基线） | 42.06% | 8.87% | 24.67% |
| **动作状态在线检测（完整方法）** | **16.82%** | **8.60%** | **10.47%** |

相对最强当前-only 基线，完整方法的失败召回相对变化为 **−40.00%**，而不是预注册的至少 +10%。失败轨迹配对 Bootstrap 的召回差为 −11.21 个百分点，95% 置信区间为 **[−20.56, −1.87] 个百分点**；按失败任务组配对的差为 −10.16 个百分点，95% 置信区间为 **[−20.12, −0.41] 个百分点**。两个下界都小于 0。

完整方法满足成功误停率不超过 10% 和平均节省步骤不低于 10% 两项单独条件，但这不能抵消召回下降。因此机器判定为：

```text
NO-GO
```

#### 4. 消融结果

| 方法 | 失败报警召回 | 成功误停率 | 失败平均节省步骤 |
|---|---:|---:|---:|
| 完整方法 | 16.82% | 8.60% | 10.47% |
| 去掉动作后果模块 | 13.08% | 7.14% | 8.79% |
| 去掉变化点与持续性模块 | 16.82% | 9.52% | 10.28% |
| 去掉独立成功组校准（固定分数阈值 0） | 100.00% | 100.00% | 80.00% |

去掉动作后果后召回继续下降，说明这组特征在当前训练器中不是完全无效；但完整方法仍比 Fail-Fast 基线低 40%，所以不能把“消融下降”误写成有效方法贡献。去掉变化点后召回与完整方法相同，只改变误停和节省步骤，当前数据不足以证明变化点模块带来独立的检测增益。固定阈值导致成功误停率 100%，说明校准步骤是必要的运行协议，但它没有解决完整方法召回不足的问题。

#### 5. 预注册门槛逐项核对

| 门槛 | 观测 | 是否通过 |
|---|---:|---|
| 成功误停率 ≤ 10% | 8.60% | 是 |
| 相对 Fail-Fast 失败召回提升 ≥ 10% | −40.00% | 否 |
| 失败轨迹配对 Bootstrap 下界 > 0 | −20.56pp | 否 |
| 失败任务组配对 Bootstrap 下界 > 0 | −20.12pp | 否 |
| 失败平均节省步骤 ≥ 10% | 10.47% | 是 |

因此不调权重、不放宽误停预算、不更换数据子集，也不把成功参照的 42.06% 当作本方法成绩。

#### 6. 对第一章和总题目的影响

这次实验否定的是一个具体假设：仅把当前日志中的动作后果显式化，再加入固定窗口的变化点和持续性，在当前 OpenHands 记录上并不能稳定改善 Fail-Fast 风格的运行故障检测。它没有否定“运行故障检测”这个研究问题本身，但表明当前这组三模块还不够形成第一章的小论文成果。

在第二章已经只有文件级修复相关性、真实单补丁重放规模很小的前提下，本次 NO-GO 进一步说明不能用该结果补足“责任动作定位”的证据链。后续若继续研究，必须另行取得独立的动作级责任验证（例如可恢复状态、动作替换或撤销后的结果翻转），并先找到能够稳定超过当前-only 基线的第一章检测信号；在此之前不应包装成已经具备完整题目资格。
