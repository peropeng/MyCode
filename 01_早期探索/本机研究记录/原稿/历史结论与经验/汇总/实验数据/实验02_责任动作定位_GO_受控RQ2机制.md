### 检查点责任动作定位实验结果

#### 1. 结论

**GO，但只是受控动作责任定位机制的 GO。**

在 34 个不同软件任务、8 个公开仓库上，实验从相同的窗口起点恢复仓库，重放不同长度的动作前缀，并使用 Python 编译结果定位首个状态转坏动作。所有预先冻结的 GO 条件均通过。

白话结论是：

> 如果我们已知 Agent 是在某 8 个动作之间把代码从“可编译”变成“不可编译”，那么每次从同一起点重放、用 3 次二分检查，可以比同样用 3 次的固定均匀检查更准地找到责任动作；只撤销这个动作带来的故障增量后，代码能恢复，而撤销后面的同文件编辑不能恢复。

#### 3. 定位结果

| 方法 | Top-1 | MRR | 平均绝对步距误差 | 平均定位探针 |
|---|---:|---:|---:|---:|
| 同检查点二分重放 | **100.00%** | **1.0000** | **0.0000** | 3.00 |
| 同预算均匀检查 | 47.06% | 0.7353 | 0.5294 | 3.00 |
| 窗口最后动作 | 0.00% | 0.2387 | 3.9412 | 无额外探针 |
| 固定随机 | 17.65% | 0.4185 | 2.0000 | 无额外探针 |
| 最近报错文件编辑 | 0.00% | 0.2746 | 2.8235 | 无额外探针 |
| 逐动作完整检查上界 | 100.00% | 1.0000 | 0.0000 | 8.00 |
| 逐动作早停上界 | 100.00% | 1.0000 | 0.0000 | 4.06 |

与最强的同等成本基线“均匀检查”相比：

- Top-1 绝对提升：52.94 个百分点。
- Top-1 相对提升：112.50%。
- 任务级配对 Bootstrap 95% 置信区间：**+35.29 至 +70.59 个百分点**。

对逐动作上界必须使用更克制的表述：

- 与 8 次完整检查相比，准确率相同，但二分重放只用 37.5% 的定位探针。
- 与“每个动作后检查、首次失败就停止”的在线上界相比，准确率相同，定位探针平均为 3.00 对 4.06，约减少 26.1%。但后者能更早阻止故障继续传播，因此仍是 RQ1 的强基线，不能用 RQ2 的准确率替代这一优势。

#### 4. 干预结果

- 无故障窗口末态编译通过：34/34。
- 受控故障窗口末态编译失败：34/34。
- 只移除已定位故障增量后恢复编译：34/34。
- 恢复后文件与干净末态字节完全一致：34/34。
- 撤销后续“最近同文件编辑”后恢复编译：0/34。

因此：

- 责任干预闭环率：100%。
- 负对照恢复率：0%。
- 干预绝对提升：100 个百分点。

这比“定位到了同一个文件”更强：在每个窗口中，责任动作之后还有至少一次对同文件的编辑，负对照撤销的就是这个更晚动作，但它不能消除较早责任动作造成的语法故障。

#### 6. 不能从这个 GO 推出什么

1. **不能推出已经解决自然 Agent 失败。** 本实验故障是人工施加的未闭合分隔符，不包含误解需求、错误工具参数、跨文件状态错误或延迟失败。
2. **不能推出在线故障检测已经 GO。** RQ1 在这里只提供一个稀疏检查给出的 8 动作窗口，没有与 Fail-Fast 等近年在线基线比较检测召回、误停率和延迟。无成功参照的既有 RQ1 复验仍是 NO-GO。
3. **不能推出二分总能处理 Agent 故障。** 它依赖故障检查的单调性；自然轨迹中可能出现暂时失败后自我修复。
4. **不能将题目定为《面向智能软件 Agent 的运行故障检测与责任动作定位方法研究》。** 动作级受控机制已有规模证据，但“运行故障检测”和自然失败责任定位仍未通过。

#### 7. 对开题的真正价值

这个 GO 把前期只到“文件与修复相关”的证据推进到了“具体动作造成可执行状态转坏，撤销该动作才恢复”的证据。它可以作为第二章方法中的核心机制，但还需要两个扩展：

1. 把 Python 语法编译探针扩展为语法、导入、局部测试和文件状态等多类可观察后果。
2. 在自然 Agent 失败中只对有可执行故障假设的动作进行恢复/替换干预，并与静态轨迹评分、最近编辑和逐动作检查比较。

在这两项完成之前，合理的工作题目应该窄于“运行故障检测与责任动作定位”，不应为了保留旧题目而拔高证据。
