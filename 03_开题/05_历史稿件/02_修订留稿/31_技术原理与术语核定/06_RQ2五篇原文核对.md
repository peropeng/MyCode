# RQ2 原理与命名核定

核定日期：2026-10-26。依据当前开题正文 §3.4，以及实验262留存的 `SOURCE/ours_core/progress_guard240.py`。只核对文献与现有机制，未运行实验。文献读取范围为以下原论文的方法定义和相关实验解释，不将摘要检索视为全文阅读。

## 结论与名称建议

RQ2 是诊断引导的迭代程序修复：历史步骤排序改变修复上下文，模型依据当前代码和执行反馈生成候选，再以测试约束决定是否更新当前代码。最直接的研究范式是 **生成—验证式程序修复（generate-and-validate program repair）**，而不是事务恢复、强化学习训练或蒙特卡洛树搜索。

建议三个流程框分别命名为：**排序引导的修复上下文构建 → 反馈驱动的补丁生成 → 基于测试的补丁验证**。第三框下方用小字注明“保持回归测试与累计已通过目标”。若标题需要突出本课题具体设计，§3.4.3 可用 **累积测试约束下的补丁验证**；正文再说明“接纳／拒绝”是验证结果触发的状态更新决策。这里的“累积测试约束”是对本文规则的描述性命名，不能宣称是已有独立算法的标准名称。

“补丁验证”有 Agentless 的直接原文阶段名称支持；“补丁接纳”适合描述决策动作，但不必作为第三项技术的上位名称。“修复上下文构建”比“同步机制”准确，因为本文收集历史编辑、当前源码和反馈，不要求恢复 SyncMind 意义上的协作信念状态。第二项可以保留现有“反馈驱动的候选补丁生成”，不必增加抽象术语。

## 五篇核心论文：可支持的原理与不能外推的部分

### 1. SyncMind：当前环境信息与失步恢复

来源：[ICML 2025 正式页面](https://proceedings.mlr.press/v267/guo25l.html)。已读 §2.1–2.3、§3.1 的问题与数据构造。核对定位：§2.2 Agent Out-of-Sync Recovery。

短摘录（14词）：“independent agents update their world beliefs through interacting with Environment (Env) and proposing solutions”。

原方法中的失步是智能体信念状态与实际项目状态不一致；恢复通过环境交互、反馈反思或协作者帮助获取缺失更新。§2.3 另以交互轮数和假设成本约束恢复资源。该文可支持“历史认识可能落后于实际环境，恢复需要获取当前状态”这一动机。本文每轮读取当前代码，是这一动机的具体适配。

边界：SyncMind 不提出本文的责任步骤排序、历史编辑筛选或累计通过集合；其 out-of-sync recovery 不等于本文全部失败任务恢复。不能据此把第一个框命名为“信念同步算法”，也不能声称本文复现 SyncMind。

### 2. STRATUS：事务式非退化的严格前提

来源：本地正式论文 `formal_literature/pdf/stratus.pdf`（NeurIPS 2025）；§3.1–3.3、§4.1。核对重点：§3.1.1 Assumptions、§3.1.2 Transaction Semantics、§3.1.3 Transactional Non-Regression。

短摘录（19词）：“An aborted transaction leaves no trace on externally visible state transitions.”；“A1 Writer Exclusivity”；“A2 Faithful Undo”；“A3 Bounded Risk Window”。

原方法以系统严重度 μ 为指标。事务先保存检查点，再执行操作；仅当执行成功且 μ(后态)≤μ(前态) 时提交，否则精确恢复前态。安全结论针对外部可见状态，事务内部允许存在较差的中间状态。论证依赖独占写入、忠实撤销和有界事务长度。§3.3 的并发扩展还依赖资源集合隔离，不是补丁集合的筛选规则。

与本文的联系仅为：候选执行后检查是否退化，未通过则保持此前状态。本文把退化具体定义为受保护测试标识失去通过状态，且候选代码快照的恢复不自动等于外部系统全部副作用的回滚。因此可引用“非退化约束”的设计动机，不应把测试保持规则称为 TNR 的直接实现或引用其定理证明整个程序安全。

### 3. Reflexion：反馈转成反思记忆，再用于下轮

来源：[NeurIPS 2023 正式论文](https://proceedings.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html)。已读 §3（页3–5）、算法1及相关实验解释。

短摘录（16词）：“This feedback, which is more informative than scalar rewards, is then stored in the agent’s memory (mem).”

原方法区分 Actor、Evaluator 与 Self-Reflection；评估结果连同轨迹产生自然语言反思，存入跨尝试记忆，再条件化下一轮生成。模型权重不更新。本文把既往执行结果放入下一轮输入，可以引用其反馈迭代思想。

边界：若本文未实现独立的反思生成及反思记忆，就不要声称采用完整 Reflexion 或“语言强化学习算法”；传入测试日志本身不等于自反思。适合用“反馈驱动／反馈引导的迭代修复”描述当前机制。

### 4. LATS：树搜索、反馈与反思共同构成方法

来源：[ICML 2024 正式页面](https://proceedings.mlr.press/v235/zhou24r.html)。已读 §3.2、§4.1–4.2（页4–6）。

短摘录（7词）：原文六种操作为“selection, expansion, evaluation, simulation, backpropagation, and reflection”。

原方法以状态为节点、动作为边，通过 UCT 选择、扩展多候选、价值评估、模拟和回传组织搜索，失败轨迹及反思参与后续上下文。价值函数组合语言模型评分与自一致性。它支持“环境反馈可以参与多轮候选探索”的一般论点。

边界：本文当前是一条接纳状态上的连续补丁尝试，没有 UCT、搜索树与价值回传。因而不应把本文第二项称为“蒙特卡洛树搜索”“树搜索修复”或引用 LATS 作为本文搜索算法公式的来源。若仅需解释测试反馈迭代，RepairAgent 比 LATS 更直接。

### 5. AgentSpec：可执行规则参与运行时决策

来源：[作者公开的 ICSE 2026 正式稿](https://cposkitt.github.io/files/publications/agentspec_llm_enforcement_icse26.pdf)。已读 §3.1–3.3、§4。

短摘录（11词）：“check, the condition that must be satisfied for the rule to take effect”。

原方法以规则组织事件触发、谓词检查和执行干预，能在动作前、观察后或任务结束时检查状态；干预包括停止、人工检查、预定义动作或模型自省。它支持“将约束显式化为运行时可执行检查，再据此干预执行”的一般框架。

边界：本文测试完成后计算集合包含关系，是一个具体的可执行约束，但未实现 AgentSpec DSL，也未使用其各类安全规则。不能以此直接命名为“形式化验证”或声称普遍安全保证。本文是否更新代码，由明确测试结果判定，而非仅凭模型自评。

## 更直接的程序修复依据

### Agentless

来源：[FSE 2025 作者正式稿](https://lingming.cs.illinois.edu/publications/fse2025.pdf)。已读 §3.3，重点 §3.3.1–3.3.2。

短摘录（16词）：章节标题“Patch Validation”“Patch Selection”；方法“keeps the patches with the lowest number of regression failures”。

Agentless 从多个候选补丁中选择交付，先识别原代码中的通过测试并剔除与需求变更冲突的测试，再使用回归测试、生成的复现测试和多数投票筛选候选。该文直接支持“补丁验证”及“补丁选择”这一阶段名称。

必须区分：Agentless 的回归错误最少规则不等于本文严格保留每个已通过标识；它也不维护本文的跨轮累计目标集合。该文适合解释通用验证阶段，本文公式应自行定义。

### RepairAgent

来源：[ICSE 2025 作者公开稿](https://arxiv.org/pdf/2403.17134)。已读 §III 中状态控制与工具交互说明，及评价中 plausible / correct 的区分。

短摘录（17词）：“Each fix attempt modifies the code base and is validated by executing the test cases.”

其流程在理解缺陷、收集修复信息、尝试修复之间转移，每次修复执行测试，必要时返回前面状态形成新假设或补充信息。它比 LATS 更直接支持本文“当前代码—补丁—执行反馈—下一轮”结构。论文区分通过测试的 plausible patch 与语义正确的 correct patch，可用于界定本文测试验证的结论范围。

## 当前机制核对：应突出集合保持，而非通过数量

正文 §3.4.3 与源码 `RepairProgressGuard.consider` 一致：基线回归集合 B 必须全部通过；PROGRESS_SET 模式还要求 frontier ⊆ goal_pass。候选通过才更新 incumbent，并把 goal_pass 合并到 frontier；拒绝候选的新增通过项不进入保护集合。初态通过的目标已加入初始 frontier。普通回归保持与按失败数量保持是不同对照。

可写为：对第 t 轮候选代码 S′，只有 B∪H_t⊆Pass(S′) 时才更新当前代码，随后 H_{t+1}=H_t∪(Pass(S′)∩T_goal)。这一规则容许无新增通过项的候选，故应称“保持”或“非退化”，不能称每轮严格提升。

在测试标识、测试代码、运行环境稳定且观察完整确定时，H_t 恰等于当前已接纳状态通过的目标集合。因此本文机制不是比“保留当前所有已通过目标”更强的新数学性质；特点是将原本失败、后来通过的目标逐步加入后续约束，区别于只保护固定基线回归项。名称和创新表述应落在这一适配及其效果验证上。

源码还对测试覆盖、冻结测试、进程终止及结果一致性进行检查，未知结果抛出异常。`restore_exact` 比较业务源码哈希，支持源码恢复核验；这仍不意味着任意外部系统状态全部精确恢复。无需为此次术语核定运行程序测试。

## 可直接用于正文的一段原理说明

本方法采用生成—验证式程序修复流程。责任排序用于选择历史编辑，并与当前源码及可见执行反馈共同构成修复上下文；生成模型据此提出候选补丁，执行结果用于后续修正。补丁验证除检查初态已通过的回归测试外，还将各轮已接纳状态中确认通过的目标测试纳入后续约束。只有保留这些测试通过状态的候选才能更新当前代码。该机制将新获得的测试进展作为下一轮验证条件，其有效性与限制通过恢复效果及接纳策略对照评价。
