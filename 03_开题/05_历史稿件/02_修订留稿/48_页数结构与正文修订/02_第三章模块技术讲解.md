# 第三章模块技术讲解

这份说明与开题正文使用同一套模块。先说明数据在模块之间怎样流动，再解释具体计算。下面的任务、分数和修复过程均为教学示意，不是实验结果。

各模块的论文、专业中文表达与实际实现依据见[逐段溯源与学术表达核查](08_逐段溯源与学术表达核查.md)。下文示例用于解释运算，不作为实际数据或方法效果的证据。

## 1. 整个方法接收什么，最后得到什么

方法接收一次已经失败的任务执行，分成两个阶段。

**执行轨迹**记录同一任务从开始到结束的实际过程，**步骤**刻画其中一次具体的决策或交互活动。各数据源原有的记录边界与编号在适配时保留。**排序阶段**读取完整失败轨迹，输出优先检查的步骤编号；**恢复阶段**从失败后留下的当前代码出发，利用排序筛选历史材料，继续提出和验证修改，输出最终代码。

这里有三个不同对象，先分清楚：

| 对象 | 里面有什么 | 用来做什么 |
| --- | --- | --- |
| 历史轨迹 | 当时说了什么、读了什么、改了什么、工具返回什么 | 判断哪些历史行为值得先查 |
| 当前代码 | 失败执行结束后实际留下的实现，此后随修复更新 | 本轮补丁真正修改的对象 |
| 测试与反馈 | 本次要求是否满足、已有功能是否保留、失败报错 | 指导后续修改并判断候选能否采用 |

排序分析的是历史步骤，恢复修改的是当前代码。两个阶段通过“选中的历史编辑及其与当前实现的对应”连接。

## 2. 用一个失败任务贯穿所有模块

任务要求是：为查询接口增加分页，并继续正确支持按状态筛选；删除和更新接口的既有功能也要保留。

| 步骤 | 执行者 | 记录内容 |
| --- | --- | --- |
| 1 | 规划者 | 说明分页要求，并指出原有状态筛选应继续有效 |
| 2 | 实现者 | 读取查询函数，查看原来的筛选条件 |
| 3 | 实现者 | 改写查询，在示意中遗漏了状态筛选条件 |
| 4 | 检查者 | 阅读其他实现，没有发现遗漏 |
| 5 | 实现者 | 修改响应格式，使其适配分页返回 |
| 6 | 验证者 | 分页测试通过 |
| 7 | 验证者 | 状态筛选测试失败，返回了不符合状态条件的数据 |
| 8 | 协调者 | 记录任务尚未完成并结束执行 |

这个例子的关键错误发生在第3步，但失败反馈到第7步才出现。第5步同样修改了代码，也值得排查。排序要帮助确定先检查第3步还是第5步；第7步本身提供失败证据。

```mermaid
flowchart LR
  A[完整失败轨迹] --> B[步骤特征编码]
  B --> C[门控多关系消息传递]
  C --> D[全局自注意力聚合]
  D --> E[轨迹内步骤评分]
  E --> F[优先检查的步骤次序]
  F --> G[修复上下文构建]
  G --> H[候选补丁生成]
  H --> I[测试验证与代码更新]
  I -->|满足停止条件| J[选定交付与独立验收]
  I -->|继续修复时更新代码及反馈| G
```

图表示主要数据流。评分模块还保留读取初始表示的路径，避免后面的信息聚合完全覆盖步骤本身的内容。

## 3. 排序模块一：步骤特征编码

### 输入

每步的文本、执行者、可观察操作与反馈、原始编号及日志字段形式。当前适配规则还识别特定日志格式中的决策上下文及其后续动作，将其作为关联记录使用。

### 实际做的事

固定的Qwen3-Embedding-0.6B编码器将每步的内容、动作及思考字段转换为向量。例如第3步的表示包含查询修改内容，第7步包含状态筛选失败信息；这些向量不是预先给出的正确性分数。

当前原型不独立编码原始任务说明，只能利用记录本身携带的信息。本例第1步已记录任务要求，因此其他步骤能够从该记录读取相关内容；真实来源是否保留这些信息，需要按实际输入核对。

执行者在同一轨迹内匿名编号，使模型知道第2、3、5步来自同一个执行者。结构特征还记录相对位置、字段形态和重复情况。文本、身份与结构共同形成步骤的初始表示。

部分日志将过去经验、工具状态、当前计划等写入一条显式决策上下文，紧接着由同一执行者给出下一条动作或输出。当前规则在原步骤号连续、执行者及特定格式吻合时建立配对，再把伙伴内容及差异通过门控融合到原步骤特征中。两个原编号仍分别保留，未识别到配对的记录保持独立。

### 输出与作用

输出是每个步骤的初始向量。后续模块据此判断步骤之间怎样联系，也保留它参与最终评分。这个模块解决“怎样让模型读懂每条记录的内容和形式”，此时还没有完成根因排序。

## 4. 排序模块二：门控多关系消息传递

### 输入

所有步骤的初始向量，以及按日志直接构造的四类关系。

| 关系 | 连接规则 | 本例中可能提供的信息 |
| --- | --- | --- |
| 时间相邻 | 连接前一步和后一步 | 第3步可以读取第2步原实现及第4步检查记录 |
| 同一执行者 | 连接该执行者前后最近的记录 | 第3步可以联系第5步，理解实现者后续又做了什么 |
| 完整记录结构相同 | 对字段形式相同的记录，连接前后最近者 | 两次形式相同的编辑记录可成为邻居 |
| 非空动作结构相同 | 对非空动作字段形式相同的记录，连接前后最近者 | 类似工具操作可成为邻居 |

“结构相同”比较日志字段和类型等形式。它提供可观察的联系，具体记录是否相关还要由内容、模型和实验判断。每类只连接最近的匹配记录，不把一条轨迹直接变成全连接图。

### 实际做的事

以第3步为例，模型读取关系邻居的向量，把邻居内容以及它与第3步的差异变换成“消息”。这里的消息就是传递给当前步骤的一份数值信息。

门控为每条消息计算0到1的比例，例如某条消息保留较多、另一条保留较少。每条边独立计算比例；各类关系内部汇总消息后，再由当前步骤决定不同关系各占多少，融合得到新的步骤向量。当前实现进行两层更新，第二层能够利用邻居已经汇集的信息。

### 输出与作用

输出仍然是每个步骤一个向量，但已经包含邻步信息。它解决“让一个步骤结合明确相关的附近记录理解”。关系图规定可以从哪里读信息，门控和关系融合决定这些信息怎样参与表示。

这里借用的是图神经网络中的消息传递机制。四类连边规则和具体融合方式需要用实验验证；“有连边”本身不等于“存在因果关系”。

## 5. 排序模块三：全局自注意力聚合

### 输入

关系更新后的全部步骤向量。一次诊断针对已经结束的完整轨迹，因此可以读取候选步骤之前和之后已经发生的记录。

### 实际做的事

第3步需要联系第1步的任务要求及第7步的失败反馈，这些信息可能不在它的局部邻居中。模型让第3步提出一个查询，再与全轨迹各步进行匹配，决定分别读入多少信息。第5步提出的是另一个查询，因此可以形成不同的读取重点。

自注意力中的三个名称分别表示：

- **查询：** 当前待判断步骤用来寻找相关信息的表示。
- **键：** 其他步骤供查询匹配的表示。
- **值：** 匹配后真正汇集进来的内容表示。

三个量都由同一轨迹的步骤向量转换得到，所以叫自注意力。当前实现先保留全轨迹均值作为共同背景，再在其上加入每个候选的注意力修正，得到该候选的上下文。

### 输出与作用

输出是每个候选各自的全局上下文。它解决“判断这一候选时，应结合全轨迹中的哪些信息”。读取权重用于汇集证据，最终检查次序由下一个评分模块产生。

消息传递与全局读取的分工是：前者沿规定的日志联系汇集信息，后者从全轨迹补充候选相关的信息。两者是否互补，需要与去除关系传播、改用共享均值上下文的设置比较。

## 6. 排序模块四：轨迹内步骤评分

### 输入与操作

评分网络对每一步读取四份信息：这一步的初始表示、关系更新后的表示、它自己的全局上下文，以及步骤表示与上下文的差异。模型把四份向量拼接，经过线性变换和非线性变换，压成一个数值分数。所有步骤共用同一套评分参数，再按分数降序排列。

在本例中，可以示意为第3步得分最高，第5步其次，第7步再后。输出是“先查3，再查5，再查7……”的编号列表。即使第7步包含报错信息，模型也可以把更早引入错误的第3步排在前面。

### 模型怎样学会打分

训练数据为每条失败轨迹提供一个标注错误位置。设一条轨迹有`m`步，第`i`步的输出分数为`s_i`；`p_i`是将同一轨迹所有分数归一化后，第`i`步对应的预测概率；`y`是**该条训练轨迹的标注错误位置**，取值为1到`m`。这里按1起编号，实现中的数组下标和日志原编号通过适配映射保持对应。

$$
p_i=\frac{\exp(s_i)}{\sum_{j=1}^{m}\exp(s_j)},\qquad
\mathcal L=-\log p_y.
$$

这里`j`遍历同一轨迹的所有步骤，`𝓛`表示这条轨迹的训练损失。标注为第3步时，提高第3步相对于其他候选的分数可以降低损失；训练据此调整评分及前面可学习模块的参数。固定的文本编码器不随这一步训练更新。

`y`在训练中提供监督，预测新轨迹时没有这个标签。恢复器使用模型输出的排序，也不读取`y`。原稿中突然出现`y`而不解释，会把训练信息、预测输入和恢复输入混在一起。

这种训练没有为所有步骤提供完整的责任先后关系。它首先学习让标注位置优先出现，前几位之外的全序由共享评分函数估计。现有三模型部署是分别归一化后平均概率；它与“三种数据划分”是不同安排。

## 7. 恢复模块一：排序引导的修复上下文构建

### 输入

原任务、排序列表、历史轨迹、当前代码、允许读取的测试反馈。

### 实际做的事

先沿排序找实际成功修改过项目源码的步骤，提取修改前后的差异，去除同一次工具调用的重复记录。纯讨论、读取和验证步骤可以帮助诊断理解，但不会自动成为历史源码编辑。

本例第3步排在前面，恢复器可以读到“此前怎样改写了查询”。第5步又修改了相关实现，因此当前文件已不同于第3步刚执行完的版本。恢复器继续读取当前函数，结合“状态筛选失败、分页已经通过”的反馈，形成生成模型本轮实际读取的材料。

历史编辑筛选的数量和输入容量事先固定，后续轮次按既定次序补充历史材料，并刷新当前实现与反馈。输出不只是一个排序列表，而是原任务、选定历史差异、当前代码和测试结果组成的具体输入。

### 这个模块为什么重要

它把过去的行为线索转成当前可用的修复信息，避免根据旧版本直接覆盖当前的正确修改。判断根因排序是否真正参与恢复，也应看这里：不同排序有没有选入不同的编辑，实际输入有没有变化。

如果完整步骤排序变了，筛选后仍得到完全相同的历史编辑和输入，就不能把这次恢复结果的差异归因于排序输入的变化。

## 8. 恢复模块二：反馈驱动的候选补丁生成

生成模型读入上一个模块的材料，提出对当前代码的具体修改。例如恢复状态筛选条件，同时保留分页响应格式。执行端在当前代码副本上应用该补丁，得到候选版本。

补丁不能应用时，将应用错误作为下一轮可见反馈；补丁能够应用时，进入测试验证。测试失败的现象也供下一轮使用，帮助补充代码读取或改变修改方案。

这个模块输出候选代码，是否采用该代码由下一模块决定。重复生成使用最新代码和反馈，不是每轮从原始仓库重新开始。

## 9. 恢复模块三：基于测试的补丁验证与交付

### 先确定两类测试

- **目标测试：** 检查本次任务要求。本例包括分页查询和状态筛选。
- **回归测试：** 检查需要保留的已有功能。本例包括初态已经通过的删除、更新接口测试。

任务开始恢复时，分页目标已经通过，状态筛选目标失败。因此初始保护内容包括删除、更新等已通过回归项，以及已通过的分页目标。

### 候选代码怎样采用或拒绝

| 候选表现 | 处理 | 原因 |
| --- | --- | --- |
| 修好状态筛选，但破坏分页 | 拒绝，继续保留此前代码 | 已通过目标被破坏 |
| 保留分页和回归功能，并修好状态筛选 | 采用，并把状态筛选加入保护 | 保留旧进展并取得新进展 |
| 保留全部保护项，但没有新目标通过 | 规则允许采用 | 保持条件不要求每轮都有新增通过项 |
| 测试缺失、超时或结果无法确定 | 停止继续更新，保存已有状态 | 没有完整结果支持此次代码更新 |

这一规则检查的是测试项的身份。例如以前通过分页，现在改为只通过状态筛选，虽然通过数量没变，但分页已退化，候选仍应拒绝。被拒候选中新通过的项，也不会加入后续保护。

### 用一个公式对应实现

令`B`为初态已通过且需要保护的回归测试集合；`T_goal`为预先固定的目标测试集合；`H_t`为第`t`轮之前已经采用的代码累计通过的目标项；`S'`为本轮候选代码；`Pass(S')`为本轮实际确认通过的测试项集合。只有满足下式，才更新当前代码：

$$
B\cup H_t\subseteq \operatorname{Pass}(S').
$$

采用后得到下一轮保护集合`H_{t+1}`，它由原集合`H_t`与本轮新通过的目标项合并而成；拒绝时继续使用旧代码，保护集合不变。`T_goal`始终保持原定义，变化的是其中已通过并需要保护的子集。

### 最后怎样判断恢复成功

目标全过、尝试次数耗尽或预算用尽时停止生成。依据当时可见的反馈从已有代码状态中选择交付，再交给与生成过程隔离的验收测试。最终验收通过，才记为恢复成功。

可见测试参与修改，独立验收参与评价。后者的答案不传回正在修复的模型。测试保持能保证的是指定检查条件下的已通过项继续通过，最终完整任务效果仍要实际验收。

## 10. 用一句话记住每个模块

| 模块 | 它真正做的事 |
| --- | --- |
| 步骤特征编码 | 把每条日志的内容、执行者和形式变成模型可读取的向量 |
| 门控多关系消息传递 | 沿明确的日志联系，把邻居信息汇入当前步骤 |
| 全局自注意力聚合 | 为不同待判断步骤分别读取全轨迹中的相关信息 |
| 轨迹内步骤评分 | 综合这些表示，给历史步骤排出检查次序 |
| 修复上下文构建 | 从排序筛选历史编辑，并核对当前代码与失败反馈 |
| 候选补丁生成 | 根据这些材料提出本轮具体修改 |
| 测试验证与交付 | 检查是否保留旧进展，决定更新代码，并验收最终交付 |
