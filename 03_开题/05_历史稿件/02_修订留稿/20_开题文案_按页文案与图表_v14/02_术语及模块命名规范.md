# V14 术语及模块命名规范

题名固定为**基于学习排序的智能体失败诊断与任务恢复方法**。题名保留“任务恢复”以避免重复出现“失败”；正文首次定义后统一使用“失败任务恢复”，明确研究从失败执行留下的代码和环境出发，继续完成同一原始任务。

本规范先固定概念和模块名，再用于全文、图题、方法图、基线表及消融表。模块名称采用功能性术语，具体操作在正文解释。

## 研究概念

| 固定术语 | 本文含义 | 使用边界 |
| --- | --- | --- |
| 执行轨迹 | 同一任务一次尝试产生的有序步骤记录 | 保留来源字段、步骤边界和原始索引 |
| 失败诊断 | 分析已经失败的轨迹，输出历史步骤的责任排序 | 责任依据来源标签评价，因果判断仍需干预证据 |
| 责任步骤 | 数据来源按自身规则标注的关键历史位置 | 不统一改称已证实的根因 |
| 责任排序 | 同一轨迹内全部有效步骤的检查优先次序 | 分数和预测权重只作轨迹内比较 |
| 步骤初始表示 | 文本、匿名角色和日志结构特征编码后的向量 | 记为 $h_i^{(0)}$ |
| 关系增强表示 | 经过多关系门控传播更新的步骤向量 | 记为 $h_i$ |
| 步骤上下文向量 | 面向待评分步骤汇集全轨迹信息形成的向量 | 记为 $c_i$，不是一行注意力权重 |
| 历史编辑记录 | 失败轨迹中真实成功执行的源码修改及其来源 | 按编辑调用标识去重，不把无编辑步骤补造为记录 |
| 当前代码 | 本轮修复实际面对的文件内容 | 每轮重新读取，历史版本不能替代当前文件 |
| 修复输入 | 历史编辑、当前代码、原始问题和此前执行反馈组成的生成材料 | 全文用此词指生成模型本轮收到的材料 |
| 候选补丁 | 已提出、尚未被接纳的当前代码修改 | 应用检查和测试通过项须分别记录 |
| 补丁接纳 | 候选满足规定的测试保持条件后，更新当前已接纳代码 | 接纳本身不表示任务恢复成功 |
| 状态回退 | 拒绝候选时恢复此前已接纳代码 | 不等同于完成原始任务 |
| 失败任务恢复 | 从失败初态出发，利用诊断信息继续修正以完成原始任务 | 总称用于RQ2、流程和评价对象 |
| 恢复成功 | 预算节点已选定交付的结果通过规定独立验收 | 可见测试改善、候选接纳和继续运行分别记录 |
| 失败任务恢复成功率 | 按软件问题汇总的独立验收成功比例，记为RSR | 同一问题三次完整运行先取比例，再按问题平均 |

## RQ1 模块名

| 固定名称 | 输入及核心计算 | 输出 |
| --- | --- | --- |
| **步骤表征编码** | 编码步骤文本、匿名角色和日志结构特征，拼接投影 | 步骤初始表示 |
| **多关系门控传播** | 沿四类可观察连接传递邻步消息，学习消息门控及关系融合 | 关系增强表示 |
| **步骤上下文聚合** | 面向各步骤计算全轨迹注意力，以轨迹均值加注意力修正形成上下文 | 步骤上下文向量 |
| **轨迹内责任评分** | 将 $h_i$、$h_i^{(0)}$、$c_i$、$h_i-c_i$ 拼接后输入MLP | 步骤分数及完整责任排序 |

第三章用“3.2 关系增强的步骤表征”说明前两个模块，用“3.3 上下文感知的责任评分”说明后两个模块及监督学习。标题描述一个计算目的，避免把两个并列概念简单拼接。

StepFinder分别组织轨迹编码、时序特征提取、角色感知交互及步骤评分，这支持按计算功能命名模块的写法。本文名称按自身计算重新确定，没有将StepFinder的时序模块直接改名为本文关系模块。[StepFinder原文](https://arxiv.org/html/2606.03467v1)

“多关系门控传播”明确本文有可学习消息门控。关系类型来自可见日志，模型也学习关系融合权重。R-GCN提供按关系类型组织信息传播的基础参考，但本文名称不表示完整照用其架构，也不表示连接已被确认为错误的因果传播路径。[R-GCN原文](https://arxiv.org/abs/1703.06103)

## RQ2 模块名

| 原V13名称 | 固定名称 | 名称所指的功能 |
| --- | --- | --- |
| 历史编辑记录选择与当前代码读取 | **排序引导的修复输入构建** | 按责任排序选择历史编辑，每轮读取当前代码，组织原始问题和已有反馈 |
| 候选补丁生成与测试 | **反馈驱动的候选补丁生成** | 根据修复输入生成修改，经应用检查和可见测试形成下一轮反馈 |
| 已通过测试检查与补丁接纳 | **测试保持约束下的补丁接纳** | 要求初始已通过回归项和累积已通过目标项继续通过，决定接纳或回退 |

“反馈驱动”描述应用错误和测试结果进入下一轮生成输入，生成模型参数保持固定。“补丁接纳”描述逐轮状态更新，不暗示同时比较候选池。“测试保持约束”只约束实际执行且状态确定的可见测试。

Agentless按定位、修复和补丁验证划分流程，EnAgent按生成、剪枝和选择组织功能。本文据此采用可识别的功能模块表达，同时明确自身使用历史步骤排序和逐轮测试保持条件。[Agentless作者论文](https://lingming.cs.illinois.edu/publications/fse2025.pdf)，[EnAgent正式会议页](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/233/Agent-Based-Ensemble-Reasoning-for-Repository-Level-Issue-Resolution)
