# 0. 独立评审结论

## 0.1 对上一版 RQ1 的处置

上一版 RQ1“运行故障转变的可执行验证”不再建议作为硕士论文第一章。它能够证明仓库状态可恢复、某段动作前后存在可重复的健康—故障转变，但其核心产出仍偏向**实验数据合同与故障重现接口**，缺少足够独立的系统目标，也没有直接证明它能够改善 Agent 的运行结果、故障检测收益或调试效率。若把“检查点、编译检查和区间重放”本身包装成第一章方法，导师很容易追问：这与常规测试、断点恢复或二分定位相比，研究问题究竟在哪里？

因此，本报告正式拒绝“故障验证”作为第一章主问题，不再把它写入题目、研究目标或创新点。现有检查点能力保留为第二章的实验基础设施。

## 0.2 在线故障检测是否属于足够大的研究方向

答案是**属于，但必须从“根据前缀猜最终成败”升级为“基于过程证据的在线故障检测与及时纠偏”**。

与上一版不同，本次检索找到了与研究对象直接一致的正式论文：

- [Process-Centric Analysis of Agentic Software Systems](https://doi.org/10.1145/3798271)，OOPSLA 2026 正式论文。论文把软件工程 Agent 视为随机、适应性的现代软件系统，构建 Graphectory 表示 SWE-agent 与 OpenHands 的执行过程，并在运行时识别轨迹问题、发送诊断信息和必要时回退轨迹；在线监测与干预使问题实例的解决率提高 6.9%—23.5%，同时缩短轨迹。该论文不是把在线监测作为附带小模块，而是围绕“从终局评价转向过程中心分析”展开整篇工作。
- [SAFE: Multitask Failure Detection for Vision-Language-Action Models](https://proceedings.neurips.cc/paper_files/paper/2025/hash/392d0d05e2f514063e6ce6f8b370834c-Abstract-Conference.html)，NeurIPS 2025 Main Conference。整篇论文正式定义跨任务及时故障检测，评价未见任务上的准确性与检测时间权衡。
- [RoboFailRing](https://aclanthology.org/2026.acl-long.602/)，ACL 2026 Long。整篇论文研究运行中及时检测、故障原因推理与修复建议，说明“检测—原因—修复”可以形成完整研究链。

其中 SAFE 和 RoboFailRing 属于具身 Agent，不能直接作为软件 Agent 的方法成绩；但它们证明“及时故障检测”本身足以成为 CCF A 正式论文的主要研究问题。OOPSLA 2026 则提供了与软件工程 Agent 直接一致的正式支撑。

因此，新 RQ1 不再写成“验证某个故障区间”，而改为：

> **运行过程中，如何仅依据已经发生的执行轨迹与仓库状态，及时检测已形成或正在持续的故障，给出可核查证据，并以低干扰方式触发纠偏，使 Agent 更可靠地完成任务？**

## 0.3 对当前 RQ2 的判定

当前 RQ2 不是失败实验。它已经在 34 个独立任务、8 个仓库上形成了同状态恢复、动作前缀重放、责任动作定位和撤销恢复的完整闭环；同预算二分重放 Top-1 为 100%，均匀检查为 47.06%，配对置信区间下界严格大于零，撤销已定位动作恢复 34/34，撤销后续同文件动作恢复 0/34。

但它当前只能判定为：

> **受控、单调语法故障下的责任动作定位机制 GO；面向一般软件 Agent 故障的第二章仍为 Conditional-Go。**

原因是当前实验预先知道故障位于一个 8 动作窗口内，故障统一为未闭合分隔符，检测探针统一为 `py_compile`，状态从“通过”到“失败”单调变化。在这种构造下，二分定位得到 100% 具有较强的算法必然性。它证明实现正确、状态一致和干预闭环有效，却尚未证明自然语义错误、工具参数错误、延迟失败、自我恢复或多故障情况下仍然有效。

## 0.4 总体开题判定

> **当前原方案：NO-GO。**  
> **按本文重构后：Conditional-Go；完成开题前联合 Pilot 后可转为“修改后 GO”。**

新的研究主线不是：

```text
故障验证 → 已知区间二分定位
```

而是：

```text
过程证据驱动的在线故障检测
        ↓ 输出故障类型、原始证据、候选动作区间和检查点
同状态自适应重放定位
        ↓
最小撤销/替换与负对照验证
```

该主线既有正式 CCF A 论文为整体方向站台，又能直接复用当前 34 任务责任动作定位成果；两章的联合实验不再要求“风险分数提高 MRR”，而是验证**第一章在线检测得到的故障类型、证据和候选区间，是否让第二章以更少执行成本找到并验证责任动作**。

# 1. 对全部已有实验的重新解释

## 1.1 可保留的证据

| 已完成实验 | 当前判定 | 可以支持的结论 | 不能支持的结论 |
|---|---|---|---|
| 成功参照早期故障识别，1,200 条轨迹 | 历史 GO，但退出主线 | 历史成功过程含有失败识别信号 | 成功参照必须成为论文主方法 |
| 无成功参照的在线检测，1,200 条轨迹 | NO-GO | 当前轻量状态特征不足 | 在线故障检测方向本身没有价值 |
| 风险分数到动作定位，61 个动作簇 | NO-GO | 风险高峰不等于责任动作 | 所有第一章输出都无法帮助第二章 |
| 跨状态搬运事后错误动作，5 个任务 | NO-GO | 静态标注不能跨状态直接当干预对象 | 同状态重放不可行 |
| 检查点数据合同，10 任务、20 动作 | GO | 仓库状态可以恢复、动作可以精确重放 | 这是独立算法贡献 |
| 同检查点责任动作定位，34 任务、8 仓库 | 受控机制 GO | 单调可执行故障可以被高效定位并通过撤销验证 | 已解决自然 Agent 根因定位 |

## 1.2 旧 RQ1→RQ2 桥接为什么失败

旧桥接把 RQ1 的风险高峰或风险时间序列作为动作排序先验。负结果说明：

1. “这段轨迹看起来越来越可能失败”主要描述终局风险；
2. “哪个动作导致状态转坏”要求区分错误引入、后续传播和末端症状；
3. 风险最高的位置往往更接近测试失败、错误报告或终止动作，而不一定是错误引入位置；
4. 因此，风险分数并不是 RQ2 所需要的操作性证据。

新桥接改成传递以下可执行对象：

- 最后一个低风险/健康检查点；
- 第一个稳定异常或高风险检查点；
- 两者之间的候选动作区间；
- 触发检测的原始事件和仓库状态证据；
- 故障检测器判断的故障类型。

RQ2 不再把 RQ1 分数直接加到动作排名上，而是在该区间内从同一检查点进行真实重放。这样，第一章给出的信息与第二章的定位机制在语义和操作上是一致的。

## 1.3 当前 RQ2 结果为什么既强又不够

### 强的部分

1. 34 个 `instance_id` 互不重复，覆盖 8 个仓库；
2. 每次重放使用相同窗口起点，检查点哈希一致；
3. 与同样 3 次探针的均匀检查比较，预算公平；
4. 配对 Bootstrap 置信区间下界显著大于零；
5. 已定位动作的最小故障增量被撤销后，34/34 恢复；
6. 撤销后续同文件编辑 0/34 恢复，排除了“只要撤销同文件任意动作都行”；
7. 金标、结局和注入字段没有进入排名输入。

### 不够的部分

1. 8 动作候选窗口是已知的，尚未由在线故障检测器预测；
2. 所有故障均为未闭合分隔符，类型单一；
3. `py_compile` 既定义故障，也作为定位探针，任务与方法高度匹配；
4. 故障在窗口内单调持续，二分查找天然适用；
5. 不包含“先失败后自我修复”的非单调轨迹；
6. 不包含编译通过但测试语义回归的延迟故障；
7. 不包含错误工具参数、错误文件状态和跨文件依赖；
8. 尚未和完整轨迹 LLM Judge、Who&When 类步骤定位器、StepFinder 类时序定位方法在未知区间上公平比较。

因此，当前 100% 结果适合在开题中作为**机制可行性和工程基础**，不能作为第二章最终效果。

# 3. 新论文题目、目标与两个研究问题

## 3.1 最推荐题目

> **《面向软件工程智能体的在线故障检测与责任动作定位方法研究》**

题目采用稳妥抽象层级：

- “软件工程智能体”限定真实研究对象，不泛化到所有智能软件；
- “在线故障检测”对应第一章的明确研究任务：只使用当前及过去的运行信息，及时识别已形成或正在持续的故障状态；运行时过程监测只是支撑该任务的数据采集与表示手段；
- “责任动作定位”对应失败后的具体调试问题；
- 不在题目中写过程图、API、检查点、二分、误报率、数据集或因果根因。

### 3.1.1 术语层级：监测是手段，检测是任务，及时性是目标

为避免题目和答辩混淆，本文固定采用以下层级：

| 术语 | 含义 | 在论文中的位置 |
|---|---|---|
| **运行时过程监测（runtime process monitoring）** | 持续采集和组织动作、工具调用、观察、代码差异、测试与成本等运行信息 | RQ1 的底层输入与 M1 方法模块，不是论文题目中的研究目的 |
| **在线故障检测（online fault/failure detection）** | 在不读取未来事件和最终结果的条件下，根据当前及过去证据判断故障状态是否出现，并输出类型、证据和首次告警时刻 | RQ1 的核心研究任务，也是论文题目用词 |
| **及时故障检测（timely failure detection）** | 在低误报和可接受成本下尽量缩短从责任动作发生到正确告警的时间 | RQ1 的性能目标，通过检测延迟、提前量和任务结果评价 |

因此，正文允许说“运行时监测模块采集过程信号”，但整体方法、研究问题和实验结论统一使用“在线故障检测”。

## 3.2 备选题目

1. 《面向软件工程智能体的运行时故障检测与责任动作定位方法研究》
2. 《面向软件工程智能体的及时故障检测与责任动作定位方法研究》
3. 《面向软件工程智能体的运行过程分析与责任动作定位方法研究》

其中第一项强调“运行时”场景，第二项强调“及时性”目标，第三项最宽。开题阶段建议使用主标题；只有自然动作干预形成规模结果后，正文中才讨论“根因”。

## 3.3 总体研究目的

本研究面向软件工程智能体的长程执行过程，解决“故障能否在任务结束前被及时发现”和“失败后能否确认哪个动作真正导致状态转坏”两个问题。首先，从 Agent 已发生的动作、工具调用、观察、代码差异和测试状态中建立过程中心表示，在线检测计划偏离、振荡、无效编辑、工具误用和验证退化等故障状态，输出故障类型、原始证据、首次告警时刻和候选动作区间，并在证据充分且干预风险可控时触发建议或回退。其次，将在线故障检测输出的候选区间、检查点和证据交给同状态重放定位器，在固定执行预算内缩小责任动作范围，并通过最小撤销或替换及阴性对照验证动作责任。最终目标不是增加一个离线分类指标，而是形成“及时检测—必要纠偏—失败定位—执行验证”的可审计可靠性闭环。

# 4. RQ1：过程证据驱动的在线故障检测与纠偏

## 4.1 一句白话

> Agent 正在解决软件任务时，能不能只看已经发生的操作和仓库反馈，及时发现它正在停滞、偏离或把状态带坏，并给出有证据的下一步纠偏，而不是等最终测试失败后才知道？

## 4.2 学术表述

> 给定软件工程智能体在时刻 `t` 之前的可观察执行前缀及对应仓库状态，研究如何构建阶段感知的过程表示，联合结构行为、工具反馈、任务进展、可执行状态和语义证据，在线识别已经形成或正在持续的故障状态；输出故障类型、支持证据、首次告警时刻、置信度、候选动作区间与处置建议，并在控制误报、误干预、检测延迟和额外成本的条件下提高未见任务的解决率。

## 4.3 独立研究价值

RQ1 不需要靠 RQ2 才成立。它单独回答：

- 哪些过程问题可以在任务结束前被发现；
- 在线故障检测与纠偏能否提高实际任务解决率；
- 多少本来会成功的运行被误干预；
- 故障检测、可执行探针与 API 调用增加多少成本；
- 哪些问题适合建议、回退或保持观察；
- 检测效果是否跨模型、仓库和任务难度成立。

RQ1 的主要输出不是“最终会不会失败”的单一概率，而是面向当前运行状态的可核查检测结果：

```text
fault_type            故障类型
trigger_event_ids      触发证据事件
last_healthy_step      最后健康检查点
first_fault_alert_step 首个稳定故障告警位置
candidate_interval     候选动作区间
confidence             置信度
recommended_action     继续 / 检查 / 建议 / 回退
advice                  高层下一步建议
```

## 4.4 方法设计：控制在三个模块

### M1：过程中心的运行表示

**来源：**OOPSLA 2026 的 Graphectory，以及软件执行轨迹分析。  
**解决的问题：**原始日志把自然语言、工具、编辑和测试混在一起，简单最近窗口难以识别 Agent 当前处于定位、修改还是验证阶段。  
**内容：**

- 将动作统一为 `read/search/edit/test/execute/plan/finish` 等事件；
- 识别定位、修改、验证、提交等阶段；
- 构建时间边、文件读写边、工具输入输出边和测试依赖边；
- 记录工作区 diff、编译/导入/局部测试结果和重复/回退模式；
- 只使用 Agent 当时可见信息，不读取最终 `resolved` 或后续事件。

**预期作用：**为在线故障检测器提供“行为发生在什么阶段、影响了什么状态、后续是否继续依赖”的上下文，避免仅凭错误词和步数报警。

### M2：确定性证据与 API 语义诊断的融合检测

**来源：**OOPSLA 2026 的在线过程分析、LivePlan 的规则触发 Advisor、RoboFailRing 的检索与语言落地、OS-Sentinel 的确定性验证器与语义 Judge 组合。  
**解决的问题：**纯规则无法判断“当前操作是否符合任务语义”，每步直接调用大模型又成本高、容易产生无依据判断。  
**内容：**

1. 每一步通过运行时过程监测采集阶段违规、重复、停滞、无有效编辑、连续验证退化、无效工具参数和文件状态冲突，并作为故障检测的低成本初筛信号；
2. 必要时运行轻量探针：语法、导入、受影响测试、文件不变式；
3. 仅当规则或探针触发时调用 API；
4. API 输入任务要求、最近事件、关键历史、diff 与探针摘要；
5. API 必须返回证据事件 ID 和结构化判断，不能只给自由文本结论；
6. API 不能读取注入类型、金标动作或最终测试结果。

**预期作用：**规则保证低成本和可审计性，API 处理任务语义和跨步骤关系，探针约束 API 的事实判断。

### M3：证据约束的纠偏与回退

**来源：**OOPSLA 2026 的诊断消息与轨迹回退，以及 LivePlan 的高层下一步建议。  
**解决的问题：**检测准确不等于干预有效；错误建议可能破坏本来会成功的运行。  
**内容：**

- 低置信时只记录，不干预；
- 中置信时给出高层建议，不直接替 Agent 写补丁；
- 高置信且存在可恢复检查点时，允许回退到最近健康状态；
- 所有干预保存触发证据、前后状态和 Agent 响应；
- 采用“影子模式”和“干预模式”分开评价：先证明检测结果有效，再证明干预有净收益。

**预期作用：**减少误干预造成的回归，并将 RQ1 输出转化为可供 RQ2 使用的候选区间和检查点。

## 4.5 API 能否用于在线故障检测

可以，但不建议采用“每一步把完整轨迹发给 API，让它回答是否失败”的单一设计。更可行的工程方案是：

```text
Agent 执行一步
    ↓
运行时过程监测（采集）与低成本规则/探针（初筛）
    ↓ 未触发                       ↓ 触发
继续执行                      调用 API 语义诊断
                                  ↓
                    在线故障检测结果：类型、证据、区间、建议
                                  ↓
                    影子记录 / 建议 / 回退
```

建议配置：

- 固定模型版本、温度 0、结构化输出模式；
- API 调用只在触发后发生，另设固定周期 API 作为同预算基线；
- 输入窗口以最近事件为主，但保留任务要求、最近有效编辑和最近测试状态；
- API 生成的是**语义判断和建议**，故障事实仍由仓库状态与可执行探针支持；
- 在线线程可异步运行；只有需要回退或阻断时暂停 Agent；
- 记录每次调用的 Token、延迟、错误和重试。

## 4.6 数据设计：自然运行与受控运行双轨

### Track A：自然在线运行

**目的：**评价在线故障检测与纠偏是否真正改善软件任务完成。  
**任务：**从 SWE-Gym / SWE-bench Verified 选择至少 60 个独立任务，正式实验目标 80—100 个，覆盖不少于 8 个仓库，并按难度分层。  
**执行：**同一 Agent、同一模型和相同总预算下，比较无检测、规则检测、固定周期 API 检测和本文方法；建议每个任务至少两个随机种子。  
**标签：**官方测试是否解决；不人工定义每个自然失败的唯一责任动作。

### Track B：受控在线故障检测

**目的：**获得精确故障动作和转变时刻，评价在线故障检测是否及时、输出区间是否覆盖责任动作。  
**数据来源：**从真实成功 Agent 轨迹和可恢复检查点出发，在动作执行层施加最小故障，不改任务题面。  
**开题前至少覆盖三类：**

1. **语法/导入类：**未闭合语法、错误导入、符号名破坏；
2. **工具参数/文件状态类：**错误路径、错误命令参数、误写文件、错误工作目录；
3. **语义回归类：**编译通过，但局部测试、回归测试或任务不变式失败。

正式论文增加：

4. **延迟故障：**错误动作后若干步才由测试暴露；
5. **可恢复故障：**Agent 后续自行修正，验证检测器是否过早告警或干预；
6. **多故障：**两个动作共同造成失败，只作为压力测试，不作为初期主任务。

受控数据必须同时保留一条干净对照，注入类型和位置不能进入在线故障检测器输入。

## 4.7 RQ1 五个主要对照

1. **Vanilla Agent：**无在线故障检测、无纠偏；评价解决率基线。
2. **固定规则故障检测：**OOPSLA/LivePlan 风格的重复、振荡、停滞和阶段违规规则，不调用 API。
3. **固定周期 API Judge：**每隔相同事件数调用同一个 API，控制“只是调用了大模型”的解释。
4. **Fail-Fast / AgentForesight 风格前缀故障检测：**按论文协议做可复现适配；明确标注为预印本方法适配，不冒充官方完整结果。
5. **本文混合方法：**过程表示 + 触发式 API + 证据约束纠偏。

SAFE 和 RoboFailRing 属于跨场景正式理论参照，不直接把机器人模型数字与软件任务横向比较。

## 4.8 RQ1 主体实验

### 实验 R1-A：在线故障检测与纠偏能否改善自然任务解决率

| 条件 | 在线检测方式 | API | 可纠偏 | 主要回答 |
|---|---|---|---|---|
| Vanilla | 无检测 | 无 | 无 | 原始任务水平 |
| Rule-only | 规则检测 | 无 | 固定建议/回退 | 确定性证据是否足够 |
| Periodic-API | 固定周期诊断 | 有 | 有 | API 调用本身是否有效 |
| Hybrid-shadow | 融合检测 | 触发式 | 不执行 | 检测准确性，不受干预影响 |
| Hybrid-intervene | 融合检测 | 触发式 | 有 | 完整方法的净收益 |

**主指标：**任务解决率（Resolve Rate）。  
**关键辅助指标：**

- 相对 Vanilla 和最强故障检测基线的新增解决任务数；
- 原本成功运行被干预后失败的回归率；
- 平均轨迹长度、Token 和美元成本；
- 每个新增解决任务的额外检测与纠偏开销；
- 触发次数、API 调用次数和建议采纳率。

### 实验 R1-B：故障区间与检测时机

在受控故障数据上评价：

- 故障运行召回；
- 干净对照误报率；
- 首次报警到真实责任动作的步距；
- 候选区间是否覆盖责任动作；
- 候选区间平均宽度；
- 检测延迟；
- 每条轨迹的 API 与探针数；
- 可恢复故障上的过早干预率。

建议定义联合指标：

> **有效区间召回（Verified Interval Recall）**：在不超过预设误报与探针成本时，在线故障检测器输出的候选区间包含真实责任动作的故障比例。

该指标是实验定义，不写成新理论名词。

### 实验 R1-C：故障类型和纠偏收益

按以下类型分别报告：重复/振荡、计划偏离、无效编辑、验证退化、工具参数错误、语义回归。分析：

- 哪类问题规则即可处理；
- 哪类问题需要 API 语义判断；
- 哪类建议能提高成功率；
- 哪类干预容易破坏可成功轨迹；
- 不同 Agent 模型是否具有相同失效模式。

## 4.9 RQ1 开题与正式论文 Gate

### 开题前最低 Gate

1. 新增至少 45 个独立受控任务，覆盖不少于 5 个仓库和三类故障；
2. 本文方法相对最强同预算故障检测基线，在有效区间召回或故障截获率上相对提升至少 10%；
3. 任务级配对 Bootstrap 95% 区间下界大于 0；
4. 干净对照误报/误干预率不超过预先声明上限，建议 10%；
5. 真实责任动作区间覆盖率至少 80%，且平均区间不超过 8 个动作或轨迹长度的 25%；
6. 至少完成 20 个自然任务的影子检测和 10 个自然任务的实际纠偏，证明 API Hook 与执行链稳定。

### 正式论文 Gate

1. 自然任务解决率相对最强等预算在线故障检测方法有至少 10% 的相对增益，或取得明确的新增解决任务且配对区间下界大于 0；
2. 原本成功运行的回归率不超过 5 个百分点；
3. 受控三类故障上均保持正向增益，不由单一语法故障贡献全部结果；
4. 故障检测与纠偏开销低于节省的无效执行成本，或能以很小开销提高解决率；
5. 至少在两个 Agent 执行模型或两个脚手架上方向一致。

### 否定 RQ1 的结果

- API 语义故障诊断不优于简单周期调用或规则；
- 收益主要来自更高调用预算；
- 增加解决任务的同时大量破坏原本成功运行；
- 区间覆盖率低，不能为 RQ2 提供有效候选；
- 在新任务或换模型后全面失效；
- 只有人工注入语法错误有效，自然任务无任何运行收益。

# 5. RQ2：检测证据引导的责任动作定位与可执行验证

## 5.1 一句白话

> 第一章已经告诉我们故障大概在哪一段发生、当时出现了什么证据；第二章能不能从同一个检查点重放这段动作，找到第一个真正把状态带坏的动作，并通过撤销或替换证明不是后续症状？

## 5.2 学术表述

> 对 RQ1 在未见任务上输出的候选区间、健康/异常检查点和触发证据，研究如何根据故障探针的单调性与恢复行为选择自适应前缀重放策略，在固定执行预算内定位首个引起稳定可观察状态退化的责任动作，并通过最小撤销或替换、相邻动作和后续症状动作的阴性对照，评价该动作的结果责任。

## 5.3 RQ2 独立价值

即使 RQ1 已经报警，开发者仍需知道：

- 是哪一次代码编辑、命令、参数或状态改变造成问题；
- 后续哪个动作只是暴露症状；
- 撤销哪一步才能恢复；
- 定位需要多少次额外执行；
- 自我修复和多故障时定位如何变化。

RQ2 的独立成果是一个可执行动作定位器，而不是对完整轨迹生成一段自然语言解释。

## 5.4 方法设计：三个模块

### M1：消费 RQ1 的区间与检查点

RQ2 直接读取：

- `last_healthy_step`；
- `first_fault_alert_step`；
- 候选区间；
- 故障类型与探针；
- 触发证据。

它不把 RQ1 的风险值直接加到动作分数中，也不硬删除区间外所有动作。低置信时允许扩大区间或回退全轨迹，以防上游错误永久裁掉责任动作。

### M2：单调性感知的自适应重放

当前二分方法只对单调故障可靠。正式方法先判断探针结果是否近似单调：

- **单调区间：**前缀越长，故障一旦出现便持续；使用二分重放；
- **可恢复区间：**故障出现后又恢复；使用分段重放，定位引入动作与恢复动作；
- **延迟故障：**错误动作发生后若干步测试才失败；结合动作—后果依赖和候选编辑测试；
- **多候选/非单调：**使用候选逐一检查、Delta Debugging 或预算受控的分块消减，不强行二分。

二分、分段检查和 Delta Debugging 都是成熟算法，不单独作为创新。研究内容在于：根据在线故障检测输出的证据、候选区间与可执行状态选择合适定位策略，并评价各类 Agent 故障的适用边界。

### M3：最小干预与阴性对照

对高排名动作执行：

- 撤销该动作产生的最小 diff；
- 替换错误工具参数；
- 恢复到动作前检查点并执行修正版本；
- 保持其他前缀与测试环境一致；
- 同时撤销相邻动作、后续同文件动作、末端报错动作和随机动作作为阴性对照。

只有当目标干预显著改变故障结果，而对照干预不能产生同等恢复，才称为“获得可执行责任支持”。自然 Agent 后缀可能随机变化，因此需要重复重放并报告成功概率与置信区间。

## 5.5 RQ2 五个主要基线

1. **完整轨迹 API Judge：**直接从完整轨迹输出责任动作；同模型、同 Token 预算。
2. **Who&When / StepFinder 风格静态步骤定位：**基于局部与时序语义排名，不执行重放。
3. **同预算均匀重放：**当前最强执行型基线；固定相同探针数。
4. **逐动作早停或完整检查：**准确率与成本上界，不作为可部署方法成绩。
5. **本文方法：**RQ1 预测区间 + 单调性感知自适应重放 + 最小干预验证。

最后动作、最近报错编辑和固定随机保留为弱基线，不占主表的五个方法位置。

## 5.6 RQ2 数据扩展

### 受控主数据

在现有 34 个语法故障基础上扩充：

- 语法/导入类：至少 30 个任务；
- 工具参数/文件状态类：至少 30 个任务；
- 局部测试语义回归：至少 30 个任务；
- 总计目标 90 个独立任务，不少于 8 个仓库；
- 每个任务保存动作级检查点、工作区哈希、探针结果、干净轨迹和故障轨迹。

### 自然失败验证集

从新运行的 Agent 失败轨迹中选择至少 20—40 个满足以下条件的任务：

- 有可恢复检查点；
- 至少两个真实候选编辑或工具动作；
- 可以提出可执行故障假设；
- 候选动作能够被撤销或替换；
- 官方或局部测试能够稳定判定结果。

自然失败不强制每条都有唯一原因。无法形成稳定干预的样本应公开计入“不可验证”，不能静默删除。

## 5.7 RQ2 主指标

- Verified Top-1：排名第一动作是否通过干预得到责任支持；
- Verified Recall@3：前三动作是否至少有一个通过干预；
- MRR：正确责任动作的平均倒数排名；
- 干预闭环率；
- 阴性对照恢复率；
- 平均绝对步距误差；
- 平均重放探针数；
- 总 API、执行和测试成本；
- 非目标测试回归率；
- 无法重放率和状态漂移率。

## 5.8 RQ2 正式 Gate

1. 在至少 60 个独立任务、三类故障上，本文方法相对最强等预算基线的 Verified Top-1 或 Verified Recall@3 相对提升至少 10%；
2. 任务级配对 Bootstrap 95% 区间下界大于 0；
3. 目标动作干预闭环率不低于 80%；
4. 相邻/后续/随机阴性对照恢复率不高于 10%，且显著低于目标动作；
5. 平均探针数不超过逐动作完整检查的 60%；
6. 自然失败子集上至少方向一致，不允许全部增益来自语法故障；
7. 非单调或恢复型故障不得被强行删除，必须分表报告。

### 否定 RQ2 的结果

- 去掉 RQ1 区间后结果不下降；
- 预测区间不优于随机或固定窗口；
- 高排名动作和随机动作的干预恢复率相同；
- 只有 `py_compile` 单调故障有效；
- 真实自然失败的大部分动作无法从同状态重放；
- 排名提高但任务结果不发生预期变化。

# 6. 两章联合证明：新的核心实验

## 6.1 为什么不能再用“风险分数提高 MRR”作为桥梁

旧实验已经否定风险高峰的增量。新桥梁必须是 RQ1 实际输出、RQ2 实际需要的对象：候选区间、检查点和故障证据。

RQ1 与 RQ2 的关系为：

```text
当前轨迹与仓库状态
        ↓
RQ1 在线故障检测
        ├─ 故障类型与原始证据
        ├─ 最后健康检查点
        └─ 首个稳定异常检查点
                    ↓
             候选动作区间
                    ↓
RQ2 同状态自适应重放
                    ↓
责任动作 + 最小干预 + 阴性对照
```

## 6.2 联合实验条件

在同一批受控故障任务上，固定总 API 调用数、探针数或综合成本，比较：

1. **Full-trace API Direct：**任务结束后由 API 直接选责任动作；
2. **Fixed/Random Interval + Uniform Replay：**固定或随机窗口，执行均匀检查；
3. **RQ1 Predicted Interval + Uniform Replay：**只检验 RQ1 区间的价值；
4. **RQ1 Predicted Interval + Adaptive Replay：**完整两章方法；
5. **Oracle Interval + Adaptive Replay：**理想上界，不能算方法成绩。

附加条件：

- `No Monitor + Full Per-step Replay` 作为高成本上界；
- `Rule Monitor + Adaptive Replay` 检验 API 是否真正提供语义增量；
- `Shuffled Interval` 在任务间打乱 RQ1 输出，排除“只要缩小窗口就好”。

## 6.3 联合主指标

建议以固定总预算下的结果定义联合主指标：

> **Verified Responsible-Action Yield@Budget**：在限定 API、重放和测试成本内，最终找到并通过干预验证责任动作的任务比例。

同时报告：

- 责任动作覆盖率；
- Verified Top-1/Recall@3；
- 总探针数和 API 成本；
- 从责任动作发生到报警的延迟；
- RQ1 在线纠偏直接恢复的任务数；
- RQ1 未恢复后由 RQ2 找到责任动作的任务数；
- 从在线故障检测到责任定位的总耗时。

联合指标只是为了把两章放在同一预算中评价，不作为新理论名称。

## 6.4 联合 Gate

两章递进成立必须同时满足：

1. `Oracle Interval + RQ2 > No/Fixed Interval + RQ2`，证明区间信息理论上有用；
2. `Predicted Interval + RQ2 > Random/Shuffled/Fixed Interval + RQ2`；
3. 相对最强同预算基线提升至少 10%，配对 95% 区间下界大于 0；
4. 预测区间不通过硬裁剪大规模丢失责任动作；
5. RQ1 独立的在线解决率或检测收益也通过，不能只靠 RQ2 反向证明 RQ1；
6. RQ2 在预测区间而非人工 8 动作窗口上仍保持至少 80% 干预闭环。

若 Oracle 区间有效而预测区间无效，结论是 RQ1 仍不足；若 Oracle 区间也无效，则说明两章理论关系不成立，应停止该题目。

## 7.2 实验 P1：三类故障和干净对照

- RQ1 影子模式的候选区间；

- No/Fixed/Random/Predicted/Oracle 完整表；
- 每类故障的覆盖率、区间宽度、探针数和闭环率。

### 开题通过条件

## 7.3 实验 P2：API 辅助的在线故障检测与纠偏 Pilot

### 样本

- 20—30 个真实 SWE-Gym/SWE-bench 任务；

### API 输出契约

```json
{
  "fault_type": "stagnation | oscillation | invalid_edit | validation_regression | tool_misuse | none",

  "evidence_event_ids": [],
  "last_healthy_step": 0,
  "first_fault_alert_step": 0,
  "recommended_action": "continue | inspect | advise | rollback",
  "advice": ""
}
```

### Pilot 目标

- 结构化输出解析成功率 ≥95%；
- 触发式 API 调用数显著低于固定周期 API；
- 误干预率可控；
- 至少出现若干由建议或回退新增解决的任务；
- 检测器输出可无缝交给 RQ2；
- 不要求 20—30 个任务直接证明最终显著性，但若方向和基线均无正信号，则不开题。

## 7.4 实验 P3：自然失败的最小干预预检

- 从 Pilot 失败运行中选择至少 10 个存在真实代码编辑或工具参数候选的任务；
- 使用 RQ1 输出区间；
- 对 Top-1/Top-3 做撤销、参数替换或检查点重放；
- 与相邻、末端症状和随机动作比较；
- 记录无法重放、状态漂移和测试不稳定；
- 至少 7/10 能完成稳定执行链，才扩大正式自然失败实验。

# 11. 新开题报告正文

## 11.1 研究背景与现状

大语言模型驱动的软件工程智能体已经能够围绕真实代码仓库完成需求理解、代码检索、问题定位、补丁修改和测试验证。然而，这类 Agent 的运行轨迹具有长程、随机和状态依赖等特征：一次错误工具参数、错误代码编辑或错误验证判断可能改变仓库状态，后续动作继续基于该状态执行，最终才表现为任务失败。仅以最终解决率评价 Agent，无法解释运行过程中何时出现关键问题，也无法确定失败后哪个具体动作真正导致状态转坏。

近期研究正在从终局评价转向过程分析与及时故障检测。OOPSLA 2026 的 Process-Centric Analysis 将软件 Agent 视为现代软件系统，使用结构化执行表示分析定位、修改和验证过程，并通过在线监测与干预改善任务解决率；在本文中，这类运行时监测被视为在线故障检测的数据与触发基础。NeurIPS 2025 的 SAFE 和 ACL 2026 的 RoboFailRing 则分别证明，及时故障检测以及“检测—原因推理—修复建议”可以构成完整研究问题。另一方面，ICML 2025 的 Who&When、ACL 2026 的 TraceElephant 和 ARCHITECT 表明，仅知道任务最终失败不足以完成责任归因，完整执行证据和可控干预对于定位具体责任步骤与根因具有重要价值。

现有两类工作仍存在连接缺口：在线故障检测或运行时监测方法通常侧重早停、纠偏或运行效率，较少检验带原始证据的检测结果能否支持具体责任动作定位；事后归因方法通常读取完整失败轨迹，以文本判断责任 Agent 或步骤，缺少运行时检查点和可执行干预。因此，本研究拟构建从在线故障检测到同状态动作定位的连续证据链。

## 11.2 研究目标与意义

本研究旨在提高软件工程智能体运行过程的可观测性、干预有效性和故障诊断可信度。

第一，研究过程证据驱动的在线故障检测方法，从动作、工具、观察、代码状态和测试反馈中识别计划偏离、停滞、无效编辑和验证退化等关键问题，在控制误干预和额外成本的条件下提供诊断建议或回退，提高任务解决率。

第二，研究检测证据引导的责任动作定位方法，将第一部分在未见任务上输出的候选故障区间、检查点和原始证据用于同状态重放，在固定执行预算内定位首个导致状态稳定退化的动作，并通过撤销或替换及阴性对照验证责任。

理论意义在于分析“在线故障证据”和“动作结果责任”之间的关系，明确在线检测输出能否迁移为可执行定位证据。工程意义在于为软件 Agent 提供故障及时发现、低风险纠偏和失败后调试能力，减少无效长轨迹和人工排查范围。

## 11.3 研究内容与方法

### 研究内容一：软件工程智能体的在线故障检测与纠偏

构建阶段感知的过程表示，将原始动作、工具调用、代码编辑、观察和测试反馈映射到统一事件链；以运行时过程监测持续采集重复、振荡、停滞、无效工具调用和验证退化等信号，利用规则与轻量可执行探针形成确定性证据；只在需要任务语义判断时调用 API，要求其返回证据事件、故障类型、首次告警位置、候选区间和纠偏建议；根据置信度选择仅记录、建议或回退，并通过自然任务解决率、故障召回、误报、检测延迟和受控故障区间指标评价方法。

### 研究内容二：检测证据引导的责任动作定位与执行验证

将第一部分产生的最后健康检查点、首个异常检查点和候选区间作为输入；根据探针结果是否单调选择二分重放、分段重放或候选消减；在固定预算下定位责任动作；对高排名动作执行最小撤销或参数替换，并以相邻、后续和随机动作作为阴性对照，通过官方测试或局部测试验证责任。

### 技术路线

```text
任务与 Agent 执行
        ↓
动作/工具/观察/代码/测试事件化
        ↓
阶段与执行依赖表示
        ↓
低成本规则和可执行探针
        ↓ 触发
API 语义诊断与纠偏建议
        ↓
在线继续 / 建议 / 回退
        ↓ 若仍失败或需要调试
候选故障区间与检查点
        ↓
单调性感知的同状态重放
        ↓
责任动作排序
        ↓
撤销/替换与阴性对照
        ↓
可执行责任证据
```

## 11.4 拟解决的难点

1. **自然过程问题缺少精确标签。** 通过自然运行与受控故障双轨数据，分别评价实际解决收益和精确检测机制。
2. **API 判断可能缺少证据。** 强制结构化输出和事件 ID，并使用编译、导入、局部测试和状态不变式约束判断。
3. **在线干预可能破坏成功运行。** 采用影子模式、低置信不干预和成功运行回归率评价。
4. **故障不一定单调。** 在二分之前检查单调性，对恢复和延迟故障采用分段或候选消减。
5. **相关步骤不等于责任动作。** 使用同状态重放、最小干预和阴性对照形成更强证据。
6. **两章可能再次桥接失败。** 预注册 Predicted/Fixed/Random/Shuffled/Oracle 区间对照，未达到门槛时直接否定递进关系。

## 11.5 预期贡献

1. 给出一套面向软件工程智能体的过程证据驱动在线故障检测方法，并系统分析运行时过程监测、API 语义诊断和可执行探针对任务解决率、误报、误干预和成本的影响；
2. 设计能够被下游诊断直接使用的检测输出，使在线故障检测从单一终局失败概率扩展为故障类型、证据事件、首次告警时刻和候选动作区间；
3. 给出基于同状态自适应重放和最小动作干预的责任动作定位方法，明确单调、可恢复和延迟故障的适用策略；
4. 通过联合预算实验回答在线故障检测区间能否真实改善可执行责任动作定位，并给出成立和失效边界。

以上贡献来自问题定义、证据组织、方法闭环和实验结论，不把过程图、API、二分、OOF 或 Bootstrap 单独包装成创新。

# 12. 最终 GO / NO-GO 决策

## 12.1 现在能够说什么

- 在线故障检测不是过小方向：SAFE 等正式论文将及时故障检测作为整篇研究问题，OOPSLA 2026 又证明软件工程 Agent 需要过程中心的运行分析与在线干预；
- 使用 API 辅助在线故障检测可行，但应采用低成本过程监测与可执行探针触发 API，而不是每步无约束询问；
- 当前检查点和同状态动作重放能力已经形成稳定工程基础；
- 当前 34 任务实验已经证明受控单调语法故障下可以定位并干预责任动作；
- 新方案在研究对象、论文来源和两章逻辑上比“故障验证”方案更完整。

## 12.2 现在不能说什么

- 已经完成自然软件 Agent 在线故障检测；
- 已经证明 API 语义故障诊断能提高解决率；
- 已经证明 RQ1 预测区间能提高 RQ2；
- 已经解决语义、工具参数、延迟和可恢复故障；
- 二分重放是新的理论或适用于所有 Agent 故障；
- 当前 34 个受控案例等同于一般根因定位。

## 12.3 最终判定

> **建议判定：修改后 Conditional-Go。**

开题前必须完成 P1 和最小版 P2，并满足：

1. 在线故障检测区间在三类故障上优于同预算基线；
2. `Predicted Interval + Adaptive Replay` 显著优于固定、随机或打乱区间；
3. 干预闭环不再只存在于未闭合分隔符；
4. API 在线链能够在真实 Agent Loop 中稳定运行；
5. 自然任务至少出现可解释的故障检测或纠偏正信号。

通过后可正式使用：

> **《面向软件工程智能体的在线故障检测与责任动作定位方法研究》**

若 P1 或联合 Gate 失败，应判为 NO-GO，而不是重新把“故障验证”写回第一章。此时可将当前成果收缩为“受控责任动作定位与执行验证”的单项研究，再另选能够独立成立的第二项工作。

# 13. 两分钟导师口语说明

> 我的研究面向会连续检索代码、调用工具、修改仓库并运行测试的软件工程智能体。当前多数评价只看最终任务是否成功，但开发者还需要知道两件事：Agent 在运行中什么时候已经出现值得干预的问题，以及最终失败以后哪个具体动作真正把仓库状态带坏。
>
> 第一项工作研究在线故障检测。它不是再做一个固定前缀成败分类器，而是参考 OOPSLA 2026 的软件 Agent 过程中心分析，把定位、修改、验证等阶段以及动作、工具、代码差异和测试状态组织成可审计的运行表示。运行时过程监测负责低成本采集重复、停滞、无效编辑和验证退化等信号；只在需要任务语义判断时调用 API，要求 API 返回故障类型、原始证据、首次可疑位置、候选动作区间和纠偏建议。第一章以任务解决率、故障召回、误报/误干预率、检测延迟和成本独立验证。
>
> 第二项工作使用第一章在未见任务上输出的最后健康检查点、首个异常检查点和候选区间，从同一仓库状态重放不同长度的动作前缀，定位第一个造成状态稳定转坏的动作，再通过撤销或替换以及相邻、后续动作的负对照验证责任。前期我已经在 34 个任务、8 个仓库上完成了受控语法故障的定位和撤销闭环，Top-1 为 100%，同预算均匀检查为 47.06%，但这个结果使用人工给定的 8 动作窗口，也只覆盖单调语法故障，所以我把它作为机制上界而不是最终结论。
>
> 下一步最关键的实验，是让第一章真正输出故障类型、证据事件和候选区间，再比较预测区间、固定区间、随机区间和人工上界在相同总预算下的责任动作定位与干预结果。只有第一章独立实现更及时、低误报的故障发现并改善运行结果，而且预测区间也显著提高第二章的可执行定位，整篇论文才判定成立。这样研究故事不是拼接已有模块，而是用一条可证伪的证据链回答：在线故障检测是否能够进一步支持可信的责任动作定位。
