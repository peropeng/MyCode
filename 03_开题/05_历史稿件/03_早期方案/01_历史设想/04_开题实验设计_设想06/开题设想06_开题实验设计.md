### 0.2 对现有方案的最终处理

现有实验不能丢弃，反而是本方向能够开题的重要起点：

| 已完成实验 | 新鲜确认集结果 | 它真正证明的内容 |
|---|---:|---|
| 责任主体识别 | Top-1 从 0.5889 提高到 0.7111，相对提升 20.75% | 轨迹证据能够产生有用的责任 Agent 概率 |
| 责任动作定位 | MRR 从 0.3909 提高到 0.5002，相对提升 27.96% | 预测的责任 Agent 概率确实能改善步骤排序 |

但当前第一章不能直接定稿，原因是其消融结果表明：消息数量和位置统计被删除后反而更好，角色/领域先验也没有稳定增益；当前方法主要依靠故障和验证文本信号。因此，现有第一章应被重新定位为：

> **Agent-only 责任识别基线与两章桥接可行性证据。**

正式第一章进一步研究：

> **错误由哪个动作和 Agent 引入，之后经过哪些 Agent、工具和状态传播，哪些后期动作只是暴露症状。**

正式第二章进一步研究：

> **第一章预测出的传播结构，是否比现有“只知道哪个 Agent 可疑”的概率提供更多责任动作定位信息，并能否得到可执行干预支持。**

这不是为了强行追求“别人从未做过”，而是把 Who&When、TraceElephant、Agent-as-a-Judge、SWE-Gym 等已有工作放到一条理论一致的故障链上，利用新数据组合、分层输出和递进实验得到更完整的结论。

### 0.3 是否达到研究生毕设的工作量

若按本文执行，两章的主体工作不是“再增加几个 baseline”，而是：

- 建立跨数据集统一的多智能体事件表示；
- 构造并人工核验故障引入、传播和症状标注子集；
- 完成事件级状态识别、Agent 级责任分解和传播链恢复；
- 完成预测传播先验到动作排序的真实桥接；
- 在自然失败、构造失败和全可观轨迹上进行外部验证；
- 在可执行环境中完成小规模动作替换、撤销或前缀重放。

这足以形成两章独立又递进的硕士论文核心工作。真正的风险不在工作量不足，而在传播标签是否可稳定定义、传播信息是否对动作定位产生额外价值。本文首先用小规模 Gate 验证这两个问题，再进入完整实验。

## 1. 研究背景、目的和整体故事

多智能体 Agent 在完成复杂任务时，会持续进行任务理解、分工、信息检索、计划制定、工具调用、代码或环境状态修改、结果验证和跨 Agent 通信。最终失败通常不是最后一条错误消息独立造成的，而可能来自更早的一次错误搜索、错误计算、错误工具参数或错误代码修改。该错误被写入共享消息、记忆、文件或环境状态后，下游 Agent 会继续把它当成正确输入，最终形成级联传播。负责测试或总结的 Agent 往往只是最后发现问题，不一定是错误源。

现有最终成功率只能说明任务是否完成；Who&When 等工作进一步给出了责任 Agent 和决定性步骤，但单一 Agent 标签仍不能完整描述“错误如何从源头传播到终局”。同一失败中可能同时存在错误引入者、错误传播者和症状暴露者。若只把所有责任压缩成一个 Agent，第一章研究目的较小，也难解释为什么它能稳定帮助第二章。

本研究的总体目的，是提高多智能体系统运行故障的**过程可观测性、责任分解能力和动作级诊断可信度**。第一项工作从完整执行轨迹中识别故障的引入、传播和暴露过程，并在 Agent 层面区分源责任与传播责任；第二项工作把第一项对未见任务产生的真实预测作为软证据，结合动作局部语义和执行依赖对责任动作进行排序，最后通过可执行测试或受控重放区分真正影响结果的动作与表面症状。

整篇论文回答的是一条完整问题链：

```text
某个动作引入错误
        ↓
错误进入消息、工具结果或环境状态
        ↓
其他 Agent 继续依赖并传播错误
        ↓
测试、检查或终止动作暴露最终症状
        ↓
第一章识别传播过程和责任分布
        ↓
第二章利用预测传播证据定位具体动作
        ↓
动作替换、撤销或重放验证结果责任
```

## 2. 两个研究问题及其递进关系

### 2.1 RQ1：故障传播状态识别与责任主体分解

**白话表达：**

> 一次多 Agent 任务失败后，谁最早把状态带错了，错误又经过哪些 Agent 和工具继续传播，最后是谁只把问题暴露出来？

**学术定义：**

> 给定不读取责任金标的完整多智能体执行轨迹，联合识别事件级的故障引入、错误传播和症状暴露状态，恢复 Agent—消息—工具—环境之间的故障传播关系，并聚合得到源责任、传播责任及其不确定性分布。

RQ1 的主要输出不是单一类别，而是：

1. 每个事件属于“正常、故障引入、错误传播、症状暴露”的概率；
2. 最可能的故障源 Agent 和故障源步骤；
3. 从故障源到终局症状的候选传播链；
4. Agent 级的源责任概率和传播责任概率。

“恢复/纠正”可以作为辅助状态分析，但不在第一版中强制成为独立核心类别。若人工标注一致性足够，再扩展为“引入—传播—恢复—症状”四态模型；若一致性不足，保持三种故障状态，避免为了内容多而制造不可靠标签。

### 2.2 RQ2：传播证据引导的责任动作定位与干预验证

**白话表达：**

> 第一章已经判断错误从哪里开始、沿什么路径传播，那么这些预测能不能比“只知道哪个 Agent 可疑”更准确地找到真正带坏任务的具体动作？

**学术定义：**

> 将 RQ1 对未见任务产生的事件状态概率、Agent 责任分布和候选传播链作为软先验，与动作局部语义、工具参数、状态变化和跨步依赖联合，对具体责任动作进行排序，并通过动作替换、撤销或前缀重放检验高排名动作的结果责任。

### 2.3 两个问题为何目的不同

| 维度 | RQ1 | RQ2 |
|---|---|---|
| 研究目的 | 理解失败如何产生和传播 | 找到最值得干预的具体动作 |
| 输出粒度 | 事件状态、传播链、Agent 责任分布 | 动作排名、证据和干预结果 |
| 主要证据 | 完整过程、跨 Agent 依赖、状态演化 | RQ1 预测、动作局部证据、结果变化 |
| 主要指标 | 状态 F1、责任 Agent、传播链质量 | MRR、Recall@K、翻转率 |
| 应用价值 | 过程分析和故障责任分解 | 调试、修复和根因验证 |

### 2.4 两个问题为何真实递进

现有实验已经证明：预测责任 Agent 概率能把动作定位 MRR 从 0.3909 提高到 0.5002。因此“上游责任信息能够帮助下游步骤定位”已有真实证据。

新方案不再只问 Agent 概率是否有用，而是比较：

```text
无上游信息
    < 预测责任 Agent 概率
    < 预测故障传播链
    < 人工传播链上界
```

若预测传播链不能优于现有 Agent-only 概率，则第一章增加的传播建模没有给第二章提供额外价值。该结果会直接否定新方案，而不是用更多解释性图表掩盖桥接失败。

## 4. 成熟理论基础：只保留三条

### 4.1 软件可靠性的“故障—错误状态—失效”链

来源：Avizienis 等，**Basic Concepts and Taxonomy of Dependable and Secure Computing**  
链接：https://arxiv.org/abs/cs/0101024

在本文中的映射：

- **故障**：错误搜索、错误计算、错误工具参数、错误修改或错误终止动作；
- **错误状态**：错误进入共享消息、计划、代码、文件、数据库或环境状态；
- **失效**：最终测试不通过、答案错误或任务未完成。

它解释了为什么最后报错的 Agent 可能只是症状，也解释了第一章为什么要研究传播过程而不是只做角色分类。

### 4.2 过程监督与时序状态识别

过程监督来源：**Let’s Verify Step by Step**  
链接：https://arxiv.org/abs/2305.20050

变化与状态转移参考：**Selective Review of Offline Change Point Detection Methods**  
链接：https://arxiv.org/abs/2011.01857

本文不照搬数学推理过程奖励或变化点算法，而使用两个成熟观点：

1. 最终结果无法替代对中间过程的评价；
2. 事件状态之间存在顺序和转移约束，不能把每一步当作互不相关的文本分类。

### 4.3 候选排序与干预验证

学习排序参考：**Pairwise Learning to Rank by Neural Networks Revisited**  
链接：https://arxiv.org/abs/1909.02768

结构化原因与解释参考：**Causes and Explanations: A Structural-Model Approach**  
链接：https://arxiv.org/abs/1301.2275

本文使用的机制是：

- 对候选动作进行相对排序，而不是要求模型一次生成唯一根因；
- 相关性和文本解释只生成候选；
- 改变候选动作后结果是否改变，提供更强的责任证据。

### 4.4 哪些不是理论创新

以下都属于实现或协议，不得包装成新理论：

- 使用 Logistic、LightGBM、GRU、TCN、Transformer 或图神经网络中的哪一种；
- 使用 Qwen3-Embedding、BGE、TF-IDF 或 hashing；
- 任务级折外预测、随机种子、bootstrap 和文件格式；
- 事件窗口长度、Top-K 大小和阈值；
- Docker、Parquet、JSON 和缓存目录。

### 5.2 新增“故障传播标注子集”

第一章工作量的核心之一，是在已有责任 Agent/步骤标签之上增加传播过程标注。建议不重新做一个巨型 benchmark，而是构造一个规模受控、定义严格的研究子集。

#### 5.2.1 主标签

每个事件只使用下面四类之一：

1. **正常事件**：没有引入或继续使用错误状态；
2. **故障引入事件**：首次形成与任务要求不一致的承诺、参数、结论或状态改变；
3. **错误传播事件**：继续读取、引用、执行或扩大已有错误状态；
4. **症状暴露事件**：检测、报告或呈现失败，但没有引入导致失败的错误状态。

“恢复事件”先作为附加二值属性：该事件是否试图修正已有错误；修正后错误是否实际消失。只有标注一致性足够时，才将恢复升级为第五种主状态。

#### 5.2.2 传播边

只标注可解释的有限依赖边：

- 消息引用或内容继承；
- 工具输入使用前一步生成的参数、实体或文件；
- 文件/环境状态被后续动作读取；
- 测试或检查使用前一步产生的结果；
- 管理 Agent 根据下游报告作出继续、终止或分派决定。

不要求构建语言模型内部不可观测的“真正思维因果图”。传播图只描述执行轨迹中可观察的依赖关系。

#### 5.2.3 标注规模

开题前建议完成：

- **150—200 条双人独立标注轨迹**；
- 覆盖 AFTraj、Who&When/Pro 和 TraceElephant 至少两个来源；
- 每类至少 30—50 条有效事件；
- 至少 50 条长轨迹和 50 条多角色轨迹。

开题后正式扩大到：

- 300—500 条人工 Gold；
- 800—1,500 条规则或模型产生的 Silver 标签；
- Silver 只用于训练，正式主指标只在人工 Gold 上计算。

#### 5.2.4 标注一致性 Gate

建议使用 Cohen’s kappa 或 Krippendorff’s alpha。以下阈值是项目管理门，不是理论真理：

- `≥ 0.65`：标签可用于开题和模型实验；
- `0.50—0.65`：合并容易混淆的类别，重新定义；
- `< 0.50`：停止传播状态多分类，不得靠 Judge 自动标签代替人工一致性。

### 5.3 数据伪影与捷径控制

现有 Agent-only 模型可能利用角色名称、发言数量和显式错误词。正式实验必须加入：

1. **角色名匿名化**：Planner、Coder、Critic 改为 Agent A/B/C；
2. **角色顺序随机置换**：保持行为不变，打乱显示名称；
3. **显式错误词屏蔽**：屏蔽 failure、incorrect、error、mistake 等明显词；
4. **注入模板清洗**：Who&When Pro 中不允许把注入错误描述直接作为输入；
5. **任务级分组**：同任务改写、重复执行和成败配对不得跨训练/测试。

这些不是额外创新，而是证明模型没有走捷径的必要可信性实验。

## 6. 任务级折外预测 OOF：完整白话解释

### 6.1 OOF 到底是什么

OOF 是 **out-of-fold prediction**，中文可称“折外预测”。它的意思不是“模型在测试集预测”，而是：

> 给第二章使用的每一个第一章预测，都必须来自没有使用该任务标签训练过的模型。

假设有 10 个独立任务：

```text
第 1 折测试：任务 1、2；训练：任务 3—10
第 2 折测试：任务 3、4；训练：任务 1、2、5—10
第 3 折测试：任务 5、6；训练：其余任务
第 4 折测试：任务 7、8；训练：其余任务
第 5 折测试：任务 9、10；训练：其余任务
```

把五次测试预测拼起来后，任务 1—10 都有一个预测；但每个预测都来自没有训练过该任务的模型。这组预测才可以交给第二章。

### 6.2 为什么普通训练分数不能交给第二章

若第一章在任务 1 上训练后，又把任务 1 的高置信预测交给第二章，第二章会间接得到任务 1 的金标信息。此时“第一章帮助第二章”可能只是数据泄漏。

### 6.3 为什么必须按任务分组

若同一个任务有多次 rollout，不能把其中三条放训练、两条放测试。模型可能记住问题文本、角色模板或答案。正确做法是：

> 同一个任务的所有轨迹必须放在同一折。

### 6.4 正式实验的嵌套结构

```text
外层训练任务
    ├─ 内层分折：产生第一章的训练集 OOF 预测
    └─ 用全部外层训练任务重新训练第一章模型

外层测试任务
    └─ 由只见过外层训练任务的第一章模型产生预测
```

第二章在外层训练任务的 OOF 预测上训练，在外层测试任务的样本外预测上测试。OOF 是防泄漏协议，不是论文创新。

## 7. 实验一：故障传播状态识别与责任主体分解

### 7.1 实验目的

当前责任 Agent 分类只回答“先查谁”。正式第一章需要进一步回答：

1. 错误在哪个事件首次被引入；
2. 哪些后续事件继续依赖并传播错误；
3. 哪些事件只是测试、总结或终止时暴露症状；
4. Agent 层面的源责任和传播责任如何区分；
5. 这种区分能否跨角色名、数据集和 Agent 框架保持稳定。

### 7.2 实验一的三个研究工作点及来源

#### 创新点 E1-I1：全过程多源证据表示

**要解决的问题：**只看 Agent 输出会丢失输入、工具参数、工具结果和环境状态；只看错误词又容易把检查者误判为根因。

**核心论文来源：**

- TraceElephant：完整输入、输出、工具调用和系统上下文；
- Agent-as-a-Judge：按任务要求主动定位和验证过程证据；
- SWE-Gym：代码修改、测试和环境反馈。

**模块内容：**

将原始轨迹统一成事件：

```text
event_id
actor
role_type
action_type
input_message
tool_name
tool_arguments
observation
state_read
state_write
requirement_or_test_evidence
```

形成三个证据视图：

1. 行为与工具视图；
2. 任务要求与验证视图；
3. 状态读写与跨 Agent 依赖视图。

**预期作用：**区分“说到错误”“检测到错误”与“真正产生错误状态”。

#### 创新点 E1-I2：带状态转移约束的故障传播识别

**要解决的问题：**故障引入、传播和症状存在顺序关系，独立逐步分类容易把后期错误词最多的步骤排为源头。

**核心论文来源：**

- Who&When：责任 Agent 和决定性步骤；
- Plan-RewardBench：长轨迹困难负例、错误恢复和最小扰动轨迹对；
- 成熟理论：故障—错误状态—失效和时序状态转移。

**模块内容：**

对事件序列编码后，使用轻量序列模型加状态转移约束。例如：

```text
正常 → 故障引入 → 错误传播 → 症状暴露
                    ↘ 恢复/停止传播（辅助属性）
```

模型可以是 BiGRU/TCN/轻量 Transformer 加 CRF，也可以先用规则约束的动态规划。模型名称不是创新，关键是状态定义和可验证转移。

**预期作用：**让模型从“哪个事件文本最像错误”转向“错误状态如何沿时间延续”。

#### 创新点 E1-I3：事件到 Agent 的多粒度责任分解

**要解决的问题：**当前单一责任 Agent 标签不能区分错误制造者、传播者和症状报告者。

**核心论文来源：**

- Who&When：责任主体和步骤的层级任务；
- TraceElephant：完整可观测条件下的责任归因；
- 现有前期实验：Agent-only 概率已证明可帮助步骤定位。

**模块内容：**

将事件级概率沿依赖关系聚合成：

- 源责任概率；
- 传播责任概率；
- 症状/检测概率。

允许输出多个责任候选或概率分布，不强迫每条轨迹只有一个绝对唯一责任 Agent。

**预期作用：**提供第二章需要的传播软先验，并减少把检查者或最后发言者误判为根因。

### 7.3 候选模型的最小实现

```text
原始轨迹
    ↓
事件规范化与证据提取
    ↓
文本/结构/状态向量
    ↓
轻量时序编码器
    ↓
事件状态头：正常/引入/传播/症状
    ↓
依赖聚合
    ↓
Agent 源责任与传播责任概率
```

先实现轻量版，不需要训练大模型：

- 文本使用冻结 embedding；
- 时序模型控制在 0.5B embedding + 小型 GRU/TCN/Transformer；
- 图依赖先用显式规则边，再验证图学习是否有必要；
- LLM 仅用于辅助取证或标注候选，不直接提供测试 Gold。

### 7.4 主体实验内容

实验一不是只有一个 Top-1 表格，应包含四个互相关联的主体问题。

#### 主任务 A：故障源 Agent 和步骤

- Agent Top-1 / macro-F1；
- 步骤 MRR、Recall@1/3/5；
- 与现有 0.7111 Agent-only 模型比较。

#### 主任务 B：事件状态识别

- 引入、传播、症状的 macro-F1；
- 故障引入边界偏差；
- 传播状态持续区间 IoU 或 token/event-level F1。

#### 主任务 C：传播链恢复

- Gold 依赖边 Recall / Precision；
- 从源步骤到症状步骤的路径覆盖率；
- Gold 源步骤是否进入恢复链 Top-K。

#### 主任务 D：责任分解的有效性

- 源责任 Agent 准确率；
- 传播责任候选集合 F1；
- 症状角色误判率；
- 多责任轨迹的 set-valued accuracy。

### 7.5 五个主要 baseline

为控制工作量，正式主体 baseline 最多五组：

1. **规则基线**：发言最多、最后发言、错误词最多；
2. **当前 Agent-only 模型**：现有 0.7111 方法，作为必须超过或解释的内部强基线；
3. **Who&When 官方方法族**：All-at-once / Step-by-step / Binary-search 统一作为正式方法族报告；
4. **Agent-as-a-Judge 或等成本完整轨迹 Judge**：主动读取证据后直接判断；
5. **时序语义 baseline**：StepFinder 或同等 BiGRU/TCN/Transformer 序列方法。

VerifyMAS、FALAT、TrajDebug 可根据公开代码状态作为补充对照，不要求全部成为主表，否则会让项目变成复现竞赛。

### 7.6 只保留三个消融

1. **去掉全过程证据**：只保留 Agent 输出文本；
2. **去掉状态转移建模**：每一步独立分类；
3. **去掉依赖聚合**：直接按事件分数平均得到 Agent 分数。

消融回答三个模块是否有用，不再围绕词表、隐藏维度和窗口长度生成大量小变体。

### 7.7 稳健性和进一步分析

这些分析属于主体实验的一部分，不是额外 baseline：

- 角色名匿名化；
- 显式错误词屏蔽；
- 完整轨迹与部分可观轨迹对比；
- 短/中/长轨迹；
- 2—3 Agent 与更多 Agent；
- coding、math、general agent；
- AFTraj 内测、Who&When 和 TraceElephant 外测；
- 注入错误与自然错误分层。

### 7.8 实验一开题前目标

#### 最低开题 Gate

1. 完成 150—200 条双人传播标注；一致性 `κ/α ≥ 0.65`；
2. 源步骤和 Agent 标签映射率 ≥ 90%；
3. 角色匿名化后，现有或精简 Agent-only 模型仍明显高于发言最多基线；
4. Oracle 传播链在第二章的桥接 Pilot 中优于 Oracle Agent-only；
5. 至少一个轻量传播模型在人工 Gold 上达到可用水平，例如事件状态 macro-F1 约 0.55 以上，并且不是只命中多数类。

这里的 0.55 是工程可行门，不是最终论文必须写成的理论阈值。开题需要证明标签可学、桥接有空间，而不是开题前完成最终 SOTA。

#### 完整论文目标

- 源 Agent 识别不低于现有 0.7111，并在外部数据上优于当前 Agent-only；
- 事件状态 macro-F1 达到 0.60 左右或稳定优于无转移序列基线；
- 症状角色误判率相对 Agent-only 明显下降；
- 跨数据外测仍有正增益，任务级置信区间不跨 0；
- 三个模块各有独立边际贡献。

### 7.9 否定实验一的结果

出现以下情况应缩小或停止第一章：

- 人工标注一致性低于 0.50；
- 角色匿名化或错误词屏蔽后性能接近随机；
- 状态转移模型不优于独立文本分类；
- 传播链不能恢复已知注入源和下游依赖；
- 强 Who&When/StepFinder 基线全面优于本方法，且传播责任分解没有新的可解释结论。

## 8. 实验二：传播证据引导的责任动作定位与干预验证

### 8.1 实验目的

实验二不再证明“责任 Agent 信息有用”，因为现有实验已经证明这一点。它需要回答一个更进一步的问题：

> 在已经拥有预测 Agent 概率后，第一章新增的故障引入、传播和症状信息，是否还能稳定改善责任动作定位？

### 8.2 实验二的三个研究工作点及来源

#### 创新点 E2-I1：预测传播链软先验

**要解决的问题：**Agent-only 先验只知道“谁可疑”，不知道该 Agent 的哪次动作引入错误，也不知道后期高风险步骤是否只是症状。

**来源：**

- 当前真实实验：Predicted Agent Prior 已使 MRR 从 0.3909 提升到 0.5002；
- Who&When：责任 Agent 与决定性步骤；
- TraceElephant：完整轨迹中的输入、工具和上下文。

**模块内容：**

第二章直接读取第一章对未见任务输出的：

- 故障引入概率；
- 错误传播概率；
- 症状概率；
- Agent 源责任和传播责任概率；
- 候选传播路径。

所有先验都是软加权，不硬删除低概率 Agent 或步骤，避免第一章预测错误时把真实根因永久裁掉。

#### 创新点 E2-I2：依赖感知的动作学习排序

**要解决的问题：**单独依靠局部错误词会偏向后期测试和失败报告；单独依靠 Agent 概率又无法区分同一 Agent 的多个动作。

**来源：**

- Who&When 和 StepFinder：步骤级归因与时序语义排序；
- TraceElephant：完整执行依赖；
- 成熟理论：Pairwise Learning-to-Rank；
- FALAT：依赖引导搜索作为前沿压力。

**模块内容：**

动作最终分数可采用如下概念形式：

```text
动作局部证据
+ Agent 源责任先验
+ 事件故障引入概率
+ 下游依赖与传播强度
- 症状暴露概率
- 已恢复证据
```

实现可以是线性排序器、LambdaMART 或轻量神经排序器。论文贡献是证据组合和桥接结论，不是某个排序器名字。

#### 创新点 E2-I3：定位结果的可执行验证

**要解决的问题：**数据集中的决定性步骤和 Judge 解释仍然只是标注或相关性证据。

**核心论文来源：**

- SWE-Gym：可执行仓库、单元测试和 verifier；
- TraceElephant：可重放多 Agent 环境和中间干预可能；
- Who&When Pro：成功前缀精确重放后的单点错误注入。

**模块内容：**

对 Top-K 候选做以下一种或多种操作：

- 替换错误工具参数；
- 撤销或替换错误代码编辑；
- 恢复到动作前状态并重放固定后缀；
- 对自然语言多 Agent 任务，替换错误消息后重新执行下游 Agent；
- 与随机同 Agent 动作、相邻动作和最后症状动作作阴性对照。

### 8.3 两章桥接的核心条件

所有条件使用同一个候选池、排序器、上下文长度和预算，只替换上游先验：

1. **No Prior**：没有第一章信息；
2. **Random Prior**：随机生成同形状概率；
3. **Shuffled Prior**：把真实预测在任务之间打乱；
4. **Predicted Agent-only Prior**：当前已经验证的方法；
5. **Predicted Propagation Prior**：新方法；
6. **Oracle Agent Prior**：人工正确 Agent，上界；
7. **Oracle Propagation Prior**：人工传播链，上界。

Random、Shuffled 和 Oracle 是依赖对照，不重复计入五个主要 baseline。

### 8.4 五个主要 baseline

1. **Local / No Bridge**：只用动作局部文本、工具和状态证据；
2. **当前 Predicted Agent-only**：现有 MRR 0.5002 方法，是新方法必须正面对比的最重要基线；
3. **Who&When 官方直接定位方法**；
4. **StepFinder 或同等时序语义定位方法**；
5. **完整轨迹 Agent-as-a-Judge / TraceElephant 定位协议**。

### 8.5 主体实验内容

#### 主任务 A：离线责任动作排序

数据：AFTraj 新划分、Who&When、Who&When Pro 文本子集、TraceElephant。

指标：

- MRR；
- Recall@1/3/5；
- Joint Agent-Step Accuracy；
- Gold coverage；
- 候选压缩率；
- 症状步骤被错误排为第 1 的比例。

#### 主任务 B：桥接增量

核心比较：

```text
Predicted Propagation
    vs Predicted Agent-only
    vs No / Random / Shuffled
```

该比较比“新方法对最近一步”重要得多，因为它回答第一章增加传播建模是否有真实必要性。

#### 主任务 C：外部泛化

- AFTraj 训练，Who&When/TraceElephant 测试；
- 构造错误与自然错误分表；
- 角色名匿名；
- 不同轨迹长度和 Agent 数量；
- coding、math 和 general agent 分层。

#### 主任务 D：可执行干预

先做 20 个独立任务 pilot：

- 至少 15/20 可以稳定重放；
- 每个任务测试 Top-1 或 Top-3 候选；
- 同时测试随机动作、相邻动作和症状动作；
- 记录失败→成功、失败类型变化和非回归测试。

Pilot 通过后扩大到 50—100 个独立任务。若环境成本过高，正式论文可保持 20—50 个高质量干预案例，但必须报告任务选择规则，不能只挑成功案例。

### 8.6 只保留三个消融

1. 去掉第一章传播先验，只保留 Agent-only；
2. 去掉动作—消息—工具—状态依赖；
3. 去掉症状抑制或低置信全轨迹回退。

### 8.7 开题前桥接 Gate

在开发完整第一章前，先做 Oracle Gate：

```text
Oracle Propagation > Oracle Agent-only > No Prior
```

建议至少使用 100 条具有传播标注的独立任务。开题前要求：

- Oracle Propagation 相对 Oracle Agent-only 在 MRR 或 Recall@3 上有稳定正增益；
- 配对 bootstrap 95% 区间下界大于 0，或症状误判率至少下降 10 个百分点；
- 若 Oracle 传播链都不优于 Agent-only，则传播建模对第二章没有价值，本方案不得开题。

### 8.8 实验二开题和论文目标

#### 最低开题目标

- 当前 Agent-only 桥接结果能够在重新冻结的任务划分上复现；
- Oracle Propagation 明显优于 Oracle Agent-only；
- 最小 Predicted Propagation 模型相对 Agent-only 至少呈稳定正增益，不要求开题前达到最终 10%；
- 至少 5 个已有或新建可执行案例能完成动作替换接口。

#### 完整论文目标

- Predicted Propagation 相对 Predicted Agent-only 的 MRR 或 Recall@3 提升约 8%—10%，任务级置信区间下界大于 0；
- 同时优于 No、Random 和 Shuffled；
- 症状误判率显著下降；
- 外部数据上不出现全面负迁移；
- Top-3 候选干预翻转率相对随机/症状动作提高至少 15 个百分点；
- 干预成功不以引入额外测试回归为代价。

这些数值是论文项目目标，不是成熟理论规定。最终应报告原始分数、绝对差、相对差和置信区间，而不是只报告“提升百分比”。

### 8.9 否定实验二的结果

- Oracle Propagation 不优于 Oracle Agent-only；
- Predicted Propagation 与 Shuffled 相同；
- Predicted Propagation 不优于当前 Agent-only；
- 排名提高但高排名动作的干预结果与随机动作相同；
- 增益只来自更长上下文、更多 LLM 调用或更大模型；
- 传播先验导致 Gold 大规模被裁掉。

### 9.1 已完成的基础证据

### 9.2 正式开题前必须补齐

| Gate | 最低要求 | 为什么必要 |
|---|---|---|
| 文献身份 | 五篇核心论文的正式页、CCF、代码、数据和许可证核验表 | 防止把预印本或特殊 track 当核心正式论文 |

| Oracle 桥接 | Oracle Propagation > Oracle Agent-only | 证明第一章扩展信息值得做 |
| 最小模型 | 一个轻量传播模型能超过多数类/独立分类并产生 OOF 输出 | 证明研究可计算、可训练 |
| 实验环境 | AFTraj/Who&When/TraceElephant adapter 可运行；至少 5 个可执行案例 | 证明第二章不依赖不存在的私有环境 |

只要上述 Gate 通过，即使完整 Predicted Propagation 还未达到最终目标，也足以开题，因为：

- 现有 Agent-only 两章桥接已经有真实正结果；
- 新传播链的人工上界证明了进一步空间；
- 数据、标签、模型和执行接口都已可运行；
- 完整模型提升属于开题后的研究任务，而不是开题前必须全部完成的结论。

### 9.3 不能开题的红线

以下任一情况出现，应停止该方向而不是继续包装：

1. 传播标签人工一致性长期低于 0.50；
2. Oracle 传播链不优于 Agent-only；
3. 角色匿名后现有责任 Agent 模型接近随机；
4. 传播链只能依靠读取 `mistake_reason`、注入模板或其他金标字段；
5. 数据许可证不允许研究或复现；
6. 第一章输出不能以任务级 OOF 方式交给第二章。

## 15. 两分钟导师口语说明

> 我的研究面向大语言模型多智能体系统的失败分析。现有工作通常定位一个责任 Agent 和一个决定性步骤，但一次失败往往不是单点现象：某个 Agent 先引入错误，其他 Agent 继续使用错误消息、工具结果或环境状态，最后测试或检查 Agent 才把问题暴露出来。因此，我的第一项工作不再只做“哪个 Agent 错了”的分类，而是利用完整轨迹中的消息、工具和状态证据，识别故障引入、错误传播和症状暴露，并把事件级结果聚合成源责任和传播责任。这个设计继承 Who&When 的责任 Agent/步骤任务、TraceElephant 的完整可观测轨迹，以及 Agent-as-a-Judge 的过程取证机制。
>
> 第二项工作使用第一项在未见任务上产生的真实预测，而不是人工金标，把传播概率和执行依赖加入责任动作排序。核心对照是无先验、随机先验、当前已经跑通的责任 Agent 先验、预测传播先验和人工传播上界。我会重点验证传播先验是否比现有 Agent-only 方法进一步提高 MRR 和前 K 召回，并减少把后期症状当根因。最后在 SWE-Gym 或 TraceElephant 可执行环境中，对高排名动作做替换、撤销或重放，比较随机动作和症状动作，判断定位结果是否得到结果翻转支持。
>
> 前期我已经在 180 条新鲜确认轨迹上证明责任 Agent 预测比发言最多基线提高约 21%，使用这个预测后步骤 MRR 相对仅局部证据提高约 28%，所以两章桥接已经有可行性。开题前我还需要完成约 150 到 200 条传播标注，并验证人工传播链确实比单纯责任 Agent 更能帮助动作定位。若这个 Oracle Gate 不成立，我会停止该方向；若成立，就说明数据、理论链和实验闭环足以支撑开题。

### 18.1 明确结论

> **基础两阶段方案 GO，可以开题；“故障传播必须进一步改善动作定位”的升级方案 NO-GO，不写成开题阶段必须成功的核心承诺。**

推荐题目相应收敛为：

> **《面向大语言模型多智能体系统的运行故障分析与责任动作定位方法研究》**

第一章研究责任主体识别及错误源/末端症状的混淆分析；第二章使用第一章在未见任务上产生的任务级折外责任概率定位具体责任动作，并在后续加入动作替换、撤销或前缀重放。传播图保留为解释、症状区分和后续诊断，不再预先承诺它能独立带来第二章性能增量。

### 18.2 GO 的真实证据

在 AFTraj 新鲜确认集的预注册协议上重新复核：

| 实验 | 最强公平基线 | 方法 | 相对提升 | 95% 置信区间 | 决策 |
|---|---:|---:|---:|---:|---|
| E1 责任主体识别 Top-1 | 0.5889 | 0.7111 | 20.75% | [0.0611, 0.1889] | GO |
| E2 责任动作定位 MRR | 0.3909 | 0.5002 | 27.96% | [0.0810, 0.1389] | GO |

复核副本与原确认结果的 SHA256 完全一致：`7722178c087ddee1ce8ea526543d7b64ebe03043c61a8a30d13b0b49739c3cce`。传播 Pilot 单元测试 6/6 通过，组 6 AFTraj 集成测试 13/13 通过。

### 18.3 传播升级的否定证据

Who&When Pro 文本数据审计覆盖 6,257 条原始记录；纳入六种多智能体框架 2,670 条、14,792 个候选事件和 1,069 个原始任务组。修复首次实现中 Predicted/Shuffled 共用向量的问题后，冻结 v1 的预测传播相对 Agent-only 最高仅在 Recall@1 上提高 5.72%，低于预注册 10% 门槛。进一步移除 `is_injected/is_replayed` 依赖、对所有事件统一清洗的 v2 诊断中，MRR 相对提高 0.04%，Recall@1 相对提高 1.61%，Oracle 传播也没有稳定优于 Oracle Agent。

因此不能把“传播链相对责任 Agent 一定提供额外动作定位价值”写成已经证实的研究假设，也不能通过降低 10% 门槛把它包装成 GO。若未来重新启用传播主线，最低前提是新增人工核验的传播状态/依赖边，并在可重放环境中完成动作干预对照。

### 18.4 与 Who&When Pro 及近期工作的最终边界

Who&When Pro 的成功前缀精确重放、单点错误注入和 who/when/type 金标可作为构造数据与干预协议参考，但它当前是预印本，不能冒充 CCF A 核心正式论文。FALAT 已覆盖源—传播—症状区分、类型化依赖和反事实充分性；TrajDebug 已覆盖错误生命周期与终局影响；Causal Agent Replay 已覆盖动作级干预、重放和置信区间；ErrorProbe 已覆盖症状驱动反向追踪与可执行验证。因此这些单点机制不再作为本文“首次创新”。

可开题方案的核心论文组保留正式 CCF A 工作：Who&When（ICML 2025）、TraceElephant（ACL 2026 Long）、Agent-as-a-Judge（ICML 2025）和 SWE-Gym（ICML 2025）。可辩护的进一步内容是：在新数据划分上验证责任主体概率到动作排序的严格任务级折外桥接，并用后续可执行实验检验责任动作，而不是重复命名已有模块。
